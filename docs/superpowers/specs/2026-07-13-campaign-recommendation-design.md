## 1. 결정 경위 요약

피봇 방향(캠페인 브리프 → 인플루언서 추천 + 근거)과 파이프라인 5단계
(①제출→②브리프 분석→③매칭→④근거 서술→서빙)는 사용자가 제시한 출발점이고,
아래 결정들을 순서대로 함께 확정했다:

| 결정 | 선택 | 검토한 대안 |
|---|---|---|
| 브리프 폼 예상 필드 | **핵심 4종** — 제품 카테고리·제품 이미지·캠페인 목표·팔로워 규모 (폼은 팀원이 확정 중 — superset 설계 후 덜어내기) | 캠페인 조건류(예산·기간), 타깃 오디언스류(§10), 자유 서술류 |
| 카테고리 매칭 시맨틱 | **2층 하이브리드** — 대분류는 하드 필터(분포 비율 임계), 중·소분류는 소프트 점수 | 순수 하드 필터(50:50 계정 자의적 탈락), 순수 소프트(엉뚱한 카테고리 상위 혼입) |
| 캠페인 목표 어휘 | **3종** — 인지도 / 전환 / 신뢰·리뷰 (셋 다 기존 B1·B2·C1 데이터로 축이 성립) | 2종 미니멀, 4종+(브랜딩 — 페르소나 축 없어 보류) |
| 캠페인 파이프라인 소유 | **was** — 캠페인은 상태·트랜잭션을 가진 서비스 데이터, 브리프는 raw와 무관한 사용자 입력 | analytics 소유(서비스 데이터를 분석 층이 읽는 새 화살표 발생), 신설 모듈(과분) |
| 매칭 재료 형태 | **전용 프로필 테이블** `influencer_profiles` (인플루언서당 1행, analytics 배치 미러) | 기존 미러 조합(매칭 축 부재 + 조인 범벅), 하이브리드 |
| 제품 이미지 역할 | **매칭 속성까지 추출** — VLM이 속성·톤을 뽑아 소프트 점수 축으로 | 카테고리 보조+서술용(어휘 신설 불필요), MVP 제외 |
| 속성·톤 어휘 관리 | **`contract-analysis`에 enum** (§3) | DB 테이블 관리, 하이브리드 |
| 입력→로직 라우팅 구조 | **명시적 라우팅 계층** — `MatchingCriteria` 조립 한 곳에 필드→로직 매핑 집중 | 제네릭 룰 엔진(과설계 — 07-12 MaterializationService 전철), 단계별 직접 참조(수정 지점 분산) |

## 2. 전체 구조

```
[크롤링] crawler   (변화 없음) ──쓰기──▶ raw DB
                                          · 분류 계층(뷰티>마스크팩>…)도 여기 소속 — 카테고리 어휘의 원천

[분석]   analytics = 프로필 팩토리
           raw 읽기 ──▶ ⓐ 콘텐츠 속성 VLM 배치 (신설: 썸네일 → 속성 태그, 공유 어휘 강제)
                        ⓑ influencer_profiles 미러 (인플루언서당 1행: 숫자 축 + 분류 분포 + 속성 집계)
                        ⓒ category_hierarchy 미러 (폼 선택지·검증용 — §7-1)
           ──쓰기──▶ analysis DB

[서빙]   was = 캠페인 오케스트레이터
           ① 제출(폼 검증·저장) → ② 브리프 이미지 VLM(속성 추출, 같은 공유 어휘)
           → ③ 매칭(influencer_profiles 읽기 전용 + 폼 값 바인드) → ④ 근거 서술 → 폴링 서빙
           ──읽기/쓰기──▶ app 스키마 (campaign·recommendation·후보)
```

**LLM 소속 원칙은 대상 기준으로 이원화**: raw 콘텐츠(인플루언서)를 분석하는 LLM은
analytics(재현 가능한 분석 결과로 미러), 마케터 제출물(브리프 이미지·서술 생성)을 다루는
LLM은 was(서비스 트랜잭션의 일부로 `app` 스키마에 저장). 근거: 캠페인은 상태·트랜잭션을
가진 서비스 데이터고, 브리프 이미지는 raw DB와 무관한 사용자 입력이다.

**공유 모듈 +1 — `llm-core`**: was도 Anthropic 호출이 필요해지므로 F에서 만든 호출
골격(인증·재시도·포트)을 분리해 analytics·was가 같이 쓴다. 대안(복붙)은 재시도·비용가드
수정이 두 곳 관리가 됨. 계약 모듈처럼 얇게 — 호출 인프라만, 프롬프트·비즈니스 로직 금지.

## 3. 어휘 — 왜 필요하고, 어디서 오나

매칭은 결국 단어 비교다: 브리프 쪽이 "[립틴트]"라 하고 인플루언서 쪽이 "[립 메이크업]"이라
하면 SQL은 연결하지 못한다. LLM은 자유 생성이라 강제하지 않으면 같은 이미지도 실행마다
다른 단어를 뱉는다. 그래서 **비교가 일어나는 의미 축은 양쪽이 같은 허용 목록(closed set)에서만
단어를 고르도록 강제**해야 한다. 숫자 축(팔로워·조회·비율)은 이 문제가 없다.

설계 시점 실데이터 확인 결과 어휘는 **두 원천**으로 나뉜다:

| 어휘 | 원천 | 관리 | 쓰는 곳 |
|---|---|---|---|
| 카테고리 | **crawler 분류 계층 재사용** (신설 아님) — 풀 전 계정이 이 계층의 키워드로 발굴돼 분류가 이미 붙어 있음 | 기존대로 raw DB + 어드민 UI (was에는 미러로 전달 — §7-1) | 폼 선택지, 프로필 분포, 하드 필터 |
| 제품 속성·톤 | **신설** — 이미지에서 매칭 속성을 추출하기로 한 결정의 귀결 | `contract-analysis`에 enum | 양쪽 VLM 프롬프트 강제, 소프트 점수 축 |
| 캠페인 목표 | 신설 — 인지도/전환/신뢰·리뷰 | `contract-analysis`에 enum | 폼 선택지, 가중치 프리셋 키 |

속성·톤을 enum(코드)으로 두는 이유: 이 어휘가 바뀌면 양쪽 프롬프트·프로필 집계·기존
분석분이 전부 영향받으므로 "재배포 없이 수정"은 이득이 아니라 위험이다. 컴파일 타임에
폼—VLM—프로필—프리셋이 같은 단어임이 보장되는 쪽을 택한다. 어휘 밖 출력은 폐기(B3
`AnthropicVisionAnalyzer`에서 검증된 방어 패턴).

**선택의 대가(명시)**: 인플루언서 쪽에도 같은 속성이 있어야 비교가 성립하므로, 콘텐츠 속성
VLM 배치(설계 시점 산출물 0건)를 신설 어휘로 실제로 돌려야 한다. 풀 114계정 × 최근 12개
≈ 1,400장 — B2 실측 기준 haiku급 수 달러 수준이나 풀과 함께 커지는 비용이다.

## 4. 폼 입력 → 로직 라우팅

### 4-1. 라우팅의 단일 지점

폼 값 + ②가 채운 속성이 캠페인 행에 모이면, 매칭 직전에 **`MatchingCriteria` 하나로
조립**한다. "어떤 입력이 어떤 로직을 타는가"는 이 조립 코드 한 곳에만 존재 — 폼이
확정·변경되면 이 지점만 고친다.

```
campaign 행 ──▶ MatchingCriteria
                 ├─ 하드 필터부  : categoryGroup(대분류), followerMin/Max
                 ├─ 스코어부     : subCategories(중·소분류), productAttrs(속성·톤), goal(→프리셋 키)
                 └─ 통과부       : 브랜드명·설명 텍스트 → ④ 서술 컨텍스트로 직행 (매칭 무관)
```

### 4-2. 필드별 라우팅 표

| 폼 입력 | ① 제출 시 | ② 브리프 분석 | ③ 매칭에서 | ④ 서술에서 |
|---|---|---|---|---|
| 제품 카테고리 (crawler 계층에서 선택) | 어휘 검증(계층에 존재?) | — | 대분류: **하드 필터** — 해당 분류 콘텐츠 비율 ≥ 임계(설정값) / 중·소분류: **소프트 축** — 분포 일치 점수 | "클렌징 콘텐츠가 최근 12개 중 7개" 식 팩트 |
| 팔로워 규모 (범위) | min≤max 검증 | — | **하드 필터** — `followers BETWEEN ? AND ?` | 팩트 카드 원값 |
| 캠페인 목표 (3종 enum) | 어휘 검증 | — | **가중치 프리셋 선택 키** — WHERE 아님, 점수식 선택 | 서술 톤 힌트 |
| 제품 이미지 | 저장·참조만 | **VLM → 속성·톤 태그** (신설 어휘 강제, 어휘 밖 폐기) | **소프트 축** — 계정 속성 집계와 교집합 점수 | 추출 속성 자체가 팩트 |
| 브랜드명·설명 등 자유 텍스트 | 길이 검증만 | — | 안 씀 | 서술 프롬프트 컨텍스트 |

옵셔널 처리: 빈 필드는 criteria에서 null → SQL은 `(? IS NULL OR …)` 패턴으로 **고정
1벌 유지**(동적 SQL 생성 없음). 이미지가 없으면 ②를 스킵하고 속성 축은 가중치 0 —
폼이 확정되기 전에도 어떤 필드 조합이든 파이프라인이 동작한다.

## 5. 매칭 알고리즘 — 3단계

**1단계, 하드 필터 (SQL·파라미터 바인드).** `influencer_profiles` 단일 테이블에 WHERE만:
대분류 비율 임계, 팔로워 범위, 최소 표본(`sample_size ≥ 설정값` — 게시물 3개짜리 계정의
비율 축 과대평가 방지, 시스템이 항상 거는 필터). 탈락 사유가 이분법으로 명확한 조건만.

**2단계, 정규화 점수 — 미러가 사전 계산.** 축별 정규화는 매칭 시점이 아니라 **analytics
미러가 풀 전체 백분위(`percent_rank`)로 미리 계산해 프로필 행에 넣어둔다.**

- 매칭 SQL이 읽기만 하면 돼서 단순·빠름, 풀이 커져도 구조 불변
- 백분위는 근거 카드 표현("풀 상위 12% 참여율")과 **같은 숫자** — 점수와 근거 자동 일치
- 대안(하드 필터 통과 후보군 내 재정규화)은 후보가 5명만 남으면 점수가 캠페인마다
  출렁여 근거로 못 쓴다 — 절대 기준(풀 전체)이 안정적

**NULL 규칙**: 피드만 올리는 계정은 조회수가 항상 NULL → 조회 축 백분위도 NULL.
가중 합산에서 NULL 축은 **0점 처리가 아니라 해당 축을 빼고 가중치 재배분** — 아니면
피드 계정이 인지도 목표에서 무조건 바닥이 된다.

**3단계, 가중 합산·순위 (Java).** 목표로 프리셋 행을 로드해 `Σ(축 점수 × 가중치)` →
정렬 → 상위 K(설정값). Java인 이유: 축별 점수 분해를 저장하려면 Java가 각 축 값을
손에 쥐고 있어야 한다. 축 점수의 출처는 둘로 나뉜다 — **풀 기준 축**(조회·참여율·구매의도
등)은 미러가 사전 계산한 백분위를 그대로 쓰고, **캠페인 의존 축**(카테고리 분포 일치·제품
속성 일치)은 브리프 값이 있어야 계산되므로 Java가 프로필의 jsonb(분포·태그)와 criteria를
대조해 0~1 점수로 산출한다.

프리셋 초안 (튜닝 전제 — `app` 스키마 테이블이라 재배포 없이 조정):

| 축 | 인지도 | 전환 | 신뢰·리뷰 |
|---|---|---|---|
| 평균 조회 백분위 | **0.35** | 0.10 | 0.10 |
| 참여율 백분위 | 0.15 | **0.25** | 0.15 |
| 구매의도 댓글 비율 | 0.05 | **0.30** | 0.15 |
| 카테고리 분포 일치 | 0.20 | 0.15 | 0.15 |
| 제품 속성 일치 | 0.15 | 0.10 | 0.10 |
| 댓글 진정성·긍정 비율 | 0.05 | 0.05 | **0.20** |
| 비광고 성과 우위(C1 격차 역방향) | 0.05 | 0.05 | **0.15** |

## 6. 확정 저장 — ③의 출력이자 ④의 유일한 입력

상위 K 각각에 대해 `campaign_recommendation`에 **점수 분해(축별 백분위 × 적용 가중치)
+ 팩트 원값(비율의 분자·분모 포함) 스냅샷**을 jsonb로 저장. 프로필 미러는 계속 갱신되므로
저장 없이는 "어제 추천의 근거"가 오늘 데이터로 바뀐다. **④ 서술 LLM은 이 저장분만
프롬프트에 받는다** — 서술이 팩트를 벗어날 수 없게. 적용 가중치를 행에 복사하므로
프리셋을 나중에 튜닝해도 과거 추천의 근거는 불변.

## 7. 데이터 스키마

### 7-1. 경계 유지 장치 — 분류 계층 미러

폼 선택지·검증에 분류 계층이 필요한데 계층은 raw DB(crawler) 소속이고 **was는 raw 접근
금지**다. analytics가 `category_hierarchy`(행 수십 개)를 analysis DB로 미러 → was는
"분석 결과 읽기"로 사용. 미러 +1로 경계 원칙이 그대로 지켜진다.

### 7-2. analysis DB (analytics 소유)

| 테이블 | 내용 | 성격 |
|---|---|---|
| `influencer_profiles` | 인플루언서당 1행: followers, sample_size, 축별 원값+풀 백분위(조회·참여율·구매의도·진정성·광고비율·비광고 격차), 분류 분포(jsonb), 속성 태그 집계(jsonb) | 미러 (뷰+DDL+record+대조 가드, TRUNCATE+INSERT) |
| `content_attribute_tags` | short_code, 속성·톤 태그(jsonb, 어휘 강제), 어휘 버전, model | 신설 VLM 배치 산출물 — `content_analyses`(불변)와 달리 **재분석 허용(UPSERT)**: 어휘 개정 시 다시 돌릴 수 있어야 함 |
| `category_hierarchy` | 분류 계층 스냅샷 | 미러 (§7-1) |

### 7-3. app 스키마 (was 소유, JPA 자유)

| 테이블 | 핵심 컬럼 |
|---|---|
| `campaign` | 폼 필드(category_group/sub, follower_min/max, goal, 브랜드명·설명), 이미지 참조, `product_attrs`(jsonb — ② 산출), `status`, `fail_reason`, 타임스탬프 |
| `campaign_recommendation` | campaign FK, username, rank, total_score, `score_breakdown`(jsonb — 축별 백분위·적용 가중치), `fact_snapshot`(jsonb), `narrative`, `narrative_status` |
| `matching_weight_preset` | goal(enum), 축별 가중치(jsonb) — 튜닝용. 적용분은 추천 행에 복사 저장 |
| `candidate` | campaign_recommendation FK — "이 캠페인의 이 추천에서 저장됨" 추적 (기존 후보 관리 계획 승계) |

이미지 저장은 MVP에선 로컬 파일 + 경로 저장(포트로 추상화, 추후 S3 교체 가능).

## 8. 상태 머신 · 잡 실행

```
SUBMITTED → ANALYZING_BRIEF → MATCHING → NARRATING → DONE
                 ↓FAILED_BRIEF   ↓FAILED_MATCHING   ↓FAILED_NARRATING
```

- 잡 실행은 인프라 없이 **인프로세스 스레드풀** + DB 상태가 유일한 진실. 큐 도입은 YAGNI.
- 재시도는 실패 단계부터 (이전 산출물은 캠페인 행에 있음). **서버 재시작 시 진행 중
  상태로 남은 캠페인은 부팅 훅에서 해당 FAILED_*로 전환** — 유령 "진행 중" 방지.
- `FAILED_NARRATING`은 부분 성공: 추천·팩트는 확정 저장됐으니 먼저 노출, 서술만 재시도.
- 이미지 없는 캠페인은 ② 스킵(SUBMITTED→MATCHING 직행).

순서: **V·L·G·P1 (병렬) → P2·W1 → M → W2 → API.** M은 P2 없이도 가동 가능(속성 축
가중치 0) — 이미지 축은 나중에 켜도 파이프라인이 돈다. 구 R1·R2(페르소나 계정 LLM)는
이 재편으로 소멸 — 페르소나 축은 현 프리셋에 없어 보류.

기존 자산: A·F·B1~B3·C1·D 전부 유지(프로필 재료 + 근거 하위 화면), 랭킹 대시보드만 제거.
보류(⏸) 유지: 레퍼런스 콘텐츠 매칭, 브리프발 발굴 트리거.

**검증**:
- 프로필 뷰·미러: 기존 SQL 하니스(더미 시드+ROLLBACK) + 컬럼 대조 가드. 백분위 기대값 고정.
- 매칭: Testcontainers — 프리셋별 기대 순위 고정 + 저장된 점수 분해가 재계산과 일치.
  NULL 조회수 계정의 가중치 재배분 케이스 필수.
- VLM/서술: 포트 fake, 어휘 밖 출력 폐기 테스트.
- 잡: 단계별 실패 주입 → 상태·재시도·재시작 복구 시맨틱 검증.

## 10. 미결

- **폼 필드 확정** — 팀원 진행 중. §4-2가 superset 라우팅이므로 필드 추가/삭제는 criteria
  조립부 수정으로 흡수. 단, **오디언스 인구통계(연령·성별) 필드는 매칭 불가**(데이터 없음) —
  폼에 들어오면 저장·서술용으로만.
- 속성·톤 어휘의 실제 값 목록 — 태스크 V에서 확정 (제품 이미지·콘텐츠 양쪽에서 유효한 축으로).
- 하드 필터 임계값(대분류 비율·최소 표본)·상위 K 초기값 — 태스크 M에서 설정 키로.
- 프리셋 §5 초안 수치 — 실데이터 튜닝 전제.
