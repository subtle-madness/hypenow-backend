# 브랜드 모니터링 게시물 해시태그 필터 설계

> 상태: 🟢 활성 · 2026-08-31 설계 확정 · ✅ 구현됨(2026-08-31, feat/brand-post-hashtag-filter)

## 목적

브랜드 모니터링으로 수집된 게시물의 캡션에서 해시태그를 추출해 태그 목록(칩)으로 보여주고,
사용자가 태그를 선택하면 **이미 수집된 게시물 안에서** 그 태그가 캡션에 있는 게시물만 필터해 보여준다.
신규 수집은 스코프 밖 — 해시태그 직접 수집 파이프라인(`brand_hashtag_post`)과는 별개 기능이다.

## 핵심 결정

### 1. 추출은 정규식 — AI 판단 불채택

해시태그는 의미 판단 대상이 아니라 인스타그램이 렉시컬 규칙으로 정의하는 토큰이다.
인스타 앱이 캡션에서 링크화하는 문자열이 곧 정답이고 그 규칙은 결정적이다.
LLM을 끼우면 같은 캡션에서 실행마다 다른 태그가 나올 수 있어 "선택한 태그로 필터"라는
기능 계약(추출 = 필터 키)과 상충하며, 비용·지연만 추가된다.

### 2. 추출 시점은 조회 시 (A안)

was가 이미 `/v1/brand-monitoring` 응답 조립에서 `brand_post_meta.caption`을 전량 읽는다
(`BrandReadRepository.findPostMeta()`). 그 조립 단계에서 Java 정규식으로 추출한다.
스키마 변경·마이그레이션·백필·수집 경로 수정이 전부 0이고, 브랜드당 게시물 수백~수천 규모에서
정규식 비용은 기존 조립 비용 대비 무시 가능하다.

기각한 대안(B안): 수집 시 `brand_post_hashtags(brand_id, short_code, tag)` 사이드 테이블 저장.
SQL 레벨 필터·인덱스가 가능해지지만 마이그레이션 + 백필 + Java/SQL 정규식 이원화 부담이 붙는다.
게시물 수가 커져 전량 조립이 못 버티는 시점의 확장 경로로 남긴다 — 그 시점의 진짜 병목은
이 기능이 아니라 `/posts` 전량 조립 자체다(08-17 지연 진단).

### 3. 추출 규칙 — 인스타 링크화와의 정합 (2026-08-31 검증)

```
#[\p{L}\p{N}_]+          (ASCII # 한정, 종료는 첫 비허용 문자)
```

- 문자 집합은 기존 정본 `BrandHashtagTags.VALID_TAG`(`[\p{L}\p{N}_]+`)와 동일.
- 인스타 공개 파싱 규칙은 `(?<!&)#(\w+)` + 이모지 블록. 한글·영문·숫자·`_`·숫자-only(`#2024`)·
  캡션 중간 위치(`가나다#세일`)·연속 `##`·종료 위치 전부 일치 확인.
- **전각 `＃`(U+FF03)는 제외** — 인스타가 링크화하지 않음(검증됨). 광고 표기 판정
  (`AdDisclosurePatterns`)이 ＃를 포함하는 것은 "표기 의도 감지"가 목적이라 옳고,
  이 기능은 "실제 인스타 태그" 노출이 계약이라 ASCII `#`만 쓴다. **목적이 달라 규칙이 다르다.**
- 경계 처리는 광고 판정에서 검증된 관용구 재사용: 매치 종료 뒤 `(?![\p{L}\p{N}_])` 성질은
  greedy `+`가 자동 보장하므로 별도 lookahead 불요.

**알려진 갭(수용):**
- 이모지 해시태그 미지원 — 인스타는 2015년부터 이모지 태그를 링크화하지만(`#❤️`, `#세일❤️`)
  우리 규칙은 `#❤️`를 놓치고 `#세일❤️`를 `#세일`로 자른다. 추출과 필터가 같은 규칙을 쓰므로
  계약은 자기 일관적이고, 잘림은 사실상 병합 동작이라 무해. 필요해지면 Java 21
  `\p{IsEmoji}` 속성으로 확장 가능한 지점.
- 결합 문자(`\p{M}`)·ZWNJ가 든 태그(태국어·힌디어·페르시아어)는 마크 위치에서 잘림 — 한글은
  완성형·자모 모두 `\p{L}`이라 무영향.

### 4. 정규화

- 집계·필터 키는 `toLowerCase(Locale.ROOT)` — 인스타 태그는 대소문자 무시
  (`#OliveYoung` = `#oliveyoung`). 한글 무영향.
- 표시용 표기는 해당 키의 최빈 원문 표기를 쓴다.
- 게시물 내 중복 태그는 1회로 dedup(게시물 카운트 기준 집계).

## API 계약 (구체 필드명은 구현 계획에서 확정)

`/v1/brand-monitoring` 게시물 조립 경로에:
1. 게시물별 응답에 추출 태그 배열 필드 추가(표시용 원문 표기).
2. 브랜드 스코프 태그 facet 목록(태그 + 게시물 수, 빈도 내림차순) — 칩 렌더링용.
3. 태그 필터 파라미터(정규화 키로 비교) — 조립 단계 predicate로 적용.

기존 응답에 필드 추가만 하는 additive 변경이라 FE 무수정 하위호환.

## 구현 위치

- 추출 유틸은 was의 `BrandHashtagTags` 옆(같은 패키지)에 순수 함수로 —
  `VALID_TAG` 정본을 공유하고, monitoring 복제본과의 이원화는 현행 관행 유지.
- 필터·facet은 was 조립 서비스 레이어. DB·monitoring 모듈 무변경.

## 테스트

추출 유닛 테스트(순수 함수라 Testcontainers 불요):
한글/영문 혼합, 대소문자 병합, 숫자-only, `_` 포함, 캡션 중간 위치, 연속 `##`,
구두점 종료, 전각 ＃ 미추출, 이모지 잘림 동작 명시(`#세일❤️` → `세일`), 캡션 내 중복 dedup,
빈 캡션. facet 집계·필터는 조립 서비스 단위 테스트로.
