# 브랜드 태그 스윕 브랜드 단위 병렬화 설계

> 상태: ✅ 구현됨
> 작성: 2026-09-03 · 트랙: [MON-BT](../../tracks/MON-BT-브랜드-태그-모니터링.md)

## 1. 배경 — 실측

야간 브랜드 태그 스윕(`BrandSweepJob`, KST 02:00)이 **6시간 44분**(2026-09-03 KST, UTC 17:00:07→23:44:17,
139브랜드, 실패 0건)까지 늘었다. 8일 만에 브랜드 수 +34%에 소요는 4배 — 추세가 이어지면 04:30 미러
시작을 침범하고 업무시간까지 밀린다.

Loki 마커(`브랜드 태그 수집 —`·`태그 부재 검증 — 브랜드`·`브랜드 해시태그 수집 완료 —`)로 브랜드별
점유를 재구성한 결과(직렬 합계 404분):

| 브랜드 | 분 | 지배 단계 |
|---|---|---|
| mom.twins_official | 40.6 | 3단계 해시태그 — 신규 편입 942건 + 보강 |
| kayali | 38.1 | 1단계 열거 상한 2,016건(96페이지, 21.8분) + 2·3단계 |
| celimax.korea | 37.6 | 2단계 direct 단건 콜(열거는 2.3분) |
| celimax.global | 35.7 | 3단계 해시태그 신규 213건 |
| aestura.official | 20.5 | 혼합 |
| marynmay_official / _global | 17.9 / 14.2 | 1단계 열거 상한 2,016건 |
| 나머지 132개 | 중앙값 0.44 | |

무거움은 두 종류다. ① 열거 상한(2,000)에 닿는 브랜드의 **커서 체인 96페이지** — 커서가 직렬이라
브랜드 안에서는 병렬화가 불가능하다. ② 해시태그 감시 세트가 큰 브랜드의 **2·3단계 단건 콜 루프**.
어느 쪽이든 **브랜드 간 의존은 없다** — 3단계 모두 브랜드 단위 격리가 이미 규칙이다(스펙 08-06 §8,
08-18 direct 통합 §3-2).

자원 실측(같은 스윕 시간대, 서버 2코어/12GB): monitoring 컨테이너 CPU 평균 0.03코어·최대 0.31,
워킹셋 243→547MB(mem_limit 768m), 힙 평균 121MB·최대 204MB(Xmx 512m). **스윕은 CPU를 거의 쓰지
않는다 — 본체는 Hiker 응답 대기다.** 호스트 CPU 96% 피크(UTC 19:30~20:15)는 스윕이 아니라 analytics
미러·분석과의 겹침이다.

## 2. 목표 · 비목표

**목표**
- 스윕 본체(브랜드 루프)를 04:30 미러 전에 끝낸다 — 예상 105~140분(KST 03:45~04:20).
- Hiker 콜 수·과금은 불변(같은 콜을 같은 순서 규칙으로, 동시에 낼 뿐).
- 브랜드 단위 격리·touchSwept 규칙·3단계 순서(브랜드 안에서는 태그→direct→해시태그)는 불변.
- 롤백은 설정 한 줄(동시성 1 = 현행 직렬).

**비목표**
- 브랜드 **안** 단건 콜 병렬화(2안) — 1안 실측 후 꼬리가 한 브랜드에 묶이면 별도 설계.
- 스윕 뒤 이미지 아카이브 단계(57분, CPU 0.34~0.38코어) — 이 설계가 건드리지 않는다. 전체 잡 종료는
  아카이브 포함 KST 04:45~05:20이 된다.
- 보강 워커 풀(10) 크기 변경.

## 3. 설계

### 3-1. 브랜드 단위 병렬 실행 — `BrandSweepJob.runSweep`

- 전용 executor `brandSweepExecutor`(`BrandBackfillConfig`, 고정 N스레드, 데몬, 이름
  `brand-sweep-N`) — 설정 `monitoring.brand.sweep-concurrency`, **기본 4**. 무제한 큐(기존 executor들과
  같은 이유 — 유계 큐 + AbortPolicy는 제출 루프에서 동기 예외가 터져 격리 규칙을 깬다).
- 브랜드 1개 = 태스크 1개. 태스크 본문은 현행 3단계 try/catch 그대로(태그 스윕 성공 시에만
  `touchSwept`, direct·해시태그는 각자 격리). 태스크는 절대 예외를 밖으로 내지 않는다.
- 제출 후 `CompletableFuture.allOf(...).join()`으로 전 브랜드 완료를 기다린 뒤에야 `finally`의 광고
  판정 백필·아카이브 잡들이 돈다(현행 순서 유지 — 아카이브는 스윕이 갓 재조회한 URL을 잡는 것이
  목적이라 스윕 완료 뒤여야 한다).
- 실패 카운터 3종은 `AtomicInteger`.
- **무거운 브랜드 우선(LPT) 배정** — `findActive()`를 `findActiveHeaviestFirst(LocalDate calledOn)`로
  대체: `brand_account LEFT JOIN brand_call_count ON called_on = :calledOn`,
  `ORDER BY COALESCE(calls, 0) DESC, id`. `calledOn`은 **KST 오늘 − 1일** — 직전 스윕(전날 KST
  02:00~)의 콜이 그 날짜에 계상된다. 콜 수는 "어제 그 브랜드가 실제로 얼마나 무거웠는가"의 정본이라
  별도 추정 컬럼이 필요 없다. 전날 등록된 브랜드는 백필 콜로 앞쪽에 서는데, 무해하다(먼저 도는
  것뿐). 이력 없는 브랜드는 0으로 맨 뒤.
- 콜 집계 ThreadLocal(`BrandCallContext`)은 세 서비스가 각자 진입점에서 `scoped`를 잡으므로
  (`sweepCore`·`sweepUnenumerated`·`sweep`) 실행 스레드가 바뀌어도 집계가 새지 않는다.
- 스케줄러의 `running` 가드는 그대로 — 잡 전체가 끝나야 `sweep()`이 반환한다.

### 3-2. direct 2단계 겹침 가드를 브랜드 키로 — `BrandDirectCollectService`

현행 `unenumeratedBusy`는 **서비스 전역** `AtomicBoolean`이라 브랜드를 병렬로 돌리면 서로의 2단계를
"겹침"으로 건너뛴다(스킵된 브랜드는 그날 2단계가 통째로 빠진다 — 다음 스윕이 잡긴 하지만 매일
반복되면 영구 지연). `Set<Long> busyBrands = ConcurrentHashMap.newKeySet()`로 바꿔 **같은 브랜드**의
`sweepUnenumerated` ↔ `backfillUnenriched` 겹침만 막는다(08-28 리뷰의 원 의도 — 재기동 백필과
야간 스윕이 같은 게시물을 이중 과금하지 않게). 획득·해제 단위(브랜드 1건 처리)는 불변.

### 3-3. DB 커넥션 풀 — 변경 없음(실측으로 기각)

설계 초안은 Hikari 풀 10→20이었다(동시 DB 사용자 최악치 스윕 4 + 보강 워커 10 + 광고 판정 4 + 스케줄러
2를 세어 나온 예방적 값). 그러나 어젯밤 직렬 스윕의 HikariCP 실측(Prometheus 1분 샘플)은 **활성 커넥션
최대 1/10, 평균 0.01, 풀 대기 0**이었다 — 이미 보강 워커 10 + 광고 판정 4가 동시에 도는 상태에서도
풀은 비어 있었다. DB 점유가 밀리초 단위고 시간의 본체가 Hiker 대기라 스레드 수와 커넥션 수요는 비례하지
않는다. 따라서 풀은 기본 10을 유지한다. 배포 후 첫 야간 스윕에서 `hikaricp_connections_pending`이 0을
유지하는지 확인하고, 대기가 보이면 그 실측을 근거로 올린다. (부수 교훈: `application.yml`의 풀 값은
@SpringBootTest 컨텍스트들이 물려받아 Testcontainers Postgres 한 대의 연결 한도에 닿을 수 있다 — CI 3회
실패로 확인. 올릴 일이 생기면 운영 compose env로.)

### 3-4. 전역 Hiker 동시 콜 예산 — 문서 갱신

최악 **14 → 17**(워커 10 + 스윕 core **4** + 등록 core 2 + 해시태그 executor 1). 08-12 램프 실측(동시
20까지 429·5xx 0건)과 08-13 재실측(워커 6/8/10 꼬리 무증가) 안. 힙은 in-flight 콜당 ~10MB 공식으로
+30MB — 피크 250~300MB, Xmx 512m·mem_limit 768m 변경 없음. `BrandBackfillConfig` javadoc·
`application.yml` 주석의 예산 수치를 갱신한다.

### 3-5. 관측 — 브랜드별 소요 로그

이번 진단은 로그 마커 3종으로 소요를 역산해야 했다. 태스크가 브랜드 1건을 마칠 때
`브랜드 스윕 완료 — {username} {총 ms}ms (태그 {ms} · direct {ms} · 해시태그 {ms})`를 INFO로 남기고,
최종 로그에 총 소요 ms를 더한다. 다음 진단은 Loki에서 이 한 줄로 끝난다.

## 4. 예상 효과 · 리스크

- **소요**: 직렬 404분 → 하한 max(404/4, 최장 브랜드 41분) = 101분, 워커 풀 공유 손실을 얹어
  105~140분. 스윕이 04:30 전에 끝나 analytics 피크와 분리되므로 호스트 CPU 피크는 오히려 내려간다.
- **CPU**: 컨테이너 평균 0.1~0.15코어, 피크 0.5~0.6코어(호스트 25~30%대).
- **리스크**: Hiker 꼬리 레이턴시 증가(예산 17은 실측 안전 구간 20 이내) · 같은 브랜드의 백필과 스윕
  겹침(기존과 동일 — 멱등 upsert, 중복 콜만 낭비) · 동시성 1로 즉시 롤백 가능.

## 5. 테스트

  다른 브랜드·다른 단계에 영향 없음 + 카운터 정확(동시성 아래) ③ 전 브랜드 완료 뒤에 아카이브 잡이

## 6. 롤백

`MONITORING_BRAND_SWEEP_CONCURRENCY=1`(compose env 주입) — 코드 경로는 같고 스레드만 1개라 현행
직렬과 동일하게 돈다. Hikari 풀 상향은 롤백 불필요(무해).
