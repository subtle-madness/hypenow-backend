# 인스타 DM 자동 발송 POC — 핸드오프 노트

> 상태: 🟢 활성 · 갈림길 ①~⑧ 결정 완료(설계 착수 전) · 2026-09-02
> 목적: 세션 재시작용 컨텍스트 인계. 조사 근거 + 확정 결정 + 갈림길 결정(근거·기각한 대안·재검토 트리거 포함). 아직 구현 설계 아님 — 다음 단계가 설계/스펙.
> 갈림길 결정은 **되돌아갈 수 있는 결정**이다. 각 항목에 "재검토 트리거"를 박아, 뭘 관측하면 그 결정을 뒤집는지 명시했다.

## 무엇을 하려는가

- **인플루언서 콜드 아웃리치**(브랜드가 인플루언서에게 **먼저** 보내는 첫 DM)를 자동 발송.
- 발송 주체 = **고객사(브랜드) 계정**. 볼륨 기대 = 일 수백 건.
- 이번 작업 목표 = **POC**: "기술 가능성 + 밴 리스크 실측".

## 확정된 결정 (재론 불필요)

1. **공식 Instagram Messaging API는 이 용도에 불가** — 유저가 먼저 접촉한 24시간 창 안 응답만 허용. 콜드 아웃바운드 첫 DM은 API 경로 자체가 없음. → 자체 세션(비공식)만 기술적으로 가능. (단 콜드 첫 DM **이후**의 대화 관리는 공식 API 가능성 있음 — 병렬 트랙 참조.)
2. **아키텍처 = 서버 자동 발송으로 확정.**
   - 대안이던 **크롬 확장**(유저 IP·세션 사용, 완전자동 가능하나 설치 부담) → 기각(불편).
   - 대안이던 **딥링크 반자동**(웹만으로, 유저가 인스타 탭 가서 붙여넣고 전송, 밴 리스크 거의 0) → 기각. 이유: 전송이 인스타 표면에서 일어나야 해서 **유저 브라우저가 인스타로 넘어가는 왕복**이 불가피 + 볼륨(수백건)과 충돌.
   - 서버 자동의 대가: 밴 리스크 최고 + 레지던셜 프록시·세션·지문 난관이 전부 살아있음.
3. **책임 조항**: 고객사 계정 밴 책임은 계정 소유자(고객)에게 명시 예정(피처링 방식). 단 법적 책임과 별개로 **평판 리스크는 우리한테 남음** — 페이싱 보수성 결정 시 재고려.
4. **POC 하네스 = 독립 Python 스크립트**(instagrapi 등), 버릴 계정, 완전자동만 실측. 백엔드와 분리해 리스크 격리. (생산 전환은 실측 후 별도.)

## 우리 코드베이스 재사용 가능 요소 (crawler 모듈)

- **배관 재사용 높음**: `JdkInstagramWebClient`(GraphQL POST, 프록시 로테이션, 쿠키, HTTP/2 고정, User-Agent·Sec-Fetch 헤더 위장) — `crawler/.../adapter/out/instagram/`. 단 **IG 앱 에뮬레이션·로그인·세션·DM 로직은 없음**(전부 익명 크롤 전용) — 어려운 부분은 instagrapi가 대신.
- **프록시 이미 보유**: [`ProxyProperties`](../../../crawler/src/main/java/com/celfit/crawler/crawling/adapter/out/instagram/ProxyProperties.java)에 **DataImpulse 레지던셜 + DataImpulse 모바일** 프록시가 이미 설정됨(+Apify). 벤더 재사용 가능 — 단 크롤은 rotating 게이트웨이로 씀(④ 참조, DM은 sticky+geo로 새 세션 구성 + 크롤 트래픽과 IP 분리 필수).
- **없음(신규 필요)**: 인스타 로그인/세션, DM 엔드포인트 스키마.
- Hiker/Apify/DataLikers는 전부 조회 전용, DM 발송 기능 없음.

## 갈림길 결정 ①~⑧ (2026-09-02 확정 · 재검토 가능)

각 항목: **결정 / 근거 / 기각·대안 / 재검토 트리거**. 발송 파이프라인 순서.

### ① 계정 조달·워밍업
- **결정**: 신규 버릴 계정. **2단계 실험** — 1단계=신규 즉시 발송(즉시 정지당하는지=바닥 확인), 2단계=워밍업 후 발송(개선 측정). 워밍업 활동엔 프로필 완성(사진·bio·게시물 2~3개) 기본 포함.
- **근거**: 운영 발송 주체는 고객 본인 계정이라 계정 나이는 우리가 고르는 변수가 아니라 고객이 들고 오는 상수. POC는 고객 계정을 못 태우므로 버릴 계정. 워밍업 수치가 외부에 (피처링 30일+ 외엔) 얇아, 즉시발송 즉사 여부를 우리 데이터로 재는 게 공백을 메움.
- **기각·대안**: 구매 계정(B1)=출처 오염(이미 밴이력·재활용 지문)으로 측정 불능 + ToS 심화. 자체 숙성(B2)=고객 계정 대역으론 정확하나 수 주 비용, 지금은 불채택(2단계 워밍업이 그 역할 일부).
- **재검토 트리거**: 신규 즉시가 **로그인/발송 이전에 즉사**해 콜드DM 거동을 아예 못 재면 → 숙성 계정(B2) 대역 도입 검토. 운영이 "브랜드 본계정 전용"으로 확정되면 → POC 계정 조건을 숙성 대역으로 재설계.

### ② 세션 확보
- **결정**: **하이브리드 C** — 실행 환경(프록시·기기 프로필)에서 계정당 **1회만** 패스워드 로그인 → `dump_settings`로 세션 저장 → 이후 재사용, 만료 시에만 재로그인.
- **근거**: 로그인이 최고위험 이벤트라 횟수를 계정당 1회로 최소화. 그 1회가 실행 환경과 동일 맥락에서 태어나 IP·기기 불일치 없음. instagrapi 문서 권장 정석과 정합. POC 측정도 로그인 변수를 1회로 고정.
- **기각·대안**: A(브라우저 쿠키 임포트)=웹 세션≠모바일 앱 API 표면 불일치 + 로그인 환경(내 폰·집IP)과 실행 환경(프록시·서버) 불일치가 오히려 플래그. B(매번 로그인)=최고위험 반복 + 측정 오염.
- **재검토 트리거**: 세션 만료가 너무 잦아 재로그인이 반복되면 → 세션 수명 연장책(TTL·리프레시)·플랫폼 검토. 운영 스케일에서 계정당 수동 1회 로그인이 병목이면 → 로그인 자동화·복구 플로우 별도 설계.

### ③ 발송 실행
- **결정**: **private API 경로**(헤드리스/브라우저 아님). POC=**바닐라 instagrapi**로 빨리 측정 → 필요시 **instagrapi 포크해서 표면(기기·헤더·타이밍·시그니처)만 커스터마이즈** → 그걸로도 안 되면 완전 자체 클라이언트. (완전 자체는 로그인·서명·DM 코어 재구현이라 어려움 — 최후.)
- **근거**: 밴 실무 근거 베이스가 전부 private API/instagrapi 세계. 세션 재사용(②)·지문 고정(⑤)이 private API 전제. 우리 `JdkInstagramWebClient`도 직접 HTTP 계열. X-MID 천장은 웹에도 mid 쿠키로 동일 존재 → private API 고유 약점 아님. 모바일 앱 API가 웹보다 클라이언트측 안티봇 약하고 콜드DM 실무 생태계가 여기 몰림.
- **기각·대안**: 헤드리스 브라우저=웹 감시 두꺼움 + 헤드리스 팻말(webdriver·canvas) = 제일 잘 걸림. headful 스텔스=사람 표면에 근접하나 무거워 스케일 불가 + 자동화 잔흔. 진짜 기기 팜=천장이나 인프라 과중(POC 밖).
- **재검토 트리거**: **⑤의 무발송 대조군이 "라이브러리 시그니처 死"를 가리키면 → 요청레이어 커스터마이즈(포크) 조기 착수**. 바닐라가 비정상적으로 빨리 타면 시그니처 의심 → 포크. 운영에서 headful/기기팜을 재고할 사유가 생기면 POC 밖에서 별도.

### ④ 프록시
- **결정**: **레지던셜 Korea sticky, 1계정:1출구(미중첩)**. POC는 레지던셜로 시작, 잘 타면 **모바일로 승급**(DataImpulse 둘 다 보유, env 전환). 벤더 재사용하되 **크롤 트래픽과 출구 IP 분리**(별도 세션/크리덴셜) + **geo=Korea 묶음**.
- **근거**: 데이터센터=ASN으로 결정적 판별(즉사). IP "변화" 자체는 신호 아님(진짜 사용자도 바뀜) — 신호는 데이터센터 출신·물리적 불가능 이동(텔레포트)·계정농장 뭉침. sticky 1:1은 IP-429/연좌를 만드는 게 아니라 **막는** 구성(한 IP에 계정 하나치 트래픽만). geo 묶음이면 sticky TTL 이탈로 IP 바뀌어도 지역 일관 유지. 모바일은 캐리어 NAT라 통째 밴 불가 + ③ 모바일 표면과 정합.
- **기각·대안**: 데이터센터/서버 IP=탈락. 크롤 프록시 URL 그대로 재사용=rotating이라 텔레포트 + 크롤·DM 트래픽 혼재로 오염·연좌.
- **재검토 트리거**: 레지던셜에서 잘 타거나 IP 공유 노이즈가 크면 → 모바일 승급. sticky TTL 이탈이 잦아 지역 튀면 → 전용 IP·더 긴 sticky 플랜. IP 놀 때 뜨는 429가 관측되면(공유 탓) → 프록시 품질/전용성 재검토.

### ⑤ 디바이스 지문
- **결정**: 위장 아님, **계정당 일관된 한국 기기 프로필 1개를 생성·영구 고정 재사용**(공유·변경 금지, 앱버전 최신 유지). **L2 실기기 프로필 조기 도입**(instagrapi 바닐라 L1 대신, 한국 흔한 갤럭시 모델 공개 스펙+현행 IG 앱버전+ko_KR/Seoul 조립). **무발송 대조군 계정 함께 운용**(시그니처 死 vs 콜드DM 死 설계로 분리).
- **근거**: 불일치 자체가 신호라 안정성>영리함. 지문은 캡처가 아니라 합성(클라측 생성 + 서버발급 mid/token은 로그인 때 획득, ②와 같은 `dump_settings` 파일). 지문엔 계정 같은 "나이" 불필요(신규계정+신규기기는 자연스러움). L1 바닐라는 내장 기기목록·요청패턴이 알려져 "라이브러리 지문 死"로 1단계 측정을 오염시킬 수 있어 L2 조기.
- **기각·대안**: 기기 위장·다변화=불일치 리스크. L1 바닐라 시작 후 지연 승급=confound 위험(즉사가 시그니처 死일 수 있음).
- **재검토 트리거**: 대조군이 살고 DM계정만 죽으면 → 콜드DM 귀속 확정(지문 무죄). 대조군도 죽으면 → 시그니처/환경 문제 → **③ 요청레이어 커스터마이즈 착수 + L2 프로필 정밀화**. ※ L2는 기기 서술자 절반만 제거 — 요청패턴(헤더순서·시퀀스) 절반은 ③ 포크 몫.

### ⑥ 페이싱
- **결정**: **두 층.** (층1·제약, 전 단계 공통) Δt 지터·비주기성 + Korea 주간 시간대 한정 + 비DM 액션 섞기 — **1단계에도 적용**(리듬 제거는 운영이 안 할 조건이라 전이 안 됨). (층2·실험) 1단계는 rate를 **피처링 Max 21/hr 근처로 고정**, 산출 = **死까지 총 발송수·생존시간**. **rate 코호트 실험(3/8/21/+)은 워밍업 유효 확인 후 2차 변수**로.
- **근거**: Δt가 탐지 피처(근거표 A-)라 리듬은 필수. 피처링 3/8/21이 공짜 테스트 포인트. 단 21은 피처링 30일 숙성 기준이라 신규계정엔 훨씬 공격적 = 수치 그대로 전이 안 됨. 1단계 worst-case는 계정 조건(신규·무워밍업)이지 리듬 제거가 아님. 워밍업(①)을 이미 단계 축으로 잡아, pacing까지 동시 다변수化하면 계정 수 폭증 → pacing은 2차.
- **기각·대안**: 리듬 없는 생짜 블라스트=전이 안 되는 숫자. pacing을 1차 변수로=①워밍업과 곱해져 계정 폭증.
- **재검토 트리거**: 1단계에서 21/hr이 즉사시키면 → 앵커를 8/3으로 낮춰 재측정. 워밍업이 생존을 유의하게 늘리면 → pacing rate 코호트 실험(2차) 개시. 21 위 절벽을 명시적으로 찾고 싶으면 → 상향 코호트 추가.

### ⑦ 밴 감지·정지
- **결정**: 신호를 **3단계 분류** — 일시(429/PleaseWait=백오프, 死 아님)·액션차단(FeedbackRequired=계정 쓰기 중단)·종료(ChallengeRequired/비활성/LoginRequired 반복=死). 정지는 **계정 즉시 + 함대 서킷브레이커**(짧은 창에 N개 동시 신호=계통 문제=전체 정지). **자동 재시도 금지**(밴 가속). POC는 **첫 하드 신호(차단/종료)를 死로 확정·정지**(복구 시도 안 함 — 생존 측정 깨끗하게). **수신측 도착 확인**으로 사일런트 섀도우드롭까지 포착(수신자가 우리 더미라 가능).
- **근거**: 429를 死로 세면 생존곡선 오염 → 등급 분류 필수. 계통 문제(프록시·시그니처)가 계정을 줄줄이 태우는 걸 서킷브레이커로 차단. FeedbackRequired 재시도는 번을 가속(③ 고려사항).
- **기각·대안**: 모든 신호를 死로 뭉치기=오염. 복구 시도(챌린지 코드 풀기)=측정 흐림+품(운영 관심사, POC 밖).
- **재검토 트리거**: 운영 전환 시 → 계정 복구 플로우 별도 설계(POC는 死로 확정했던 것). 사일런트 드롭이 지배적이면 → 도착확인을 1급 지표로 승격.

### ⑧ 실측 기록 (POC 산출물)
- **결정**: 독립 하네스 안 **로컬 SQLite**. **발송 이벤트 로그**(발송마다 1행: ts·계정·수신자·결과·신호등급·도착확인·Δt) + **계정 메타 테이블**(조건 라벨: 신규/숙성일수·워밍업유무·대조군여부·L1L2·rate앵커·프록시유형geo·instagrapi버전·IG앱버전) + **死 이벤트**(신호종류·시각·누적발송수·생존시간·몇건째·응답본문). 파생 = 조건별 생존곡선·死사유 분포·대조군 대비·도달률. **응답률(효과)은 스코프 밖**(수신자 더미)으로 "측정 안 함" 명시.
- **근거**: 死만 기록하면 생존곡선·Δt·몇건째死가 사후 재구성 불가 → 모든 발송 이벤트 append 필수. SQLite=백엔드 오염 없이 조건별 집계 편함. 원장 스키마가 곧 POC가 답하는 것의 형태.
- **기각·대안**: 死만 스냅샷=곡선 소실. 백엔드 DB 사용=리스크 격리(확정#4) 위반.
- **재검토 트리거**: 계정 수가 많아지면 → 저장소 승급(postgres). 도착확인·응답 관심이 커지면 → 스키마 확장.

## 재검토 트리거 요약 (되돌아갈 조건 한눈에)

- **바닐라 instagrapi가 비정상적으로 빨리 탐 / 무발송 대조군도 죽음** → ③ 요청레이어 포크·커스터마이즈 조기 착수 + ⑤ L2 정밀화.
- **신규 즉시가 발송 이전에 즉사** → ① 숙성 계정(B2) 대역 도입.
- **워밍업이 생존을 유의하게 늘림** → ⑥ rate 코호트 실험(2차 변수) 개시.
- **1단계 21/hr 즉사** → ⑥ 앵커 8/3으로 하향 재측정.
- **레지던셜에서 잘 탐 / IP 공유 노이즈 큼** → ④ 모바일 승급.
- **운영이 "브랜드 본계정 전용"으로 확정** → ① POC 계정 조건을 숙성 대역으로 재설계.
