# 캠페인 추천 피봇 — 구조 설계

> 상태: 🟢 활성
>
> 2026-07-13. 제품 방향 피봇: "콘텐츠 랭킹 + 상세 분석 탐색" → **"캠페인 브리프 → 인플루언서 추천 + 근거"**.
> 이 문서는 피봇의 요구사항 확정 내용과 시스템 구조 결정을 기록한다. 현재 유효한 그림은
> 항상 [ARCHITECTURE.md](../../../ARCHITECTURE.md)가 기준이다.

## 1. 피봇 요약

**바뀐 제품 한 줄**: 마케터가 **캠페인 브리프**(구조화된 폼 + 제품 이미지)를 제출하면,
크롤링된 인플루언서 풀에서 **추천 리스트 + 근거**(정량 팩트 카드 + LLM 서술)를 돌려준다.

기존 MVP(콘텐츠 랭킹 페이지 중심)와의 관계:
- **추천이 메인 화면**이 된다. 콘텐츠 랭킹 페이지는 제거(축소).
- 인플루언서 상세·게시물 드로어는 **추천 근거를 파고드는 하위 화면**으로 흡수 — 기존
  B1~B3 데이터 층 산출물이 그대로 재료가 된다.
- 후보 관리(저장·상태·메모)는 추천 결과와 연결되어 유지.

## 2. 확정된 요구사항

| 항목 | 결정 |
|---|---|
| 브리프 입력 | **구조화된 폼** (제품 카테고리, 팔로워 규모, 캠페인 목표 등 — 필드 상세는 구현 계획에서) + **제품 이미지** |
| 제품 이미지 용도 | VLM으로 **제품 속성 추출** → 인플루언서 콘텐츠 속성과 매칭 |
| 레퍼런스 콘텐츠 이미지 | "원하는 느낌" 매칭 용도 — **계획에만 포함, 구현 보류(⏸)** |
| 처리 방식 | **비동기 잡 + 단계별 진행 상태 표시** (이미지 분석 → 후보 매칭 → 근거 서술) |
| 근거 형태 | **정량 팩트 카드 + LLM 서술 결합** — 서술은 저장된 팩트만 입력으로 받는다 |
| 추천 풀 | **기존 크롤링 풀 내에서만** (1차). 브리프발 발굴(크롤링) 트리거는 보류(⏸) |
| 캠페인 수명 | **영구 저장** + 추천 결과에서 후보 저장(검토중→컨택→협업) 연결 |

## 3. 구조 결정 — A안: "프로필 팩토리 + was 캠페인 오케스트레이션"

### 검토한 대안

- **A안 (채택)** — analytics는 배치로 "매칭 가능한 인플루언서 프로필"을 생산(프로필 팩토리),
  캠페인 파이프라인(이미지 분석→매칭→서술)은 was가 소유.
- **B안 (기각)** — was는 브리프 저장만 하고 analytics가 DB 큐를 폴링해 전 파이프라인 실행.
  "LLM은 분석 층" 문구는 지키지만: analytics가 상시 서비스로 변질, 서비스 데이터(브리프)를
  분석 층이 읽는 새 화살표 발생, 캠페인 결과의 소유권 모호. 원칙의 정신(분석 결과 재현
  가능성 / 서비스 상태는 was)을 오히려 깬다.

### 채택 구조

```
[크롤링]  crawler   ──쓰기──▶ raw DB                              (변화 없음)
[분석]    analytics ──읽기── raw ──쓰기──▶ 분석 결과(analysis DB)
                    = 프로필 팩토리: 매칭용 인플루언서 프로필 + 근거 화면 재료를 배치 미러
[서빙]    was       ──읽기── 분석 결과(파라미터 쿼리로 매칭)
                    ──읽기/쓰기──▶ 서비스 데이터(app 스키마: 캠페인·추천·후보)
                    + 캠페인 비동기 잡: 브리프 이미지 VLM → 매칭·스코어링 → 근거 서술 LLM
```

### 원칙 수정 (ARCHITECTURE §5-2 개정)

기존 "LLM 분석은 분석 층 소속"을 **대상 기준으로 이원화**한다:

- **raw 콘텐츠(인플루언서)에 대한 LLM** → 분석 층. 재현 가능한 분석 결과로 미러.
- **캠페인 입력(마케터 제출물)에 대한 LLM** → was. 서비스 트랜잭션의 일부로 `app` 스키마에 저장.

근거: 캠페인은 상태 변화·트랜잭션을 가진 서비스 데이터이고(§5-2 표의 원래 분류),
브리프 이미지는 raw DB와 무관한 사용자 입력이다.

### LLM 호출 골격 공유 (§5-4 예외 +1)

F에서 만든 LLM 호출 골격(인증·재시도·포트)을 analytics·was가 같이 쓴다.
공유 모듈 `llm-core`로 분리 — 계약 모듈처럼 얇게, 비즈니스 로직 금지.
모듈 공유 원칙의 두 번째 예외로 등재한다.

## 4. 추천의 3층 구조 (피봇의 심장)

### ① 매칭용 인플루언서 프로필 — analytics 생산, analysis DB 미러

추천 알고리즘이 읽는 단일 재료 테이블(`influencer_profiles`, 인플루언서당 1행).
매칭 축을 컬럼으로 평탄화 — 조회 시점에 raw를 뒤지지 않고, 배치가 미리 계산한
프로필에 파라미터 쿼리만 날린다. 기존 미러 원칙(뷰 SQL + Flyway DDL + 공유 record +
컬럼 대조 가드) 그대로 적용.

| 축 | 내용 | 출처 |
|---|---|---|
| 정체성 | 주력 카테고리 분포(jsonb), 콘텐츠 속성 태그 집계 | 기존 분류 + B3 콘텐츠 속성 |
| 규모·성과 | 팔로워, 최근 N개 평균 조회·참여율, 히트율, 벤치마크 대비 | A·B1 (최근 N개 윈도우) |
| 상업성 | 광고 게시물 비율, 광고 vs 비광고 성과 격차 | C1 산출물·계획 재활용 |
| 오디언스 반응 | 감성 비율, 구매의도 댓글 비율 | B2 |
| 페르소나 | 페르소나 라벨, 광고 유형 | 계정 LLM (구 C2 재정의 = R2) |

C1은 이미 구현됨(근거 화면 재료로 유지) — R1은 그 재료를 매칭용으로 평탄화하는 신설 태스크이고, C2는 R2로 재정의된다.

### ② 어휘 계약 — 매칭이 성립하려면 양쪽이 같은 언어를 써야 한다

브리프 쪽 VLM(제품 이미지→속성, was)과 분석 쪽 LLM(콘텐츠→속성, analytics)이
서로 다른 단어를 뱉으면 매칭 불가. **매칭 어휘(카테고리·속성·톤 enum)를
`contract-analysis`에 확정**하고 양쪽 프롬프트가 이 어휘만 출력하도록 강제한다
(어휘 밖 출력 방어 — B3에서 검증한 패턴). "분류값·라벨은 생산자가 확정" 원칙(§5-4)의
확장: 어휘의 생산자는 계약 모듈, 양쪽 LLM은 소비자.

### ③ 매칭 알고리즘 — was 소유, 3단계

1. **하드 필터** (파라미터화 SQL): 브리프 폼 값이 WHERE 조건으로 — 카테고리 일치,
   팔로워 범위, 최소 표본 크기. 탈락 사유가 명확한 조건만.
2. **소프트 스코어링**: 축별 정규화 점수 × **캠페인 목표별 가중치 프리셋**
   (인지도→도달·조회 가중, 전환→구매의도·참여 가중). 가중치는 `app` 스키마 설정
   테이블 — 재배포 없이 튜닝(기존 `app_setting` 철학의 was판).
   역할 분담: **필터·정규화는 SQL, 가중 합산·순위는 Java** — 점수 분해를 저장하려면
   Java가 축별 값을 손에 쥐어야 한다.
3. **근거 확정 저장**: 추천 시점의 축별 점수 분해 + 근거 팩트 원값을 추천 행에 함께
   저장. 프로필은 미러가 계속 갱신하므로, 저장하지 않으면 "어제 추천의 근거"가 오늘
   데이터로 바뀐다(B1 스냅샷 철학의 추천판). **LLM 서술은 이 저장된 팩트만 입력으로
   받아 생성** — 서술이 팩트를 벗어날 수 없게.

분석 결과(프로필)와 서비스 데이터(캠페인)는 SQL 조인하지 않는다 — 매칭 쿼리는 분석
결과 테이블만 읽고 브리프 값은 바인드 파라미터로, 조합은 was 코드에서 (§5-4 유지).

## 5. 캠페인 파이프라인 (was) — 엔드투엔드

was의 정체성이 바뀐다: 분석 결과를 그대로 내려보내는 서빙 층이 아니라,
**입력(브리프)을 받아 분석 DB의 재료에 알고리즘을 태워 결과를 만들어내는 오케스트레이터**다.
이 플로우가 제품의 중심 경로이며, 설계도 이 플로우를 축으로 읽는다.

### 상태 머신

캠페인 1건 = 잡 1건. 상태는 단계와 1:1 대응, 실패는 어느 단계에서 멈췄는지 그대로 남긴다.

```
SUBMITTED ─▶ ANALYZING_BRIEF ─▶ MATCHING ─▶ NARRATING ─▶ DONE
                 │                 │            │
                 ▼                 ▼            ▼
          FAILED_BRIEF      FAILED_MATCHING  FAILED_NARRATING
```

- 재시도는 실패한 단계부터 (이전 단계 산출물은 캠페인 행에 저장돼 있음).
- NARRATING 실패는 부분 성공으로 취급 가능 — 추천 리스트·팩트 카드는 이미 확정 저장돼
  있으므로 프론트에 먼저 노출하고 서술만 재시도할 수 있다.

### 단계별 상세

| 단계 | 하는 일 | 읽기 | 쓰기 |
|---|---|---|---|
| ① 제출 | 폼 검증, 캠페인 저장, 잡 시작 | — | `app.campaign` (SUBMITTED) |
| ② 브리프 분석 | 제품 이미지 VLM → 제품 속성(매칭 어휘로 강제) | 캠페인 이미지 | `app.campaign.product_attrs` |
| ③ 매칭 | 하드 필터 + 축별 정규화(SQL, 파라미터 쿼리) → 가중 합산·순위(Java) → 상위 K 확정 | 분석 결과 `influencer_profiles` + 가중치 프리셋 | `app.campaign_recommendation` (점수 분해 + 팩트 원값 스냅샷) |
| ④ 근거 서술 | 저장된 팩트만 입력으로 LLM 서술 생성 | `app.campaign_recommendation` | 같은 행의 narrative |
| 서빙 | 진행 상태·결과 조회 (프론트 폴링) | `app.*` | — |

핵심 규율: ③에서 분석 결과는 **읽기만**(브리프 값은 바인드 파라미터, 서비스 데이터와 SQL
조인 금지), ④는 **저장된 팩트 밖의 입력을 받지 않는다**(서술이 팩트를 벗어날 수 없게).

### 캠페인 도메인 데이터 스케치 (`app` 스키마, was 소유 — 상세 DDL은 G 계획에서)

| 테이블 | 내용 |
|---|---|
| `campaign` | 브리프 폼 필드, 제품 이미지 참조, VLM 추출 제품 속성(jsonb), 상태, 실패 사유, 타임스탬프 |
| `campaign_recommendation` | campaign FK, username, 순위, 종합 점수, **축별 점수 분해(jsonb)**, **근거 팩트 원값 스냅샷(jsonb)**, LLM 서술, 서술 상태 |
| `matching_weight_preset` | 캠페인 목표별 축 가중치 (재배포 없이 튜닝) |
| 후보 연결 | 기존 후보 관리가 `campaign_recommendation`을 참조 — "이 캠페인의 이 추천에서 저장됨" |

추천 시점의 프로필 값을 `campaign_recommendation`에 스냅샷으로 넣는 이유: 프로필 미러는
계속 갱신되므로, 스냅샷 없이는 "어제 추천의 근거"가 오늘 데이터로 바뀐다. 인플루언서
상세로 파고들 때(근거 하위 화면)는 최신 프로필을 보여주되, 추천 카드의 근거는 확정본이다.

## 6. 기존 자산 처분

| 자산 | 처분 |
|---|---|
| A·F·B1·B2·B3 산출물 (base 뷰, LLM 골격, 서빙 미러 4종, 댓글·콘텐츠 LLM) | **유지** — 프로필 재료 + 근거 하위 화면 재료 |
| C1 (구현 완료 — PR 대기) | **유지** — account_* 미러 3종은 근거 하위 화면(인플루언서 상세) 재료. 상업성·광고 비교 집계는 R1 프로필 재료로 재사용 |
| C2 (미착수) | **재정의** — 프로필 LLM 축 생산 (R2) |
| D (구현 완료 — PR 대기) · E (미착수) | **유지·재배치** — 근거 하위 화면(드로어·인플루언서 상세) API |
| G (서비스 데이터, 미착수) | **확장** — 캠페인 도메인(브리프·추천·후보)이 `app` 스키마의 중심 |
| was 콘텐츠 랭킹 대시보드 | **제거** — 피봇 화면 구성에서 탈락. 코드·의존 미러 테이블 정리 |
| 옛 MVP 기획(드로어 v3·인플루언서 v4 "메인 화면" 구도) | 근거 하위 화면으로 강등 — 문서 상태 헤더로 표시 |

## 7. 작업 트랙 재편

ARCHITECTURE §6의 표를 아래로 교체한다. 완료 태스크(A·F·B1~B3)는 유효하므로 그대로 둔다.

| # | 태스크 | 내용 | 의존 | 상태 |
|---|---|---|---|---|
| V | 어휘 계약 | 매칭 어휘(카테고리·속성·톤) enum을 `contract-analysis`에 확정 | — | ⬜ |
| L | LLM 공유 모듈 | F 산출물(호출 골격)을 `llm-core`로 분리, analytics·was 공용 | — | ⬜ |
| R1 | 프로필 비LLM 축 | `influencer_profiles` 뷰·미러 (정체성·규모·성과·상업성·오디언스 반응) | V | ⬜ |
| R2 | 프로필 LLM 축 | 페르소나·광고 유형 (계정 LLM) | V, L, R1 | ⬜ |

## 8. 검증

- 프로필 뷰·미러: 기존 SQL 하니스(더미 시드 + BEGIN/ROLLBACK) + 컬럼 대조 가드 그대로.
- 매칭 엔진: 가중치 프리셋별 기대 순위를 고정하는 Java 테스트(Testcontainers) — 점수
  분해가 저장값과 일치하는지 포함.
- VLM/LLM: 실 API 없이 포트 fake(기존 컨벤션). 어휘 밖 출력 방어 테스트 필수.
- 비동기 잡: 단계 실패 시 캠페인 상태가 명확히 남는지(부분 실패 시맨틱) 테스트.
