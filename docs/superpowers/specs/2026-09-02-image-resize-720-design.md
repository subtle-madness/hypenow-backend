# 서빙 이미지 리사이즈 — 720px·q70 (신규분 잡 삽입 + 기존분 백필)

> 상태: 🟢 활성

## 1. 배경·목적

GCS `hypenow-images`(asia-northeast3)가 50GB를 넘어 버킷 알람이 울렸다(09-02).
증가의 본체는 게시물 썸네일 2종 — `thumb/` 32.9GB + `monitor-brand-post/` 15.8GB = 48.8GB(전체의 97%).
수명주기 삭제는 배제(전량 보존 요구). 대신 **저장 해상도를 서빙 요구에 맞춰 축소**해
용량과 증가 속도를 함께 꺾는다.

FE 실측 근거(celfit-front):

- 이미지가 가장 크게 렌더되는 지점은 랭킹 콘텐츠 상세 패널 **488 CSS px**(`ContentDetailPanel`,
  aspect 4/5 · object-cover). 그 외 카드·리스트는 400px 이하, 아바타류는 28~72px.
- 해당 화면은 **next/image 최적화 없이 플레인 `<img>`** — 저장 바이트가 브라우저에 1:1로
  내려간다. 리사이즈는 스토리지 절감이자 곧 페이지 로드 개선이다(현재 6MB 썸네일이
  그대로 서빙되는 사례 실재).
- 720px·q70 축소본을 상세 패널 실마크업 복제 A/B로 사용자 검수 완료(09-02) — 화질 승인.

바이트 가중 실측(크기 구간별 샘플 48장, sips 인코더):

| 정책 | 48.8GB → | 절감 |
|---|---|---|
| **720px·q70 (채택)** | ~25.1GB | −23.7GB (49%) |
| 976px·q70 (차등안, 기각) | ~32.4GB | −16.4GB (34%) |

신규 증가도 같은 비율로 꺾인다(하루 ~3GB → ~1.5GB). 100GB 알람 도달이 2주 → 한 달 이상으로 밀린다.

## 2. 리사이즈 정책 (전 지점 공통)

- **최장변 720px 초과분만** 축소(비율 유지, 720px로). 이하는 **원본 바이트 그대로**(재인코딩 금지 —
  IG CDN 원본이 이미 고압축이라 동일 해상도 재인코딩은 실측 +30% 역효과).
- 출력은 **JPEG 품질 0.70**.
- **결과가 원본보다 크면 원본 유지**(스킵). 축소 자체가 실패해도(webp 미지원·디코드 불가 등)
  **원본 그대로 저장** — 리사이즈는 최적화이지 아카이브 성패 조건이 아니다.
- 프로필(150~320px)·아바타류는 정책상 자연 통과라 코드 분기 불필요.
- EXIF 회전은 무시한다(IG CDN 이미지는 회전이 픽셀에 반영된 상태로 온다).

## 3. 신규분 — 아카이브 잡에 리사이즈 삽입

적용 지점: **`ImageDownloader`를 감싸는 데코레이터** — `fetch` 결과 바이트를 리사이즈해서
반환한다. 잡 코드는 무수정이고, 배선 한 줄로 그 모듈의 모든 이미지 잡에 일괄 적용된다.

- **analytics**: `analytics/archive`에 `ImageResizer` 신설, `JobConfig`의 다운로더 배선에서 래핑
  (`ImageArchiveJob`의 thumb/·profile/ 커버).
- **monitoring**: `monitoring/image`에 동일 `ImageResizer` **복제**, `ImageArchiveConfig`의
  다운로더 배선에서 래핑(monitor-* 이미지 잡 7종 전부 커버).
  모듈 간 공유는 계약 모듈(분석 결과 record 전용)만 허용이므로 `ImageDownloader` 전례대로
  ~수십 줄 복제가 경계 원칙에 맞다(ARCHITECTURE §4).

구현(순수 JDK, 의존성 추가 없음):

- `ImageIO.read` → 디코드 실패(webp 등)면 원본 반환. 성공 시 최장변 ≤720이면 원본 반환.
- 축소는 `Graphics2D` + bilinear, `TYPE_INT_RGB` 캔버스(알파 소거).
- 인코드는 `ImageWriteParam` 품질 0.70. 결과가 원본보다 크면 원본 반환.
- 리사이즈된 경우 contentType은 `image/jpeg`로 통일(원본 유지 시 기존 contentType 그대로).
- 전 과정 예외는 원본 반환으로 흡수하고 WARN 로그 1줄.

인코더 주의: 실측(49%)은 sips 기준이다. ImageIO q0.70의 압축 효율은 다소 다를 수 있어
절감률 ±5%p 오차를 전제한다. 방향·규모는 동일.

부하: 잡 페이스가 초당 ~1장, 720px 재인코딩은 장당 수십 ms — 2코어 운영 서버에 유의미한
부하 없음.

## 4. 기존분 백필 — 로컬 맥 일회성 스크립트

- **위치**: 로컬 맥(gcloud 인증·sips 보유). GCS 이그레스 ~48.8GB ≈ $6(무료 크레딧 차감).
  운영 서버(2코어, I/O 알람 전력 2회) 배제. GCP VM은 셋업 대비 이득 없어 기각.
- **대상**: `thumb/`, `monitor-brand-post/` (48.8GB — 효과의 97%). 나머지 monitor-* 2.5GB는
  잡 코드 배포 후 자연 희석되므로 백필 제외(원하면 같은 스크립트로 추후 실행 가능).
- **동작**: 객체 목록 1회 확보 → 워커 N개 병렬로 (다운로드 → sips 치수 검사 → 720 초과면
  `sips -Z 720 -s formatOptions 70` → **작아진 경우에만** 같은 키로 덮어쓰기).
- **메타데이터 보존**: 덮어쓸 때 기존 객체의 `Cache-Control`을 복사한다(공개 서빙 캐시가
  이 헤더에 의존 — deploy/README §5-2). contentType은 `image/jpeg`.
- **멱등**: "≤720px면 건드리지 않음 + 커지면 덮어쓰지 않음"이 자연 멱등 — 중단 후 재실행하면
  처리된 객체는 치수 검사에서 자동 스킵된다. 별도 상태 저장 불필요.
- **순서**: 잡 코드(§3) 머지·운영 배포 **후** 실행 — 배포 전 실행하면 새 대형 이미지가 계속
  유입돼 잔여분이 남는다(멱등이라 재실행으로 흡수 가능하지만 불필요한 왕복).
- 실행 시 `caffeinate`로 잠자기 방지. 드라이런 모드(덮어쓰기 생략, 예상 절감만 집계) 포함.
- 소요 예상: 다운 48.8GB + 업 ~25GB + 변환 33만 장 병렬 — 2~4시간.

백필 중 새벽 잡과의 경합: 잡은 새 키만 추가하고 백필은 시작 시점 목록만 처리 — 겹치지 않는다.
설령 같은 키를 양쪽이 쓰더라도 마지막 쓰기가 남을 뿐 서빙 무결성엔 영향 없다.

## 5. 테스트

- `ImageResizer` 단위 테스트(analytics·monitoring 각각): 1440px 입력 → 720px·더 작은 바이트 /
  640px 입력 → 원본 바이트 동일 반환 / 디코드 불가 바이트 → 원본 반환 / 축소 결과가 더 크면
  원본 반환(고압축 소형 이미지로 재현).
- 잡 통합: 기존 `ImageArchiveJobTest` 경로에 리사이즈 통과가 끼어도 저장·기록 계약이
  유지되는지 확인.
- 백필: 드라이런으로 소량 프리픽스(`monitor-hashtag-post/` 등) 대상 리허설 후 본 실행.

## 6. 검증·롤백

- 배포 후 새벽 잡 1회 뒤: 신규 객체 샘플의 치수(≤720)·바이트 확인, `bucket_used_gb`
  증가 기울기 확인(정시 게시).
- 백필 후: `bucket_used_gb` ~25GB대 확인 + FE 주요 화면(랭킹 상세 패널·브랜드 모니터링 카드)
  눈 확인.
- 롤백: 원본은 IG CDN에서 이미 만료됐으므로 **백필은 비가역**이다 — 그래서 화질 승인(§1)과
  드라이런을 선행 게이트로 둔다. 잡 코드 쪽은 리사이즈 제거만으로 원상복귀.

## 7. 비범위

- webp 재인코딩·AVIF 등 포맷 전환(추가 의존성 대비 이득 불충분 — q70 JPEG로 충분).
- FE의 next/image 도입, srcset 다단 해상도.
- 수명주기 정책(사용자 배제 확정).
- `hypenow-llm-batch-v2`(Vertex 배치 버킷) — 무관.
