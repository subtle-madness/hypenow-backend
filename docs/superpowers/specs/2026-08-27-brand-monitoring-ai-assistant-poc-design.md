# 브랜드 모니터링 AI 어시스턴트 PoC 설계

> 상태: 🟢 활성
> 작성: 2026-08-27

## 1. 배경과 목표

서비스에 사용자 대면 AI 기능을 도입하되, 전면 도입이 아니라 가치가 가장 확실한 지점부터
테스트한다. 논의 결과(2026-08-27) 첫 표면은 **브랜드 모니터링 안의 자유 질의형 AI 어시스턴트**로
확정했다 — 정해진 분석 카드 하나를 만드는 게 아니라, 사용자가 자유롭게 질문하면 AI가
모니터링 데이터를 직접 조회해 답하는 구조.

기각한 대안(같은 논의에서):

- **성과 리포트 자동 생성** — 마케터의 실제 보고 형식·필요 데이터에 대한 도메인 지식이 없어
  정답지 없는 기능이 된다. 테스트 단계에 부적합.
- **자연어 발굴 검색** — 발굴 축이 아니라 모니터링 축이 이번 대상.
- **단일 고정 기능(예: 댓글 반응 분석 카드)** — 자유도가 낮아 "사용자가 뭘 원하는가"를 배우지
  못한다. 단, 댓글 분석은 어시스턴트가 답할 수 있는 질문 유형으로 자연 포함된다.

**PoC가 검증하는 것 세 가지:**

1. **수요** — 사용자가 어떤 질문을 던지는가. 질문 로그가 PoC의 핵심 산출물이다.
2. **품질** — 우리 데이터 + 툴 조합으로 쓸 만한 답이 나오는가.
3. **비용** — 호출량·토큰이 통제 범위인가.

## 2. 접근 방식 — 툴 콜링 에이전트

데이터 접근을 여는 방식 세 가지를 비교해 **A. 툴 콜링 에이전트**로 확정했다.

| 방식 | 판정 | 이유 |
|---|---|---|
| **A. 툴 콜링 에이전트** | ✅ 채택 | 질문 자유도는 무제한, 데이터 접근은 정의된 읽기 전용 툴 안으로 제한. 사용자 격리를 툴 레이어에서 강제. 툴 호출 로그가 수요 학습 자료가 됨 |
| B. text-to-SQL | 기각 | 자유도 최대지만 스키마 전체 이해 필요, 오답 쿼리가 그럴싸한 틀린 답을 만들고, SQL 레벨 사용자 격리 보장이 어려움 |
| C. 컨텍스트 조립 | 기각(흡수) | 캠페인 하나로 범위가 갇히고 댓글 포함 시 토큰 폭발. 필요하면 A의 툴 하나로 흡수 가능 |

접근 범위는 **모니터링 데이터로 한정**한다(발굴 쪽 분석 데이터 교차 조회는 후속 확장 후보).
툴에 없는 데이터를 묻는 질문에 답하지 못하는 것은 의도된 한계다 — 그 질문이 로그에 남아
다음 툴 백로그가 된다.

## 3. 위치와 구조

**was 모듈**에 둔다.

- 사용자 인증·브랜드 격리(`app.brand_monitorings`의 user_id↔brand_id 매핑)가 이미 was에 있다.
- `BrandReadRepository`(was/monitoring 패키지)가 monitoring DB 읽기 전용 조회를 이미 갖추고
  있어 툴이 그대로 재사용한다. 시스템 경계(was는 monitoring 조회 표면 읽기 전용) 무변경.
- LLM 전송은 **`common-llm`**(Vertex AI HTTP·SA 토큰·재시도) 의존을 was에 추가해 재사용한다.
  function calling 페이로드가 없으면 그 부분만 소폭 확장하되, **전송 계층 원칙 유지** —
  프롬프트·툴 정의·에이전트 루프는 전부 was 소관, common-llm에는 반입하지 않는다.
- 모델은 기존 스택대로 Vertex의 Gemini flash 계열(function calling 지원 모델).

에이전트 루프는 was 안의 단순 반복문이다: 시스템 프롬프트 + 대화 이력 → LLM →
(툴 호출이면 실행 후 결과를 되먹임)* → 최종 텍스트 답변.

## 4. 툴 정의 (6종)

전부 읽기 전용. `brandId`는 요청 파라미터로 받되 **유저 소유 브랜드 집합
(`app.brand_monitorings`) 안으로 서버가 강제** — 컨트롤러의 기존 격리 패턴과 동일하며,
LLM이 임의 brandId를 넘겨도 소유 검증에서 걸러진다.

| 툴 | 파라미터 | 데이터 소스 |
|---|---|---|
| `list_brands` | — | 유저의 브랜드 목록 + 계정 메타(`brand_account`) |
| `list_posts` | brandId, days, sort | 게시물 인덱스 + 최신 지표(`brand_tagged_post` + meta + snapshot) |
| `get_post` | shortCode | 게시물 상세: 캡션·광고 판정·지표 시계열(`brand_post_meta` + `brand_post_snapshot`) |
| `get_comments` | shortCode, limit | 댓글(`brand_post_comment`, 상한 50) |
| `list_hashtag_posts` | brandId, days | 해시태그 발견 게시물(`brand_hashtag_post`, RELEVANT만) |
| `get_author` | username | 게시자 프로필(`author_profile`) |

`get_post`·`get_comments`의 shortCode도 유저 소유 브랜드의 게시물 풀에 속하는지 검증한다.

## 5. API 계약

`POST /v1/brand-monitoring/ai/chat`

- **무상태**: 요청에 대화 이력(messages 배열)을 실어 보낸다. 서버 세션 없음(PoC 단순화).
- **응답**: 답변 텍스트 + 참조한 게시물 shortCode 목록(프론트가 링크를 걸 수 있게).
- **동기 응답**(타임아웃 60초). 스트리밍(SSE)은 지연 피드백이 오면 후속.

## 6. 로깅 — PoC의 진짜 산출물

`app` 스키마에 `ai_chat_logs` 테이블 신설(was Flyway, UTC 타임스탬프 채번):

- user_id, 질문, 답변, 호출된 툴 시퀀스(이름·파라미터·건수 — jsonb), 토큰 사용량, 소요 시간, created_at
- append-only. 이 로그가 "사용자가 무엇을 원하는가" 분석의 정본이다.

## 7. 가드레일

- 턴당 툴 호출 최대 **8회** (초과 시 그때까지의 정보로 답변 강제).
- 유저당 일일 질문 상한(기본 **30회**, `app.app_setting`으로 조정).
- 노출 킬 스위치: env 플래그(광고 판정 `AD_DISCLOSURE_EXPOSE` 패턴 재사용) — 끄면 기능
  전체가 404/비노출.
- 시스템 프롬프트로 모니터링 도메인 밖 질문(일반 상식·타사 데이터 등)은 정중히 거절.
- 댓글 등 대량 데이터 툴은 건수 상한을 툴 레이어에서 강제(모델 요청값과 무관).

## 8. 에러 처리

- **툴 실패**: 에러 메시지를 모델에 1회 되먹여 자가 수정 기회를 준다. 반복 실패 시 해당
  정보 없이 답변.
- **LLM 실패**(타임아웃·5xx·쿼터): 사용자에게 재시도 안내 응답. common-llm의 재시도/백오프를
  1차 방어로 사용.
- **한도 초과**(일일 상한): 명시적 안내 응답(429).

## 9. 테스트

- LLM은 실 API를 때리지 않는다(프로젝트 컨벤션) — 전송 포트를 fake로 갈아끼우고, 스크립트된
  툴콜 시퀀스로 에이전트 루프(호출→되먹임→종료·상한 동작)를 검증한다.
- 툴 레이어는 Testcontainers로 격리 검증. **남의 브랜드 brandId/shortCode 조회 시도가 막히는지**가
  필수 케이스.
- 로깅·일일 상한·킬 스위치도 통합 테스트 대상.

## 10. 범위 밖 (후속 후보)

- 발굴 쪽 분석 데이터 교차 조회 툴(하입 스코어·카테고리·광고 비중)
- SSE 스트리밍, 서버 측 대화 세션
- 질문 로그 기반 신규 툴 추가·고정 분석 카드 승격
- 프론트 UI 상세(이번 PoC의 백엔드 계약 확정 후 FE와 협의)
