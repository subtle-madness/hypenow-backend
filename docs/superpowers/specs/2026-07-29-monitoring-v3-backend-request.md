## 이 문서를 읽는 법

콘텐츠 모니터링은 브랜드가 협업한 인플루언서의 게시물을 등록해 두면 매일 지표를 쌓아 성과 추이와 반응을 보여주는 기능이다. 프론트 구현이 완료됐고 현재는 mock 데이터로 동작한다.

- **계약 자체**(엔드포인트·필드·검증 규칙)는 `api-spec.md` 6.25~6.33에 있다. 구현할 때는 그쪽이 정본이다.
- **이 문서**는 그 계약을 실현하기 위해 무엇을 새로 만들고 무엇을 재사용하는지, 그리고 **아직 사람이 결정해야 하는 것**이 무엇인지를 다룬다.

읽는 순서: 1절(기능 요약) → 2절(기존 자산과의 관계, 여기에 가장 큰 리스크가 있다) → 3절(배치) → 4절(엔드포인트) → **7절(결정 필요 항목)**. 시간이 없으면 2절과 7절만 봐도 된다.

## 1. 기능 요약

유저가 **인스타 게시물 링크** 또는 **계정 + 감지 조건**을 등록한다. 게시물은 즉시, 계정은 조건에 맞는 업로드가 올라오면 그때부터 수집 대상이 된다. 등록일 기준 N일(프리셋 7/14/21/30) 동안 매일 지표를 쌓고, 기간이 끝나면 종료된다. 매일 오전 9시에 그날의 변화를 알림 1건으로 묶어 알려준다.

기존 리더보드·발굴 기능과 결정적으로 다른 점 네 가지:

1. **유저가 대상을 지정한다.** 기존 파이프라인은 우리가 정한 풀(뷰티 마이크로 5,699계정)을 크롤하지만, 모니터링은 유저가 임의의 계정·게시물을 등록한다.
2. **지표가 6종이다.** 조회·좋아요·댓글에 더해 **저장수·공유수·리포스트수**가 필요하다. 기존 스키마에 없는 컬럼이다.
3. **댓글 원문이 필요하다.** 지표 숫자만이 아니라 실제 반응 내용과 인플루언서의 답글 여부를 보여준다.
4. **탈퇴 후에도 서버가 계속 일한다.** 이 제품에서 유일하게 유저가 떠난 뒤에도 배치가 도는 기능이다(3-4절 참조).

## 2. 기존 자산과의 관계

> ⚠️ 이 절은 crawler 파이프라인(raw DB) 재사용을 전제로 쓰였다. 07-30 결정으로 수집·감지·저장은
> monitoring 모듈(monitoring DB)이 담당하므로, 이 절의 테이블 매핑은 채택되지 않았다.
> 역사적 기록으로 보존한다.

### 2-1. 재사용 가능

| 기존 테이블 | 모니터링에서의 쓰임 |
|---|---|
| `contents` | 게시물 메타(썸네일, 캡션, 업로드일, 유형, 원본 URL). `short_code`가 그대로 조인 키가 된다 |
| `content_metric_snapshots` | 지표 시계열. 하루 1행 규칙이 모니터링 요구와 동일하다 |
| `accounts` | 계정 프로필(표시명, 프로필 이미지, 팔로워) |
| `account_summaries` | 팔로워·최근 업로드일 |
| `content_comments` | 댓글 원문. 단 부족한 컬럼이 있다(2-2 c 참조) |

이미 크롤 중인 계정·게시물이 등록되면 위 테이블의 값을 그대로 쓸 수 있다. 즉 **모니터링은 새 수집 파이프라인이 아니라, 기존 파이프라인에 "유저가 지정한 대상"을 추가하고 결과를 유저별로 묶어 보여주는 계층**으로 설계하는 편이 자연스럽다.

### 2-2. 확장이 필요한 것

**(a) 지표 3종 컬럼 추가** (필수. **D1 결정 완료: 수집 가능, 제공되지 않으면 null**)

`contents`와 `content_metric_snapshots` 모두 `views / likes / comments`만 있다. 계약이 요구하는 `saves / shares / reposts` 컬럼을 추가해야 한다.

```sql
ALTER TABLE content_metric_snapshots ADD COLUMN saves bigint, ADD COLUMN shares bigint, ADD COLUMN reposts bigint;
ALTER TABLE contents ADD COLUMN saves bigint, ADD COLUMN shares bigint, ADD COLUMN reposts bigint;
```

값이 없을 때 **0이 아니라 NULL**로 두는 것이 중요하다. 프론트는 null을 "제공하지 않는 지표"로 보고 집계 모수에서 제외하는데, 0으로 채우면 참여율이 왜곡된다. 유형별 제공 매트릭스는 api-spec 6.25에 있다(릴스는 6종 전부, 피드는 views·shares·reposts가 항상 null).

**이 3종은 모니터링 대상에만 적용된다.** 기존 리더보드·발굴 파이프라인은 지금처럼 조회·좋아요·댓글만 수집하면 되고, 모니터링 수집기가 채우는 행에만 값이 들어간다. 따라서 위처럼 공유 테이블에 nullable 컬럼을 더하는 방식(비모니터링 행은 null)과 모니터링 전용 스냅샷 테이블을 따로 두는 방식 둘 다 가능하다. 전자는 같은 게시물이 풀에도 있고 모니터링 대상이기도 할 때 시계열이 한 곳에 모이는 장점이 있고, 후자는 기존 파이프라인과 완전히 분리되는 장점이 있다. 프론트 계약은 어느 쪽이든 동일하다.

**(b) 수집 대상 범위 확장** (**D2 결정 완료: 온디맨드 수집 가능**)

현재 크롤 풀은 뷰티 마이크로 인플루언서 5,699계정으로 한정돼 있다. 모니터링은 유저가 임의 계정·게시물을 등록하므로:

- 풀에 없는 게시물 URL이 등록되면 그 게시물만 온디맨드로 수집
- 풀에 없는 계정이 등록되면 감지 대상으로 추가(매일 신규 업로드 확인)
- 등록이 종료·취소되면 감지 대상에서 제외

풀 밖 대상을 다루므로 실패 사유를 유저에게 정확히 알려주는 것이 중요하다. 처리 내역의 `reasonCode`(6.28)에 비공개 계정, 존재하지 않는 게시물, 링크 해소 실패를 구분해 담아야 한다.

**(c) 댓글 컬럼 추가** (**D3 결정 완료: 작성 시각·답글 모두 수집 가능**)

`content_comments`는 현재 `id / short_code / author_masked / body / like_count` 구조로 작성 시각과 답글 컬럼이 없다. 계약의 `PostComment`가 요구하는 `createdAt`(정렬 기준)과 `reply`(인플루언서 본인 답글)를 담을 컬럼을 추가한다. 답글은 **게시물 작성자 본인의 것만** 모은다. 제3자 답글까지 모으면 수집량과 마스킹 대상이 몇 배로 늘어나는데, 마케터가 확인하려는 것은 "인플루언서가 응대했는가"다.

작성자 계정명 마스킹은 응답 생성 단계의 서버 책임이다(개인정보처리방침 제3장 ②에 이미 공개돼 있다).

**(d) 감지·만료·숨김 판정 로직** (신규)

프론트에는 이 전이가 전혀 구현돼 있지 않다. 전부 서버 배치 책임이다.

- 키워드 조건 매칭으로 신규 업로드 감지
- 기간 만료로 종료 처리
- 게시물 비공개·삭제 감지
- 지표가 값에서 null로 바뀌는 전환 감지(알림 `metrics_private`의 근거)

### 2-3. 신규 테이블

api-spec 5.1의 엔티티에 대응한다. 컬럼은 제안이며 계약을 만족하면 형태는 자유다.

| 테이블 | 핵심 컬럼 | 비고 |
|---|---|---|
| `tracking_items` | id, user_id, mode(url/account), status, handle, source_url, short_code(nullable), campaign_id(nullable), registered_at, tracking_days, keywords(jsonb), next_check_at | 유저별 추적 행. 게시물이 특정되면 `short_code`로 `contents`와 조인 |
| `monitoring_campaigns` | id, user_id, name, description, start_date, end_date, brand, budget, created_at | (user_id, name) 유니크 |
| `registrations` | id, user_id, requested_at, completed_at | 등록 요청 1건 |
| `registration_entries` | registration_id, seq, input, kind(post/account), result, reason_code, reason, resolved_url, item_id | 건별 결과. `seq`로 요청 입력 순서 보존 |
| `daily_digests` | id, user_id, date, created_at, read_at, items(jsonb) | (user_id, date) 유니크 |
| `notification_settings` | user_id, settings(jsonb) | 유저당 1행, lazy 생성 |

주의할 제약:

- `monitoring_campaigns.name`은 유저 내 유니크여야 한다. 캠페인 상세 화면의 URL 키가 id가 아니라 **이름**이라서, 이름 유니크가 곧 라우팅 계약이다. 정규화·금지 문자 규칙은 api-spec 6.25 Campaign 절에 있다.
- `tracking_items`는 이름이 아니라 `campaign_id`로 캠페인을 참조하되, 응답에는 표시용 `campaignName`을 함께 담는다. 캠페인 이름이 바뀌면 응답의 `campaignName`도 즉시 따라와야 한다.
- `registration_entries.seq`가 없으면 처리 내역 화면의 결과 배지가 잘못된 항목에 붙는다(프론트가 배열 인덱스로 렌더한다).

## 3. 배치 작업 3종

시각은 전부 KST다.

### 3-1. 등록 시 온디맨드 수집 (요청 직후, 비동기)

등록 API는 접수만 하고 즉시 응답한다(201 + registrationId). 실제 수집은 백그라운드에서 수 분 내에 수행한다.

- 게시물 링크: 게시물 메타 + 첫 스냅샷 생성 → 행을 `collecting`에서 `tracking`으로 전환
- 계정: 프로필 메타 수집 → 행은 `detecting` 유지
- 실패(존재하지 않는 게시물, 비공개 계정 등): 행을 삭제하고 처리 내역에만 실패 사유를 남긴다

프론트는 실시간 통지 없이 목록을 다시 불러 상태 전환을 반영한다. 따라서 **몇 분 내 완료**가 체감 품질을 좌우한다.

### 3-2. 매일 새벽 2시 통합 배치

한 번의 배치에서 네 가지를 처리한다.

| 처리 | 대상 | 결과 |
|---|---|---|
| 지표 스냅샷 적재 | `tracking` 상태 게시물 | 하루 1행 추가 |
| 신규 업로드 감지 | `detecting` 상태 계정 | 조건 매칭 시 `collecting` → 첫 수집 후 `tracking` |
| 숨김·삭제 감지 | `tracking` 상태 게시물 | `hidden` 전환, 마지막 스냅샷 보존 |
| 기간 만료 처리 | 등록일 + tracking_days 경과 | `tracking`·`collecting` → `ended`, `detecting` → `not_uploaded` |

감지 규칙: 캡션 본문을 대상으로 `(and 전부) AND (or 중 1개 이상) AND NOT (exclude 중 1개라도)`를 적용한다. 대소문자 무시, 부분일치. **1계정 1게시물**이라 첫 감지 이후 그 행의 감지는 종료된다. **같은 유저의** 다른 행이 이미 추적 중인 게시물은 감지 후보에서 제외한다(다른 유저의 추적은 무관하다. 브랜드와 대행사가 같은 인플루언서를 동시에 시딩하는 것은 정상 시나리오다).

### 3-3. 매일 오전 9시 알림 배치

전날 배치 결과를 유저별로 묶어 다이제스트 1건을 만들고 이메일 1통을 보낸다.

- 이벤트 0건인 유저는 생성하지 않는다
- 이벤트 유형 4종: `collection_started` / `collection_ended` / `metrics_private` / `content_issue`
- 인앱 다이제스트는 설정과 무관하게 항상 생성하고, 이메일은 설정에서 켠 유형만 담는다

`metrics_private`는 "직전 스냅샷에 값이 있던 지표가 null로 바뀜"을 감지해야 성립한다. 전 지표가 사라지면 `content_issue`로 분류한다. `content_issue`는 **재시도가 소진된 뒤에만** 발화해야 한다. 그러지 않으면 인스타 차단이 하루 걸릴 때 전 유저에게 알림이 나간다.

### 3-4. 배치와 계정 수명주기

**탈퇴 시 진행 중인 추적 행을 가장 먼저 종결해 배치 대상에서 제외해야 한다.** 이 처리가 없으면 탈퇴한 유저의 대상 게시물을 계속 크롤하고 다이제스트와 이메일까지 생성한다. 탈퇴 모달은 이미 "모든 데이터가 삭제되며"라고 약속하고 있다.

삭제 대상은 모니터링 5개 엔티티(추적 행, 캠페인, 처리 내역, 다이제스트, 알림 설정)이며, **스냅샷 원본(`content_metric_snapshots`)은 전역 크롤 자산이라 삭제 대상이 아니다.**

## 4. 엔드포인트

전부 인증 필수이며 유저 소유 데이터로 격리된다. 상세는 api-spec 해당 절 참조.

| 순위 | 엔드포인트 | 절 | 비고 |
|---|---|---|---|
| 1 | `GET /v1/monitoring/items` | 6.26 | 전량 반환. 필터·정렬·검색은 프론트가 한다. `meta.lastCollectedAt` 필수 |
| 1 | `POST /v1/monitoring/items` | 6.27 | 비동기 접수. 건별 실패도 201 |
| 1 | `GET /v1/monitoring/campaigns` | 6.31 | 전량 반환 |
| 2 | `POST · PATCH · DELETE /v1/monitoring/campaigns` | 6.31 | 이름 중복 409. 삭제는 소속 행 연결만 해제 |
| 2 | `PATCH /v1/monitoring/items/{id}` | 6.29 | 기간·캠페인만 수정 |
| 2 | `POST /v1/monitoring/items/{id}/cancel` | 6.30 | 비가역 |
| 3 | `GET /v1/monitoring/registrations` | 6.28 | 등록 처리 내역 |
| 3 | `GET · POST /v1/notifications`, `/read` | 6.32 | 다이제스트 |
| 3 | `GET · PATCH /v1/notification-settings` | 6.33 | 이벤트별 이메일 토글 |

1순위 3개만 있으면 화면이 데이터를 보여주기 시작한다. 2순위까지면 편집·정리가 가능하고, 3순위는 부가 기능이다.

결정에 따라 추가될 수 있는 것: `GET /v1/monitoring/items/{id}`(단건 조회, D5가 상한·페이지네이션으로 결론 날 때 필수), `DELETE /v1/monitoring/items/{id}`(D8), `POST /v1/notifications/unsubscribe`(D15), 알림 커서 페이지네이션(D14).

## 5. 프론트가 처리하므로 백엔드가 하지 않아도 되는 것

계약을 단순하게 유지하려고 의도적으로 클라이언트에 남긴 것들이다. 서버가 미리 계산해 줄 필요가 없다.

- **필터·검색·정렬·상태별 카운트**: 목록을 전량 받아 프론트에서 처리한다. 쿼리 파라미터가 없다
- **캠페인 집계**: 합산 조회수·좋아요·댓글, 참여율, CPE·CPV 전부 프론트 파생이다
- **오늘의 성과 요약**: 최신 스냅샷과 직전 스냅샷의 차이로 계산한다. 서버는 스냅샷만 정확히 주면 된다
- **차트 좌표·눈금·툴팁**: 스냅샷 배열만 있으면 된다
- **알림 딥링크**: 이벤트 유형으로 프론트가 경로를 만든다. 응답에 링크를 담지 않는다
- **상태 라벨 문구**: 서버는 enum 코드만 주면 된다

반대로 **상태값 자체는 반드시 서버가 계산해서 내려줘야 한다.** 프론트는 상태를 표시만 하고 판정하지 않는다.

## 6. 계약 무결성 규칙 (지키지 않으면 화면이 조용히 잘못 동작한다)

프론트에 런타임 스키마 검증이 없다. 응답 형태 위반은 파싱 단계에서 잡히지 않고 렌더 단계에서 드러나거나, 더 나쁘게는 **아무 에러 없이 반대로 동작한다.** 아래 다섯 가지는 구현 시 반드시 지켜야 한다.

| # | 규칙 | 어기면 생기는 일 |
|---|---|---|
| 1 | **nullable 필드는 키를 생략하지 말고 명시적 `null`로 직렬화** | 알림 `readAt`이 생략되면 `undefined !== null`이 참이 되어 전 알림이 읽음 처리되고 배지가 영구히 0이 된다. 에러도 로그도 남지 않는다. Jackson의 NON_NULL 설정이 기본이면 바로 발생한다 |
| 2 | **enum 신규 값 도입은 프론트 배포 선행** | 모르는 알림 유형이 오면 대시보드 전체가 오류 화면으로 교체된다. 모르는 상태값이 오면 카드가 조용히 사라지고 헤더 건수만 남는다 |
| 3 | **`campaignId`가 값이면 캠페인 목록 응답에 반드시 존재** | 유령 캠페인 카드가 생긴다. 소속 콘텐츠 0건, 지표 전부 `-`, 클릭하면 빈 상세 |
| 4 | **응답 `handle`은 소문자 정규화** | 등록 모달의 중복 안내 배지가 조용히 사라진다(정확 일치 비교) |
| 5 | **`meta.lastCollectedAt`은 마지막으로 성공한 배치 완료 시각** | 부분 수집 중 조회하면 서로 다른 날짜의 증가분이 하루 종일 섞여 합산된다. "변화 없음"과 "배치 실패"를 화면에서 구분할 유일한 수단이기도 하다 |

여기서부터는 사람이 정해야 한다. 코드로는 답이 나오지 않는 것만 남겼다. 괄호 안은 api-spec 7절 번호.

### 7-0. 결정 완료 (2026-07-29)

| # | 항목 | 결정 |
|---|---|---|
| **D1** | 저장수·공유수·리포스트수 수집 | **가능. 제공되지 않으면 null.** 이 3종은 모니터링 대상에만 적용되며 기존 리더보드 파이프라인은 그대로 둔다 |
| **D2** | 풀 밖 계정·게시물의 온디맨드 수집 | **가능.** 등록 대상에 제한을 두지 않는다 |

| **D5** | 유저당 추적 행 상한 | **현재는 상한 없음.** 결제 도입 시점에 다시 다룬다 |

## 8. 프론트에 남은 일 (백엔드 작업 아님, 참고용)

계약이 아니라 프론트 배선 문제다. 실 API 연결 시 함께 처리한다.

**데이터 계층**
- 모니터링만 프로젝트의 react-query·DataSource 포트 밖에 있다. 그대로 두면 전역 401 세션 만료 처리, 재시도 정책, 유저 스코프 캐시 무효화가 모니터링에서만 동작하지 않는다
- 스토어를 `(로딩, 데이터)`에서 `(로딩, 에러, 데이터)` 세 축으로. 지금은 실패와 빈 상태를 구분할 수 없다
- Provider가 대시보드 전체를 감싸고 있어, 그대로 fetch를 넣으면 모니터링과 무관한 페이지도 전량 조회를 유발한다

**수정 완료 (2026-07-29)**

전수 검증에서 확정된 결함 19건을 수정하고 적대적 재검증을 통과했다. 크래시 3건(캠페인 이름의 `%`로 인한 상세 렌더 실패, 미지 알림 유형으로 인한 대시보드 전체 오류 화면, 미지 상태값으로 인한 카드 소실), 조용히 틀리던 것 6건(읽음 판정, 중복 판정 키, 공유 단축 링크 변환, null 지표 집계, 첫날 빈 상태 문구, 취소 토스트), 막다른 길 2건(등록 데드락, 유령 캠페인 페이지), 나머지는 폴백·로딩·진입점 보강이다.

**미연결 (실 API 붙일 때 함께 처리)**
- 알림 설정을 서버에서 조회하지 않는다. 이대로 실 API에 연결되면 유저가 껐던 메일이 계속 나가는데 화면은 켜짐으로 보인다. 해당 위치에 주석을 남겨뒀다
- 다이제스트 목록이 마운트 후 갱신되지 않는다. 9시 이전에 열어둔 탭은 그날 알림을 영원히 못 본다
- 모니터링 기능에 분석 이벤트가 한 건도 없다. D6·D7 같은 남은 결정에 필요한 실사용 데이터가 쌓이지 않는다
