# 브랜드 게시물 목록 타임아웃 해소 — 댓글 제외·페이지네이션·경량 counts 설계

> 상태: ✅ 구현/반영됨

## 배경

FE 변경요청(2026-08-27): `GET /v1/brand-monitoring/accounts/{id}/posts`가 페이지네이션 없는
전량 단일 응답이라 게시물 많은 계정(운영 marynmay_global 최근 1개월 재현)에서 프론트
타임아웃(30초)을 넘긴다. 요청 3건 —
① 목록에서 `recentComments` 제외(상세만 유지), ② 리더보드(6.1) 계약을 복제한
offset/limit 페이지네이션(생략 시 전량 유지), ③ counts·total을 요청 시 풀스캔으로 세지 말 것
(FE 제안 형태는 수집 파이프라인의 사전 집계 테이블).

무엇이 실제로 느린가: 목록 조립은 윈도우 안 게시물 **전량**에 대해 메타·스냅샷·댓글·게시자를
배치 조회해 풀 카드를 만든다. 스냅샷은 게시물당 일 단위 시계열 전량(365일이면 게시물당 최대
365행 — 463건 브랜드면 최대 ~17만 행)이고, 댓글은 08-12 실측으로 조립 시간의 57%였다.
counts는 그 풀 조립 결과에서 센다 — 즉 "첫 페이지 50건"을 위해서도 전량 풀 조립이 필요했다.

## 결정

### 1. 목록은 댓글 없이 조립한다 (요청 1, P0)

목록 경로는 어셈블러의 기존 `withComments=false` 관용구(08-12 성과 대시보드 대응으로 이미
존재)를 탄다 — 댓글 윈도우 쿼리 자체가 돌지 않는다. 응답 셰이프는 계약 무결성 규칙(키 생략
금지)대로 키를 유지한다: `recentComments: []`, `commentsCollectedCount: 0`.
스냅샷 유래 지표(`commentsTotal`·`commentsHidden`)는 불변. 과도기 폴백(레거시 direct) 카드도
목록에서는 같은 규칙으로 댓글을 비운다. 상세(`GET /posts/{postId}`)는 현행대로 포함.

### 2. offset/limit 페이지네이션 — `meta.page` 신설 (요청 2, P1)

- 파라미터: `limit`(1..100, 리더보드와 같은 캡) · `offset`(≥0). 범위 밖은 400.
- **둘 다 생략 시 기존 전량 응답 그대로**(하위 호환). 하나라도 있으면 페이지 모드 —
  `limit` 기본 100, `offset` 기본 0.
- `meta.limit`은 "수집 상한"(2000) 의미로 이미 쓰이고 있어 **건드리지 않는다**(개명은 기존
  FE가 읽는 필드를 깨뜨린다). 페이지 정보는 additive 신설 필드 `meta.page = {"offset": n,
  "limit": n|null}` — 전량 응답이면 `{"offset": 0, "limit": null}`.
- `meta.total` = 필터 적용 후 **전체** 건수(페이지로 안 잘린 값, POST_LIMIT 캡은 현행 유지).
  전량 응답에서는 오늘의 값과 동일하다. `meta.counts`는 현행대로 필터 전 전량 기준 — 페이지와
  무관하게 유지되어 FE 필터 칩 숫자가 보존된다.
- 정렬은 기존 comparator 그대로(shortcode 최종 타이브레이크가 있어 전순서) — 페이지 간
  중복·누락 없음.

### 3. counts·정렬은 경량 인덱스 패스로 — 사전 집계 테이블은 채택하지 않는다 (요청 3)

FE가 제안한 "수집 시점 버킷 테이블(계정×일자×출처×협찬)"은 **채택하지 않는다**. 이 표면의
counts는 버킷으로 고정할 수 없는 조회자 종속·소급 계산 값이기 때문이다:

- **협찬 판정은 조회 시 계산이 설계 정본** — `BrandSponsorshipClassifier` 주석에 "조회 시
  계산·저장 없음(캡션 원문이 있어 키워드 개선이 과거분에 즉시 소급)"이 명시돼 있다. 버킷에
  굳히면 키워드 개선 소급이 죽고, 개선 시마다 버킷 전체 재계산이 필요하다.
- **source·가시성이 조회자 종속** — direct-only 게시물은 등록자에게만 보이고, 겹침 행은
  등록자에겐 direct·타인에겐 tagged다(08-19 요구사항). 링크 창(collectionMonths)도 유저별이고
  direct는 창 예외다. 계정 단위 버킷만으로는 유저별 counts가 계산되지 않는다.
- **드리프트 원천 다수** — 취소 시 행 소멸, unavailable 마킹, 캡션 재수집, 레거시 폴백
  (유저별 app DB) 등 증분 유지가 새는 경로가 많아, 완료 판정("counts가 전량 계산 값과 일치")
  을 증분 버킷으로는 보장하기 어렵다.

대신 **같은 목표(응답 시간이 게시물 수와 사실상 무관)를 읽기 경로 재구성으로 달성한다**:

- **인덱스 패스(경량)**: 풀 행(`findBrandPostsInWindow`, 기존) + 신설 경량 프로젝션
  `findSponsorshipMeta`(short_code·is_paid_partnership·caption만) + (performance 정렬일 때만)
  신설 `findLatestViews`(게시물당 최신 스냅샷 1행)로 `PostRef`(shortcode·source·sponsorship·
  uploadedOn·latestViews)를 만든다. 스냅샷 시계열·댓글·게시자·캠페인 조회가 전혀 없다.
  counts·링크 창·필터·정렬·total·페이지 슬라이스는 전부 이 ref 위에서 계산한다 — 판정 함수
  (classify·resolveSource·uploadedOn·창 규칙)는 풀 조립과 동일 코드를 쓰므로 counts는 전량
  계산 값과 정의상 일치한다.
- **하이드레이트 패스(무거움)**: 페이지에 든 shortcode들만 메타·스냅샷·게시자·캠페인 배치
  조회로 풀 카드를 조립한다(목록은 댓글 제외 — 결정 1). 전량 응답이면 전 코드 하이드레이트
  (기존과 동일 결과).
- 풀 자체가 수집 상한 2,000으로 유계라 인덱스 패스는 O(상한)로 캡되고, 무거운 비용(스냅샷
  시계열·댓글)은 페이지 크기에만 비례한다.
- 상세 엔드포인트도 같은 기계를 탄다 — ref에서 shortcode 매칭·창 판정 후 그 1건만
  하이드레이트(댓글 포함). 브랜드마다 전량 풀 조립하던 기존 상세 경로의 비용도 함께 준다.

레거시 과도기 폴백(migrated_at IS NULL)은 유저별 소량·이관으로 소멸 중이라 현행대로 전체
조립해 ref·카드 양쪽에 재사용한다(풀 우선 병합 규칙 불변).

## 완료 판정 (FE 요청 기준)

- marynmay_global 12개월 조회가 `limit=50` 첫 페이지 기준 2초 내 응답 — 첫 페이지 비용이
  "인덱스 패스(경량 3~4쿼리) + 50건 하이드레이트"로 재편되어 충족.
- `meta.total`·`counts`가 전량 계산 값과 일치 — 같은 판정 코드로 계산하므로 구조적으로 일치.
- 파라미터 생략 시 기존 응답 유지(단, 결정 1의 `recentComments: []`는 의도된 계약 변경 —
  FE가 상세 조회 병행 수정), 상세에는 `recentComments` 포함.
