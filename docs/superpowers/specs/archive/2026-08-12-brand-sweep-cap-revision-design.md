# 브랜드 태그 열거 안전 상한 개정 — 백필 공백 영구화·상한 루프 결함 대응

> 상태: ✅ 구현됨 (2026-08-12 — tooq.official 등록 백필 상한 중단 운영 실측 대응.
> [크롤링 정책 v1 스펙](2026-08-09-brand-crawl-policy-v1-design.md) §6의
> `max-posts-per-sweep` 값·상한 도달 시맨틱만 개정 — 티어 정책·수집 경로·저장 골격은 불변)

## 0. 한 줄 요약

안전 상한 `monitoring.brand.max-posts-per-sweep`을 **2,000 → 10,000**으로 올려 "정상 경로에서
닿으면 안 되는 폭주 방어 밸브"라는 자기 전제를 복원하고, 상한 도달을 **error 레벨 + 커버 깊이
로그**로 격상해 조용한 영구 공백을 운영 신호로 바꾼다. 코드 구조 변경 없음 — 재개형(이어받기)
백필은 커서 체인 구조상 진전이 없어 기각. tooq의 172~365일 공백은 `last_swept_on` 리셋
1줄 SQL로 다음 야간 스윕이 재백필한다(was ready는 08-10부터 `last_swept_at` 기준이라 FE 무영향).

## 1. 운영 실측 — 무엇이 깨졌나 (2026-08-12)

tooq.official(brand_account id=34, ig_user_id=10009952791, 08-12 05:06 UTC 등록):

- 등록 백필이 `/v2/user/tag/medias` 96콜(콜당 p50 4.9초, 순차 커서 체인)로 **2,016건**을
  열거한 뒤 상한(2,000) 도달로 중단. 커버 깊이는 2026-02-22(등록 시점 기준 ~171일)까지 —
  365일 편입 창의 **172~365일 구간 미수집**.
- 유입률 실측 2,016건/171일 ≈ **11.8건/일** → 365일 창 추정 **~4,300건(~205콜)**. 즉 tooq는
  폭주가 아니라 정상 고물량 브랜드인데 상한에 닿았다 — "정상 경로에서 닿으면 안 되는 값"
  (정책 v1 §6)이라는 상한의 자기 전제가 값 2,000에서 이미 깨져 있었다(캘리브레이션 기준이
  cclime 847건이었다).
- `runBackfillSafely`는 `sweepCore` 정상 반환(상한 중단은 예외가 아니다) 직후 무조건
  `touchSwept`를 찍는다 → 이후 일일 스윕의 열거 컷은 14일+due 기준으로만 열리고, 미수집
  구간의 게시물은 링크 자체가 없어 due를 만들 수 없다 → **공백이 조용히 영구화**된다.

## 2. 추가 진단 — 방치 시 09-11부터 일일 스윕 상한 루프

백필 공백과 별개로, 상한 2,000은 tooq의 **일일 스윕도** 걸리게 한다: 등록 +30일(09-11경)
90~180일 티어(주기 30일)가 일제히 due가 되면 열거 깊이가 180일까지 열리는데, 그 깊이의
게시물 수(~2,100+)가 상한을 넘는다. 상한 중단은 `touchCrawledDepth`를 하지 않고(그 자체는
맞는 동작 — 커버 못 한 깊이다) 미열거 심층 due가 남으므로, **다음 날 스윕이 같은 깊이를
다시 열어 또 상한에 걸린다** — 잔존 due가 180일 노화로 빠질 때까지 ~열흘간 매일 ~96콜
낭비 루프가 돌고, 티어 주기가 30일이라 매달 재발한다. 상한 상향은 이 시한폭탄도 함께
해체한다(180일 깊이 ~2,100건 ≪ 10,000).

## 3. 대안 비교와 결정

| 대안 | 판정 | 근거 |
|---|---|---|
| **A. 상한 상향(2,000→10,000) + 도달 시 error 로그** | **채택** | 상한의 취지(폭주 방어) 복원. 코드 구조·정책 불변 |
| B. 백필 미완을 상태로 남겨 다음 스윕이 이어받기 | 기각 | 태그 열거는 **커서 체인이라 재개도 항상 첫 페이지부터 재열거**한다 — 같은 상한이면 같은 깊이에서 또 멈춰 진전이 0이고, 진전을 만들려면 "커버 깊이" 영속화 + 일일 예산 회계가 필요해 정책 v1의 "저장 티어 상태 없음" 원칙을 깬다. 상한이 충분히 높으면 백필은 1회에 자연 종료되므로 풀 문제 자체가 소멸 |
| C. `touchSwept` 보류(백필 미완 시 ready 안 찍기) | 기각 | 다음 스윕이 매일 365일 재열거를 반복(B와 같은 무진전 루프) + 수집분 서빙도 늦어진다. 상한 도달 시엔 "있는 만큼 즉시 서빙 + 운영 알람"이 맞다 |
| D. 상한 폐지 | 기각 | 커서 미전진 가드가 있어도 미지의 폭주 양상(예: Hiker 응답 이상으로 무한 신규 code)에 대한 최후 밸브는 남긴다. 10,000(~476콜, ~39분, ~$0.29)이면 밸브가 열려도 피해가 유한 |

**상한 도달 시맨틱(확정)**: 도달 = 폭주 또는 상한 캘리브레이션 오류라는 **운영 이상 신호**다.
`touchSwept`·수집분 서빙은 유지하되(재시도 루프 방지) error 레벨로 열거 건수·목표 컷·실제
커버 깊이를 남긴다 — Loki `{service="monitoring"}`에서 식별해 상한 임시 상향(env) +
`last_swept_on` 리셋으로 보정하는 것이 운영 절차다.

## 4. 변경 내역

- `monitoring.brand.max-posts-per-sweep` 기본값 2,000 → **10,000** (`application.yml` +
  `@Value` 기본값). 배포 env 오버라이드 없음 확인(compose는 크론만 주입).
- `BrandCollectService.sweepCore` 상한 도달 로그 warn → **error**, 열거 건수·목표 컷·커버
  깊이(최고령 열거 taken_at) 포함.
- 열거 루프·중단 규칙·티어 정책·저장 골격 변경 없음.

## 5. tooq 운영 보정 (일회성 — 사용자 확인 후 실행)

배포 후 운영 monitoring DB에서:

```sql
UPDATE brand_account SET last_swept_on = NULL WHERE id = 34;  -- tooq.official
```

- 다음 야간 스윕(KST 03:00)이 `last_swept_on` null → 365일 전체 백필 경로를 다시 탄다:
  core ~205콜(~17분) + 보강(게시자·댓글, 미수집 구간 ~2,300건분 — 워커 6 병렬 ~30분).
- **FE 무영향**: was ready 판정은 08-10부터 `last_swept_at`(완주 사실값) 기준
  (`BrandAccountAssembler` — 정확히 이런 정책 리셋 시나리오를 위해 바뀐 판정)이라 기존
  수집분은 리셋 중에도 계속 서빙된다.
- 재열거되는 기지 게시물은 전부 멱등(스냅샷 upsert·링크 ON CONFLICT DO NOTHING·워터마크
  게이트) — 부작용 없음.
- 공백 구간 게시물 중 발견 시점 나이 180~365일은 정책대로 스냅샷 1회 후 종료, ≤180일은
  티어 추적 편입. 과거 추이는 원천적으로 없으므로 `first_seen_at`으로 투명 표기(정책 v1 §3).
- 보정을 미루면 창이 하루씩 잘린다(365일 창이 실행일 기준이라) — 배포 후 조기 실행 권장.

## 6. 고물량 브랜드 유지 비용 재산정 (tooq급 11.8건/일 기준)

티어 주기 × 열거 깊이(깊은 열거가 얕은 티어 자동 포함, 콜당 21건·$0.0006):

| 열거 깊이 | 주기 | 콜/회 |
|---|---|---|
| 14일 (~165건) | 매일 | ~8 |
| 30일 (~354건) | 3일 | ~17 |
| 90일 (~1,060건) | 7일 | ~51 |
| 180일 (~2,120건) | 30일 | ~103 |

월 합계 **~720콜 ≈ $0.43/월**, 최심 스윕일 ~103콜 ≈ **~8.4분**(순차 커서 체인 — 병렬화
불가 제약). 판단: **허용** — 매일 전량(구 정책)이라면 같은 브랜드가 월 ~3,100콜이었으니
티어 정책이 여전히 4배+ 절감이고, 브랜드 단위 격리라 8분 점유는 야간 배치 창에서 무해하다.
스윕 총 시간이 문제되는 규모(수십 고물량 브랜드)가 오면 v1.1(적응형 조정·딥 스캔)에서 재론.
