# 요청 추적 대시보드 설계 — requestId로 로그를 요청 단위로 열람

> 상태: 🟢 활성 · ✅ 구현/반영됨

2026-08-23 MDC 요청 ID 도입(PR #534, DECISIONS 2026-08-23 항목)의 소비 측 후속. 로그에 심긴
`requestId`를 그라파나에서 실제로 활용하는 탐색 동선을 만든다.

## 목적

- 느린·실패한 요청 하나를 집어 **그 요청의 was·monitoring 로그 줄들만 시간순으로** 보고,
  줄 간 타임스탬프 간격으로 어느 구간이 느렸는지 읽는다(APM 없는 개별 요청 추적의 소비 UI).
- 진입점 문제 해결: "어느 ID를 볼지"를 대시보드 안에서 바로 줍는다(최근 에러 요청 목록).

## 결정 사항 (사용자 확정)

1. **배치**: 새 소형 대시보드 — `deploy/grafana/provisioning/dashboards/json/hypenow-request-trace.json`
   → "HypeNow" 폴더 자동 로드. 기존 대시보드 무수정. 진단 용도가 관제 대시보드와 성격이 달라 분리.
2. **구성**: 최소형(변수 + 통합 로그 패널) + **최근 에러 요청 테이블**.

## 구성 요소

### 텍스트박스 변수 `request_id`

기본값 `?` — 어떤 ID와도 매칭되지 않는 문자라 "입력 전엔 아무것도 안 나옴"이 명시적.
(빈 문자열 기본값은 `[]`(요청 밖 로그)와 매칭돼 혼란 — 기각.)

### 요청 로그 패널 (메인)

```logql
{service=~"was|monitoring"} |= `[$request_id]`
```

- 대괄호 포함 부분문자열 매칭 — correlation 슬롯의 ID만 정확히 잡는다(메시지 본문에 우연히
  같은 8자가 나와도 대괄호 없이는 미매칭). requestId를 Loki **라벨로 만들지 않는다** —
  요청당 유니크 값의 라벨화는 카디널리티 폭발(설계 원칙).
- 시간 **오름차순** 정렬 — 위→아래로 타임스탬프 간격을 읽는 동선.
- was·monitoring 합산 — 모듈 경계를 넘는 흐름(was 접수 → monitoring 처리)이 한 줄기로 보인다.

### 최근 에러 요청 테이블 (진입점)

```logql
topk(50, sum by (request_id, service) (count_over_time(
  {service=~"was|monitoring", level="ERROR"}
    | regexp `\] \[(?P<request_id>[A-Za-z0-9_-]{1,64})\] \S+\s+: `
    | request_id != `` [$__range])))
```

- 인스턴트 쿼리, 대시보드 시간 범위 전체(`$__range`) 집계.
- 정규식 앵커: "대괄호 그룹 바로 뒤에 로거명(`\S+`)과 ` : `" — 라인의 다른 대괄호
  (`[모듈명] [스레드명]`)와 오인 매칭을 배제한다(스레드명 뒤엔 다음 대괄호가, 모듈명 뒤엔
  스레드 대괄호가 오므로 앵커 불일치). 빈 correlation(`[]`, 요청 밖 에러)은 그룹이 1자 이상을
  요구해 자연 제외.
- `request_id` 컬럼에 **데이터 링크**: 클릭 → `var-request_id=<ID>`로 같은 대시보드 재진입 →
  로그 패널이 그 요청으로 필터됨. 시간 범위는 `${__url_time_range}`로 보존.

## 검증

- 로컬 grafana-dev 스택(127.0.0.1:3300, 레포 provisioning 마운트·60초 리로드)에서 대시보드
  로드·변수·패널 구조 확인. **Loki 스텁이라 데이터 표시는 운영에서만**(dev README "운영과 다른
  점" 관례 — '등록 초기 응답' 패널과 동급).
- 데이터 검증은 PR #534 배포 후 운영 그라파나에서: 에러 테이블에 ID가 잡히고, 클릭 시 로그
  패널이 해당 요청의 두 모듈 줄을 시간순 표시하는지.
