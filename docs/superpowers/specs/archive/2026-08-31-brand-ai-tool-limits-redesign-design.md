# 브랜드 AI 어시스턴트 툴·한계 재설계 (2026-08-31)

> 상태: ✅ 구현됨(2026-08-31)

## 0. 한 줄 요약

"집합 연산은 서버로" 원칙을 게시물 지표 축 너머(작성자·기간·여론 축)로 확장하고,
가드레일 한계를 대리 지표(툴 회수)가 아니라 뿌리 자원(시간·비용)에서 재도출한다.
구현 순서는 **A(툴·한계 구조) → eval(골드셋 자동 채점) → 모델 설정 실험**.

## 1. 배경 - 실측 결함 (2026-08-31, 로컬 ai_chat_logs id=20)

프리셋 1번 "팔로워 대비 반응 터지는 인플루언서 10명 정리해줘" → 5명만 반환 + 도달
배수 정렬 오류(92.15→7.27→6.00→10.49→5.06, 3·4위 역전).

원인은 모델이 아니라 구조다:

- 팔로워를 얻는 유일한 경로가 단건 get_author뿐이라, list_brands(1)+list_posts(1) 후
  남는 예산 6회로는 작성자 6명분 팔로워가 상한이다. **툴 8회 상한 안에서 10명은
  산수적으로 불가능**했고, 프리셋 지시문(efficient_influencers)이 정확히 그 경로
  (list_posts → 작성자별 get_author)를 공식 지시하고 있었다.
- 끊긴 시점에 진짜 자원(벽시계 55초·토큰 6만)은 남아 있었다. get_author는 수십 ms짜리
  단건 DB 조회다. 시간·토큰을 아끼려는 대리 지표(회수 상한)가 툴별 실비용 차이(무거운
  list_posts와 가벼운 get_author를 똑같이 1회로 계산)를 무시해서, **자원이 남았는데
  회수가 먼저 끊는 배신**이 일어났다.
- 도달 배수 나눗셈·정렬은 thinking을 끈 flash가 암산으로 수행 → 순위 역전.

같은 병의 전례: 캡션 카운트 오답(정답 75건을 0건으로) → search_posts 신설, 합계 오답
→ aggregate_posts 신설(2026-08-28, "집합 연산은 SQL로 - 샘플을 모델 눈에 먹이지
않는다" 원칙 확립). 이번 사례는 그 원칙이 **게시물 지표 축에만 적용되고 작성자·기간·
여론 축에는 미적용**이라 재발한 것이다. 축을 하나씩 열거해 전용 툴을 추가하는 두더지
잡기 대신, 이번에 구조로 닫는다.

## 2. 설계 원칙 (이번 합의로 확정)

1. **정량 질문은 조합형 툴이 공간 전체를 덮는다** - 사용자 질문은
   필터(기간·타입·협찬·키워드) × 묶기(작성자·기간·협찬여부·타입) × 집계 × 정렬의
   곱 조합 공간이다. 전용 툴 열거는 이 공간의 점 하나씩만 덮으므로, SQL GROUP BY와
   동형인 조합형 인자로 덮는다.
2. **정성 질문(댓글 여론·캡션 톤 등)은 계산이 아니라 읽기다** - 표본 기반이 본질이고,
   고칠 것은 수집 효율(단건 N콜 → 배치 1콜)과 정직한 표본 고지다.
3. **산수·정렬은 서버가 한다** - 파생 지표(도달 배수·참여율)의 정의와 계산·정렬을
   서버 코드에 고정한다. 모델의 일은 해석·서술이다.
4. **한계는 뿌리에서 도출한다** - 뿌리는 둘뿐이다: 사용자가 기다려줄 시간, 질문당
   감당할 비용. 나머지 한계는 전부 파생이며, 회수 상한은 안전망으로 강등한다.

## 3. 툴 재편

### 3-1. aggregate_posts 일반화 (선택지 1 채택)

기존 aggregate_posts에 인자를 추가한다. **groupBy 생략 시 현행과 완전 동일**(스칼라
집계)이라 기존 호출 무회귀.

```
aggregate_posts(
  brandId,        // 기존
  days,           // 기존 (생략 = 수집 기간 전체)
  keyword,        // 신규: 캡션 필터 (search_posts와 같은 정규화 규칙 - 공백 흡수)
  groupBy,        // 신규: enum [author | month | week | sponsorship | mediaType]
  orderBy,        // 신규: enum [postCount | totalViews | avgViews | avgLikes |
                  //        avgComments | reachMultiple | engagementRate]
  limit           // 신규: 그룹 상위 N. 기본 10, 최대 50
)
```

- 계산·정렬은 창 안 **전체**를 대상으로 서버에서 수행하고, limit은 결과 행을 몇 등까지
  보여줄지만 자른다(list_posts의 30건 표본 문제와 순서가 다르다 - 표본 위 계산이
  아니라 전수 계산 후 절단).
- `groupBy=month|week`가 기간 비교 축("지난달 대비")을 흡수한다 - 별도 compare_periods
  툴을 만들지 않는다. 버킷 경계는 KST 달력 기준(월은 1일~말일, 주는 월요일 시작)이다 -
  "지난달"이라는 질문의 자연스러운 의미와 일치시키고 롤링 30일 해석을 배제한다. `groupBy=sponsorship`이 협찬 vs 오가닉 비교(프리셋 3번)를 1콜로
  흡수한다.
- 응답에 `totalGroups`(전체 그룹 수)를 항상 싣는다 - "전체 47명 중 상위 10명 기준"을
  모델이 명시할 수 있게. 조용한 절단 금지.
- **limit 상한 도출 근거**: 그룹 행은 캡션 등 자유 텍스트가 없는 순수 숫자 행(행당
  60~80토큰)이라 50행 ≈ 3~4천 토큰으로 예산 대비 저렴하다. list_posts 30건 상한이
  빡빡한 이유(행당 캡션 120자)와 조건이 다르므로 상한도 다르게 잡는다. 정확한 값은
  구현 시 실제 행 크기를 재서 확정하되 "현실적 질문의 N을 덮을 만큼"이 기준.
- 요청 N > 상한이면 클램프하되 totalGroups와 함께 절단을 모델이 명시 고지한다.
  ("30명 시켰는데 20명" 류의 조용한 부분 답변을 설계 단계에서 재발시키지 않는다 -
  eval 골드셋에 N > 기본값 케이스를 반드시 포함한다.)

### 3-2. 파생 지표 서버 계산

작성자 그룹 행에 서버가 계산해 싣는다:

- `followers` - 기존 findAuthorsByUsernameBatched(1,000건 IN절) 재사용.
- `reachMultiple` = 릴스 평균 조회수 ÷ 팔로워. 팔로워 null·0이면 null(제외가 아니라
  유지 + 정렬 시 nullsLast - "계산 불가"도 답변에 나와야 한다).
- `engagementRate` = 댓글 합 ÷ 조회수 합(릴스만 - 피드는 조회수 항상 null). 저장·공유
  수집 시 산식 확장.

프롬프트 개정: 규칙 13·14가 "이 산식으로 계산하라"(모델 산수 지시)에서 "서버가 준
reachMultiple·engagementRate 값을 그대로 인용하고 직접 계산하지 말라"로 바뀐다(규칙
4가 totalMatches 등에 이미 쓰는 관용구와 동형).

### 3-3. get_comments 배치화 (정성 축)

`shortCode` 단건 → `shortCodes` 배열(최대 5개)로 확장. 게시물당 기본 10건, 전체 총
상한 50건(기존 MAX_COMMENTS와 동일 - 토큰 예산 불변). 원소 1개 배열 = 기존 단건과
동일 취급이라 하위호환. "상위 게시물들 댓글 여론"이 5콜 → 1콜.

### 3-4. 프리셋 지시문 재작성

5개 프리셋 지시문을 새 툴 경로 기준으로 재작성한다. 특히 efficient_influencers는
"`aggregate_posts(groupBy=author, orderBy=reachMultiple, limit=10)` 한 번으로
조회하라"처럼 **정확한 인자 조합을 지시문에 박는다** - flash의 조합형 스키마 오용
위험을 프리셋 경로에서 사실상 0으로 만드는 완화 장치를 겸한다.

### 3-5. 검토 후 기각·보류된 대안 (재론 시 참조)

- **신규 툴 분리(query_posts 신설)** - 기각. 이 시스템의 실측 오답 이력이 전부 "모델이
  잘못된 툴로 세다 틀림"이라 툴 간 역할 중복은 최대의 적. aggregate와 query의 라우팅
  혼동 지점을 새로 만든다.
- **전면 통합(list/search/aggregate → 1개)** - 기각. 08-28에 신설·실측 검증된 툴을
  폐기하는 큰 수술로 PoC 단계의 변경 폭으로 과함.
- **B: 프리셋 전용 서버 조립 경로(툴 콜링 없이 1콜 답변 생성)** - 기각. §3-1 + §6
  (컨텍스트 선주입·병렬 호출)만으로 프리셋 질문이 사실상 "선주입 + 집계 툴 1콜 +
  답변"이 되어, 별도 경로를 만들 만큼의 이득이 남지 않는다.
- **모델 상향으로 해결** - 순서만 조정해 보류(§7). 상향은 산수·정렬 오류(②)와 스키마
  조합 정확도는 개선하지만 ①(회수 산수 불일치)은 지능 문제가 아니라 산수 문제라 못
  고친다. 왕복이 많은 현행 구조에서 모델만 올리면 시간 예산에 걸려 강제 답변이 더
  자주 터지는 역설도 있다.

## 4. 한계 체계 재도출

**뿌리(사용자 합의, 2026-08-31)**: 질문당 비용 천장 ~50원(토큰 예산 10만 상당),
총 시간 90초(SSE 스트리밍 전제 - 체감 대기는 "첫 반응까지 시간"으로 분리).

비용 산수 근거: flash 단가(입력 $0.30/M, 출력 $2.50/M, 환율 1,400원 기준) 기준 현행
전형 질문 ~7원, 최악(누적 6만) ~35원. 누적 토큰의 대부분은 데이터가 아니라 매 왕복
전체 대화록 재전송 오버헤드(시스템 프롬프트+툴 명세 ~4천 × 왕복 수)다 - §6의 왕복
절감이 곧 비용 절감이다.

| 한계 | 현행 | 재도출 | 도출 근거 |
|---|---|---|---|
| 누적 프롬프트 토큰 | 60,000 | **100,000** | 비용 뿌리(천장 ~50원) 직접 환산 |
| 벽시계 예산 | 55초 | **~85초** | 시간 뿌리 90초 - 마무리 여유 |
| 툴 호출 상한 | 8회 (1차 제약) | **24회 (안전망으로 강등)** | 정상 질문이 닿지 않는 폭주 방지선 |
| LLM 호출 상한 | 12회 | 12회 유지 | 왕복은 고정 오버헤드가 커서 시간·토큰이 먼저 끊는 게 정상 |
| 분당 요청 | 5회 | **10회** (사용자 지시) | 동시성 자원(스레드 2)·사고 방어 축 - 비용 뿌리와 독립 |
| 일일 요청 | 30회 | 유지 | 유저당 총비용 - 이번 논의 범위 밖 |
| 페이로드 상한들 | 30건·50건 등 | 유지 | 툴별 토큰 배분 - groupBy limit만 신설(§3-1) |

핵심 구조 변화: **1차 제약이 진짜 자원(시간·토큰) 둘이 되고 회수는 안전망으로
물러난다.** 싼 툴(get_author 등)을 회수 상한이 먼저 끊는 배신이 사라진다.

분당 제한의 존재 이유(기록): 챗 스레드 2개(큐 없음)를 한 유저가 독점하는 것 완화,
FE 버그·연타가 일일 쿼터를 태우는 사고 방지, 스크립트 남용 방어. 질문당 최대 시간이
늘어날수록 스레드 점유가 길어져 이 축의 존재 이유는 오히려 강해진다.

## 5. 예산 초과의 구조적 고지 (FE 협의 필요)

현행 고지는 프롬프트 지시("확인 못 한 부분은 솔직히 적으라")로 모델 성실성에 기댄다.
이중화한다:

- **구조 고지(신규)**: 응답에 `limitReached: "time" | "budget" | null` 필드를 추가
  (outcome 코드에서 도출). FE가 답변 하단 배지("시간 제한으로 일부 데이터만 확인한
  답변이에요")를 렌더링. **FE 계약 변경이라 협의 필요.**
- **문구 고지(현행 유지)**: TOOL_CAP_NOTE·TIME_BUDGET_NOTE 경로 그대로.

## 6. 왕복 절감

1. **툴 그레인(§3)** - 주 수단. 프리셋 1번이 10왕복 → 2~3왕복.
2. **병렬 툴 호출 유도** - 루프는 이미 한 응답의 복수 functionCall을 처리한다
   (BrandAiAgent가 turn.toolCalls() 순회 실행). 프롬프트에 "서로 의존하지 않는 조회는
   한 턴에 묶어 호출하라"를 추가하고 툴 설명에 배치 힌트를 넣는다(코드 무변경).
3. **브랜드 컨텍스트 선주입** - 서버는 요청 검증 시점(accountIds[0] 소유 검증)에 그
   브랜드 정보를 이미 조회한다. brandId·username·팔로워·수집기간을 시스템 프롬프트에
   선주입해 질문 100%에서 첫 왕복(list_brands)을 제거한다. list_brands 툴은 폴백으로
   유지.

셋을 합치면 전형 질문이 왕복 1~2회. 반복 오버헤드가 무너져 질문당 비용도 1/3~1/5.

## 7. 모델 설정 - 순서 합의

**A(구조) → eval(자) → 모델 설정(실험)** 순. 현행 gemini-2.5-flash + thinkingBudget 0
유지. A로 모델의 일이 "계산"에서 "해석·서술"로 줄어든 뒤, eval 골드셋으로
flash / flash+thinking / pro를 같은 질문 세트로 채점 비교해서 결정한다(감으로 고르지
않는다). thinkingBudget=0은 원래 품질 판단이 아니라 I7 버그 회피였음을 기록해 둔다.

## 8. eval 계획 (개요 - 상세 설계는 A 구현 합의 후)

- 정량 질문은 SQL로 정답 산출 가능 → 자동 채점 골드셋.
- 채점 두 겹: 최종 답변 수치 정확도 + **툴 호출 인자 정확도**(flash가 조합형 스키마를
  제대로 조합했는가 - 선택지 1의 확정 조건).
- 골드셋 시드는 ai_chat_logs 실사용 질문. 필수 포함 케이스: N > limit 기본값(예:
  "상위 30명"), 기간 비교(groupBy=month), 댓글 여론(배치), 프리셋 5종.

## 9. 구현 시 주의

- ai/ 패키지는 SSE 스트리밍 전환 세션과 같은 파일을 건드린다 - **구현 착수 전 그
  세션의 머지 상태를 확인하고 순서를 조율할 것**(같은 worktree
