# 성과 대시보드 고정 지연(약 7초) 원인 규명 — 회신

>
> 작성 2026-08-12 / 작성자 백엔드 / 수신 프론트엔드
> 원 요청서: "성과 대시보드 고정 지연(약 7초) 원인 규명 요청서" (2026-08-12)

## 요약

요청 1의 원인을 규명했고, 최대 지분을 이번 배포에서 제거합니다. **원인은 두 라우트가
요청마다 수행하는 전량 조립이고, 그 절반 이상이 어디서도 렌더되지 않는 댓글의 조회·매핑**
이었습니다. 요청 3(목록 recentComments 제외)이 곧 요청 1의 최대 해법과 같은 것으로
확인되어 함께 반영했습니다 — 다만 요청서의 당부대로 "페이로드 축소"가 아니라 "조립
단계에서 댓글 쿼리 자체를 생략"하는 방식이라, 응답이 줄어서 빨라지는 게 아니라 서버
내부 작업이 줄어서 빨라집니다.

여러분의 실측 방법론(크기-시간 무상관 증명, 대조군)이 정확했고 원인 좁히기에 결정적으로
기여했습니다. 감사합니다.

## 1. 원인 규명 결과 (요청 1)

여러분의 측정을 서버 안쪽으로 이어서 확인한 사실:

**① 서버 내부 시간 확정** — 운영 Prometheus(`http_server_requests`) 기준
`/contents` 평균 10.9초, `/comparison` 평균 9.3초. TTFB 7초는 네트워크·프록시가 아니라
전부 was 내부입니다(여러분의 판단과 일치).

**② "느린 쿼리 하나"는 없음** — 운영 postgres는 500ms 초과 문장을 자동 로깅하는데
(`log_min_duration_statement=500`), 대시보드 쿼리는 한 건도 없습니다. 고정 7초는
**500ms 미만짜리 쿼리 약 50개의 순차 합 + 자바 행 매핑**입니다.

**③ 구간별 분해(운영 당일 덤프 복원 + 실코드 하니스, 측정 계정과 동일한 유저)** —

| 구간 | 소요(로컬) | 비고 |
|---|---|---|
| 레거시(개인 추적) 조립 | 6ms | 무혐의 |
| 앱 DB(매핑·링크) | 1ms 미만 | 무혐의 |
| **브랜드 7계정 순회 tagged 조립** | **1,107ms** | 사실상 전부. 계정당 쿼리 5~6개 × 7회 순차 |
| └ 그중 댓글 조회+매핑 | **절반 이상** | 최대 브랜드 1개 415ms 중 237ms(45캡 후에도 18,860행) |
| 전체 조립 | 1,140ms | 운영 2코어 박스에서 약 7~9배로 늘어나 관측치와 정합 |

- 로컬(M칩)과 운영(2코어 공유 박스)의 절대값 차이는 CPU 성능·경합 차이입니다. 구조
  (고정비, 데이터 무관)와 비중은 동일합니다.
- 두 라우트가 같은 조립을 공유하므로 `/comparison`(7KB)도 같은 고정비를 냅니다 —
  여러분의 가설 2가 맞습니다.
- 가설 1(날짜 필터 미하강)도 맞습니다 — `uploadedFrom/To`는 조립 후 메모리 필터입니다.
  다만 그것이 고정비의 "원인"은 아니고(필터를 서버로 내려도 조립 전량은 그대로 돌므로),
  고정비의 원인은 조립 자체였습니다. 상세는 3절.
- 동시 호출 악화도 설명됩니다: 두 요청이 같은 조립을 각자 돌면서 monitoring 읽기 풀
  (max 3)과 2코어 CPU를 공유하기 때문입니다. 조립이 가벼워지면 경합도 같이 줄어듭니다.

## 2. 반영한 조치 (요청 3 = 요청 1의 최대 지분)

`GET /v1/performance-dashboard/contents`와 `/comparison`은 **댓글을 조회 단계에서 생략**
합니다(슬림 조립). `GET /v1/performance-dashboard/contents/:id` 단건은 요청서 그대로
댓글 포함을 유지합니다.

- 목록 응답의 `item.post.recentComments`는 **항상 빈 배열**, `commentsCollectedCount`는
  0이 됩니다. 필드 자체는 남아 있으므로(값만 빔) 파싱 호환은 유지됩니다.
- 스냅샷 유래 지표(`commentsTotal`·`commentsHidden`)와 나머지 필드·정렬·meta는 전부
  무변경입니다.
- 효과 실측(운영 덤프, 동일 계정): 조립 1,140ms → 545ms, **52% 절감**. 운영 고정 7초의
  절반 이상이 사라질 것으로 예상하며, 스테이징 배포 후 재실측해 공유하겠습니다.
- 순서 제약 없음(요청서 7절 확인대로): FE가 이 필드를 성과 대시보드에서 쓰지 않으므로
  백엔드 단독 배포입니다. 어댑터 단계 `recentComments` 폐기(8절)는 그대로 진행하셔도
  됩니다 — 배포 후에는 빈 배열이 와서 자연히 무의미해집니다.

## 3. 요청 2에 대한 답 (uploadedFrom/To)

확인 결과 여러분의 추정이 맞습니다: 날짜 필터는 SQL WHERE가 아니라 **조립 후 메모리
필터**입니다. 이는 의도된 설계였고(전량 조립 위에 컨트롤러가 필터·집계를 얹는 구조 —
statusCounts가 기간 필터와 무관해야 하는 계약 §7-1과도 맞물립니다), "필터를 좁혀도
빨라지지 않는" 현상의 직접 원인이 맞습니다.

다만 날짜 조건을 SQL로 내리는 것은 지금 반영하지 않습니다:

1. 고정비의 본체(댓글)는 이번에 제거되므로, 남는 조립 비용에서 날짜 필터로 아낄 수 있는
   몫이 크게 줄었습니다.
2. 여러분 스스로 5절에서 밝힌 대로, 현재 FE는 12개월 전량을 받아 클라이언트에서 거르는
   구조를 의도하고 있어 서버 필터 전환은 오히려 UX를 해칩니다.
3. `statusCounts`(기간 무관)·스냅샷 병합 등이 전량을 전제하고 있어, 부분 조회는 계약
   재설계가 필요한 큰 작업입니다.

슬림 배포 후 재실측 결과가 여전히 목표에 못 미치면, 그때 후속 카드(브랜드별 쿼리 7×5개의
크로스 브랜드 배칭 → ~10개, 필요시 조립 캐시)와 함께 다시 논의드리겠습니다.

## 4. 배포·확인 계획

1. develop 머지(PR #439) → 스테이징(dev-api) 배포 → 운영 승격.
2. 배포 후 백엔드가 운영 Prometheus로 두 라우트의 평균 처리 시간을 재확인해 회신합니다.
3. FE 재실측(2절과 같은 방법)을 한 번 부탁드립니다 — TTFB가 어디까지 내려왔는지가 후속
   작업(배칭·캐시) 착수 판단 기준입니다.
