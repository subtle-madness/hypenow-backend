# hypenow 상세 분석 — 시스템 설계

2026-07-12 (설계 세션 기록)
기준 기획: 상세 분석 확정안 Artifact (2026-07-10, https://claude.ai/code/artifact/696bd39e-0f53-4bc5-916e-d4adbf013658)

> 팀 협업·다른 세션 참고용 구조 문서. **상세 구현 계획은 각 태스크 착수 시점에 별도 작성**하고,
> 이 문서는 층 구조·태스크 경계·의존성만 고정한다.

## 1. 무엇을 만드나

콘텐츠 랭킹 MVP에 이어 붙는 세 가지:

1. **게시물 상세 드로어** — 랭킹에서 게시물 클릭 시 우측 드로어 (작성자 요약·성과·벤치마크 + 댓글 분석·감지·"왜 잘됐나")
2. **인플루언서 상세 페이지** — 드로어에서 진입 (정체성·성과·일관성·커머셜 + 페르소나·AI 브리핑)
3. **후보 관리** — 후보 저장, 상태(검토중/컨택 예정/협업 중), 메모. **필수 기능.**

## 2. 시스템 구조 (3-tier)

```
[크롤링 팀]  crawler  ──쓰기──▶  raw DB (crawler)     : 크롤링 원본. 이 작업의 고정 입력
[이 작업]    analysis ──읽기── raw DB
                      ──쓰기──▶  analysis DB          : 분석 결과 = was가 보여줄 데이터
[이 작업]    was      ──읽기── analysis DB ──▶ 클라이언트(celfit-front)
                      ──읽기/쓰기──▶ 서비스 데이터(app 스키마) : 로그인·후보 관리 등
```

| 층 | 소유 | 저장소 | 책임 |
|---|---|---|---|
| crawler | 이 작업 범위 밖 | raw DB | Apify 수집. **이 작업에서 건드리지 않는 고정 입력** |
| analysis | 이 작업 | analysis DB | raw를 읽어 분석 결과를 만들어 채움 (비LLM 집계 + LLM 분석 모두) |
| was | 이 작업 | analysis DB만 접근 | REST API 서빙 + 서비스 기능(로그인·후보 관리) — 쓰기는 app 스키마에만 |

- **미러** = analysis 층의 핵심 동작. raw DB에 정의한 분석 뷰(`analytics.*`)를 실행해 그 결과를
  analysis DB의 평탄 테이블로 채우는 배치(`MaterializationService`, 뷰당 drop→create→전량 insert).
  레플리카나 인프라가 아니라 **tier 2→3 경계 그 자체** — 뷰는 DB를 못 넘으므로 이 잡이 반드시 존재한다.
- 두 DB는 지금 **한 Postgres 인스턴스**(포트 5433)에 논리 분리만 되어 있고, 부하를 보고 물리 분리를
  결정한다. was가 analysis DB만 보는 규율을 지키면 물리 분리는 설정 변경으로 끝난다.
- 데이터 신선도 = 마지막 미러 배치 시점. 갱신 주기는 미결(§6).

## 3. 층을 관통하는 설계 결정

1. **최근 N개 윈도우** — 모든 계정 단위 지표는 "계정별 최신 게시물 N개(기본 12)"만 잘라 계산한다
   (`row_number() OVER (PARTITION BY owner ORDER BY uploaded_at DESC) <= N`).
   재크롤링이 누적돼도 계정 간 비교가 공정해지고, UI 각주 "최근 N개 기준"이 이 한 곳을 가리킨다.
   N은 `app_setting` 키로 런타임 조정(재배포 불필요).
2. **LLM도 분석 층의 일부다.** 별도 트랙이 아니라 "raw를 읽어 분석 결과를 analysis DB에 채우는 일"의
   한 종류. 화면별 태스크 안에 비LLM/LLM이 나란히 들어간다(§4). LLM 실행 코드가 어느 모듈에 사는지는
   태스크 F에서 확정(기존 Plan 3 문서의 "crawler 모듈 소속" 결정은 이 모델과 어긋나서 재검토 대상).
3. **was의 쓰기는 서비스 데이터(로그인·후보 관리 등 일반 앱 데이터)로 한정한다.** 서비스 데이터는
   분석 결과와 스키마로 분리(analysis DB 내 `app` 스키마)하고 물리 분리를 고려한다. 분석 결과에는 쓰지 않는다.
4. **표기 원칙(확정안)** — 표본 크기가 약점으로 안 보이게 개수 대신 %·라벨을 쓰되, 백엔드는 항상
   `sampleSize` 원값을 제공하고 노출 여부는 프론트가 정한다. 비율은 분자·분모 원값을 함께 내려
   프론트가 분모(스팸 포함/제외 등)를 전환할 수 있게 한다.

## 4. 태스크 분해와 의존성

상세 구현 계획은 각 태스크를 잡을 때 그 자리에서 작성한다. 여기서는 경계와 의존만 고정.

**공통 기반**

| # | 태스크 | 내용 |
|---|---|---|
| A | 집계 공통 | 최근 N개 윈도우 뷰 + `app_setting` 키 정리(윈도우 크기·변동성/모멘텀 임계값) |
| F | LLM 공통 | LLM 호출 골격(모델 설정·결과 저장·멱등·비용 가드) + **정확도/비용 스파이크**(실 댓글 골드셋, opus vs haiku). 모듈 소속(§3-2)도 여기서 확정 |

**게시물 드로어 분석 (analysis 층)**

| # | 태스크 | 내용 | 의존 |
|---|---|---|---|
| B1 | 비LLM 집계 | 작성자 요약(히트율·평균 ER)·성과·벤치마크 3종 뷰 + 미러 | A |
| B2 | 댓글 LLM | 감성 4분류(스팸 통합)·키워드·구매의도 → 집계 뷰 + 미러 | F |
| B3 | 콘텐츠 LLM | 브랜드/제품/유통사 감지 + 콘텐츠 속성(캡션 기반) + "왜 잘됐나" 생성 | F, B2(집계 수치를 프롬프트 입력으로) |

**인플루언서 상세 분석 (analysis 층)**

| # | 태스크 | 내용 | 의존 |
|---|---|---|---|
| C1 | 비LLM 집계 | 정체성·성과·일관성·커머셜 뷰 + 1:N 자식 뷰(조회수 시계열·협업 이력) + 미러 | A |
| C2 | 계정 LLM | 광고유형 분류·페르소나·AI 브리핑·적합성 태그 | F, C1(수치 입력), B3(감지 결과 재사용) |

**was (서빙 층)**

| # | 태스크 | 내용 | 의존 |
|---|---|---|---|
| D | 게시물 드로어 API | `GET /api/posts/{shortCode}` — 블록 구조 응답 | B1 (B2·B3 결과는 additive 확장) |
| E | 인플루언서 상세 API | `GET /api/influencers/{username}` | C1 (C2 additive) |
| G | 서비스 데이터 | `app` 스키마 신설 + 후보 저장·상태·메모 + was 쓰기 API (로그인 등의 기반) | **독립** |

```
A ─→ B1 ─→ D          F ─→ B2 ─→ B3 ─→ C2
 └─→ C1 ─→ E          (B3·C2 결과는 D·E 응답에 additive)
G: 독립 (아무 때나)
```

권장 착수 순서: **A → B1 병렬로 F(스파이크)** — LLM이 최대 리스크라 스파이크를 일찍. G는 틈에 끼워 넣는다.

## 5. 확정된 사실·제약 (설계 전제)

- **조회수 출처**: raw의 `videoPlayCount`(인스타 공개 재생수, 폴백 `videoViewCount`).
  비로그인 GraphQL로도 취득 가능함을 실측 확인(2026-07-10). **피드 게시물은 항상 NULL** —
  평균·히트·확산배율 계산에서 NULL 처리 규칙이 항상 따라붙는다.
- 성과는 업로드 +3일 **단일 스냅샷**(시계열 아님 → 추이 그래프는 확정안에서 제외됨).
- **댓글은 게시물당 최대 50개** 수집(`aggregate.comments-per-post`). 목업의 "214개 분석"은 도달 불가 —
  드로어 카피 정정 필요(§6).
- LLM 댓글 분류 실측 비용(게시물 1,000건, 동기·무캐시·무배치): **Opus ≈ $61 / haiku ≈ $12.2**.
  Batches(50% 할인) 도입 시 절반. 모델 선택은 F 스파이크 결과로.
- 분석 뷰 검증은 SQL 하니스(`analytics/test/run.sh`, 더미 시드 + BEGIN/ROLLBACK 격리) 컨벤션을 따른다.

## 6. 미결 — 팀 결정 필요

| 항목 | 상태 |
|---|---|
| 드로어 댓글 카피 | "214개 분석" 불가 → "최근 최대 50개 댓글 분석"으로 정정 or 상한 상향+비용 재승인 |
| LLM 모델 | F 스파이크(정확도 vs 비용) 결과로 결정. 기본값은 opus |
| LLM 코드의 모듈 소속 | analysis 쪽 제안(§3-2), F에서 확정 |
| 미러 갱신 주기 | 현재 수동 1회 실행. 크론/파이프라인 후단 자동화 여부와 주기 |
| 서비스 데이터 상세 | `app` 스키마 구성·로그인 방식은 G 착수 시 설계 |
| 감성 비율 분모 | 원값 제공으로 프론트 전환 가능하게 하되, 기본 표기는 전체(스팸 포함) 기준 |
