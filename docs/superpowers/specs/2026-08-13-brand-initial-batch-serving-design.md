# 브랜드 초기 수집 — 완결 배치 서빙 설계

> 상태: 🟢 활성 · 미구현(설계 합의만) · FE 회신본은 별도 전달(레포 미보관)

## 배경 — 왜 바꾸나

08-12 스트리밍 개정으로 등록 → ready가 8분 24초 → 1분 30초로 줄었지만, 그 ready는
**열거만 끝난 상태**다. 게시자 프로필·댓글은 그 뒤 비동기로 붙으므로 FE는 작성자 이름도
댓글도 없는 카드를 먼저 받는다. FE가 "반쯤 빈 카드" 방어를 코드에 계속 들고 있는 이유고,
2026-08-13 요청서로 **완결된 것만 내려달라**는 계약 변경이 들어왔다.

사용자 결정(2026-08-13): 완결 단위 = **게시물 단위 정산**, 방출 단위 = **열거 페이지(21건) 배치**,
완주 신호 = **기존 `collectionCompletedAt` 재사용**(status에 `end` 값 추가하지 않음).

### 근거 실측 (2026-08-13, 운영 서버 · 브랜드 5개 · 470여 콜)

전부 운영과 동일한 조건(워커 풀 병렬, 실브랜드 태그 열거 첫 페이지)에서 읽기 전용 프로브로
측정했다. **댓글 엔드포인트 레이턴시는 이 측정이 최초**다(08-07 스펙의 "미실측 한계" 해소).

| 항목 | 값 |
|---|---|
| 태그 열거 1페이지(21건) | 4.0 ~ 6.8초 (p50 ~5.0) |
| 게시자 프로필 `/v2/user/by/id` | p50 1.59초 / p90 2.59초 |
| 댓글 `/v2/media/comments` | p50 ~1.5초 — **표본 54건 전부 1콜로 종료**(3페이지 상한 미도달) |
| 게시자 404율 | **2.0%**(99건 중 2건) — 실존 계정에서 발생, **재시도 1회로 2/2 복구** |
| 게시자 5초 초과 | **1.0%** — 최대 21초, 재시도 3회 전부 실패한 사례 있음 |
| 첫 페이지 21건 완결(워커 10) | **약 10초** |
| 첫 페이지 21건 완결(워커 6) | 14 ~ 16.5초, 꼬리 발생 시 30초 |

두 가지가 설계를 갈랐다.

1. **완결까지 해도 지금 ready보다 빠르다** — 첫 페이지 완결 ~10초 < 현행 ready 1분 30초.
   완결성과 속도가 상충하지 않는다.
2. **`by/id`의 404는 결정적 부재가 아니다** — `JdkHikerHttp`가 "404는 다시 쏴도 결과가 같다"를
   전제로 즉시 전파하는데, 실측은 2/2 복구로 이를 반증했다. 완결 서빙에서는 이 전제가 곧바로
   구멍이 된다(그 게시물이 영영 안 나온다).

## 설계

### 1. 완결 판정 — `brand_tagged_post.enriched_at`

게시물별 "보강 정산 완료" 시각 컬럼을 신설한다. 성공이든 재시도 소진이든 **더 기다릴 이유가
없어진 시점**에 찍는다.

```sql
ALTER TABLE brand_tagged_post ADD COLUMN enriched_at timestamptz;
```

판정 기준을 "게시자·댓글이 실제로 있는가"가 아니라 **"보강 시도가 끝났는가"**로 잡는 것이
핵심이다. 실측 404 2%·타임아웃 1%가 존재하는 이상 데이터 유무를 기준으로 하면 그 게시물은
영구 미노출이 된다. `enriched_at`은 "서빙해도 된다"이지 "완벽하다"가 아니다 — 빈 필드는
게시자 stale·댓글 워터마크가 다음 스윕에서 자동으로 채운다.

### 2. 방출 — 페이지 배치

`sweepCore`의 서빙 콜백을 "서빙 창 커버 시 1회"에서 **"페이지마다"**로 바꾼다.

- 페이지 적재 직후 그 21건을 enrich → 완료 시 그 21건에 `enriched_at` 마킹
- **첫 페이지 배치 완료 = `markServing`**(FE ready). 현행 "30일 커버" 기준을 대체하므로
  설정 `monitoring.brand.serving-window-days`와 그 판정 로직은 **제거**한다
- 태그 게시물이 0건이거나 첫 페이지가 편입 컷에 전부 걸려 정산할 게 없으면, 현행 규칙을
  계승해 **루프 종료 시점에 `markServing`**을 부른다 — 그래야 태그가 없는 브랜드가 `collecting`에
  영구히 갇히지 않는다
- 완주 시 `touchSwept`(3컬럼)는 현행 그대로

콜백 시그니처는 "그 시점까지 누적된 목록"이 아니라 **그 페이지분**을 넘긴다 — 현행은 누적
리스트를 넘기고 수신자가 코드 집합으로 잔여를 걸러내는데, 페이지 배치에서는 그 필터가
불필요해진다(`BrandRegistrationService.runBackfillSafely`의 `earlyCodes` 제거).

### 3. 일일 스윕도 같은 배치를 탄다

현행 `sweep()`은 "열거 전량 → 보강 전량"이라, 새 규칙에서는 스윕이 새로 적재한 게시물이
보강 완료 전까지 목록에서 사라진다. `sweep()`도 페이지 배치 콜백을 쓰도록 통일한다.

부작용: 스윕이 도는 동안 신규 게시물의 노출이 그 페이지 보강만큼 늦어진다(초 단위). 현행은
적재 즉시 노출이었다 — FE 회신본 §3-5로 통지했다.

### 4. 재시도·정산 규칙

| 상황 | 처리 |
|---|---|
| 게시자 404 | **1회 재시도**(실측 복구 2/2). 소진 시 게시자 없이 정산 |
| 게시자 타임아웃(15초 초과) | **재시도 없이 즉시 포기** — 3회 태워도 실패하고 워커만 45초 묶인다 |
| 댓글 실패 | 현행 재시도 그대로. 소진 시 댓글 없이 정산 |
| 댓글 미완주(중간 페이지 실패) | 받은 분 보존 + 워터마크 유지(현행) + 정산은 진행 |

404 재시도는 전송 계층(`JdkHikerHttp`)이 아니라 **보강 단계의 `by/id` 호출에만** 건다.
전송 계층의 "404 = 결정적 부재" 전제는 `by/username`·게시물 단건에서는 여전히 맞고, 거기까지
재시도를 켜면 계정 삭제 판정(`InfluencerStatus.DELETED`)이 그만큼 늦어진다.

정산이 재수집 포기를 뜻하지 않는다는 점이 규칙의 안전판이다 — 워터마크·stale 판정이 그대로
남아 다음 스윕이 빈 곳을 채운다.

### 5. was 목록 게이트

`BrandReadRepository`의 태그 게시물 조회에 `AND enriched_at IS NOT NULL`을 더한다.
직접 등록 게시물(`brand_direct_post` 경로)은 별도 파이프라인이라 게이트 대상이 아니다.

`meta.counts`·`meta.total`은 게이트 적용 후 기준이다 — 수집 중에는 폴링마다 증가한다.

### 6. 완주 신호 — 기존 필드 재사용

`collectionCompletedAt`(← `brand_account.backfill_completed_at`)은 이미 `touchSwept`가
**전량 완주 시점에만** 찍고 `COALESCE`로 최초 완주 시각을 보존한다. 조기 서빙 마크는 이 컬럼을
건드리지 않는다. 따라서 **신규 필드도, status `end` 값도 만들지 않는다.**

바꾸는 것은 하나다 — `expandWindow`에 `backfill_completed_at = NULL`을 추가한다. 현재는
"완주 이력 있는데 `last_swept_on`이 빔 = 확장 중"을 was가 판별하는 재료로 **의도적으로 보존**
중이라, 그대로 두면 FE 폴링이 확장 중에 즉시 멈춘다.

그 결과 `BrandAccountAssembler`의 2번 분기(`last_swept_on` null + `backfill_completed_at` 있음
→ `collecting`)가 도달 불가가 된다 → **제거**한다. 확장 중 상태는 `ready` +
`collectionCompletedAt == null`이 되고, 이게 08-12 결정("확장 중 collecting 우선")을 뒤집는
지점이다. 뒤집는 근거는 FE가 진행 판정을 status가 아니라 필드로 옮기기로 했다는 것 —
status는 `collecting|ready|error` 3값 계약으로 고정된다.

성과 대시보드 `covered`는 영향 없다: `backfillCompletedAt != null && lastSweptOn != null`이라
확장 중에는 현재도 이미 false다.

### 7. 동시성

| 설정 | 현행 | 변경 |
|---|---|---|
| `monitoring.brand.enrich-concurrency` | 6 | **10** |
| `brandEnrichExecutor` | 단일 스레드(하드코딩) | **2**(설정화) |
| `monitoring.brand.backfill-concurrency` | 2 | 유지 |

enrich executor 증설이 이번 전환의 필수 조건이다 — core는 2병렬인데 보강이 단일 스레드라,
연속 등록 시 두 번째 브랜드의 보강이 첫 브랜드 보강 완주를 통째로 기다린다. 완결 서빙
이전에는 `markServing`이 열거만으로 ready를 열어줘서 이게 안 아팠지만, 이제는 **두 번째
브랜드의 화면이 분 단위로 비어 있게 된다.**

워커 증설은 executor 증설의 부수효과 상쇄분이다 — 워커 풀은 공유 빈이라 executor 2면
브랜드당 실효 워커가 반감한다(6 → 3). 10으로 올려야 브랜드당 5를 유지한다.

전역 동시 콜 최악은 9 → **13**(워커 10 + 스윕 core 1 + 등록 core 2). 08-12 램프 실측의
"동시 12부터 꼬리 15~22초 상시화"를 근거로 이 구간을 위험하다고 봤으나, 08-13 실측에서
워커 6/8/10 어느 레벨에서도 5초 초과 콜이 증가하지 않았다(정상 브랜드 세 레벨 모두 0건).
관측된 꼬리는 동시성이 아니라 특정 콜에 산발적으로 붙었다.

## 마이그레이션·배포 순서

`V20260813113000__brand_tagged_post_enriched_at.sql` (monitoring, UTC 채번):

```sql
ALTER TABLE brand_tagged_post ADD COLUMN enriched_at timestamptz;
UPDATE brand_tagged_post SET enriched_at = COALESCE(last_crawled_at, first_seen_at);
```

**기존 25,759행 백필은 필수다.** 빠뜨리면 게이트 도입 순간 전 브랜드 목록이 통째로 빈다.
이미 보강이 돌았던 행들이라 정산 완료로 보는 것이 사실에 맞다.

배포 순서는 **monitoring(컬럼 + 백필) → was(게이트)**. 역순이면 was가 없는 컬럼을 조회해
브랜드 목록이 전면 500이다. ADD COLUMN nullable이라 expand-contract 위반은 없다.

## 실패 시나리오

- **첫 페이지 보강 실패** → `markServing` 미호출 → `collecting` 유지 → `backfill_error`(현행 동일)
- **N번째 페이지 실패** → 1~N-1 페이지는 이미 정산·서빙 중. 완주 미도달로 `collectionCompletedAt`
  null → FE 폴링 계속 → 다음 스윕이 백스톱
- **완주 전 사망** → `collectionCompletedAt`이 다음 새벽 스윕까지 null. FE는 벽시계 상한을
  폐기했으므로 **최대 하루 60초 간격 폴링**(열린 대시보드당 ~1,400요청/일). FE 회신본 §3-8로 통지

## FE 계약

status 값 공간은 불변(`collecting|ready|error`), 신규 필드 없음. 프론트가 대비해야 할 변화
9건은 FE 회신본에 정리했다(레포 미보관). 그중 코드 변경이 실제로 필요한 셋:

1. **ready 시점의 데이터 양** — 30일치 수백 건 → 첫 배치 21건(시각은 1분 30초 → ~10초)
2. **폴링 중 목록 순서 흔들림** — 태그 열거는 태그된 시점 순이고 `taken_at`은 비단조라,
   첫 21건이 업로드 최신순 상위 21건이라는 보장이 없다. 나중 폴링분이 기존 항목 위로 끼어든다
3. **"반쯤 빈 카드" 방어 유지** — 게시자 404 2%·타임아웃 1%로 게시자 없는 카드가 나온다

## 테스트

기존 monitoring 관용구(가짜 `HikerHttp`)로:

1. 페이지 배치 콜백이 페이지마다 1회 호출되고, 그 페이지분만 인자로 온다
2. 첫 페이지 배치 완료 시 `markServing` 1회 + `last_swept_on` 미변경
3. 게시자 404 → 1회 재시도 후 성공하면 프로필 저장, 실패해도 `enriched_at`은 찍힌다
4. 댓글 미완주(중간 페이지 실패) → 워터마크 미전진 + `enriched_at`은 찍힌다
5. N번째 페이지 실패 시 1~N-1의 `enriched_at` 보존 + `backfill_error` 기록
6. 일일 스윕 경로도 페이지 단위로 `enriched_at`을 찍는다
7. `expandWindow`가 `backfill_completed_at`을 null로 리셋한다
8. (was) 목록 API가 `enriched_at IS NULL` 게시물을 제외하고 `meta.counts`도 제외 기준이다
9. (was) `BrandAccountAssembler` — 확장 중(last_swept_on null · backfill_completed_at null ·
   last_swept_at 있음)이 `ready`로 나온다

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| **게시물 1건 단위 방출** | 꼬리 격리는 우월하다(꼬리 케이스에서 첫 화면 45초 → 15초). 그러나 FE 폴링이 5~60초 백오프라 정상 구간에서 사용자 체감 차이가 0이고(둘 다 t≈15초 폴링에 잡힘), enrich 루프를 "게시자 전체 → 댓글 전체" 2단계 조인에서 게시물당 1태스크로 재구성해야 하며 게시자 전역 dedup·댓글 게이트의 전역 최적화가 부분적으로 깨져 완주가 ~10% 느려진다 |
| **`collectionStatus`에 `end` 값 추가** | FE가 `=== "ready"` 분기 9곳을 근거로 거부. TypeScript가 못 잡고 런타임 빈 화면으로만 드러나며, 백엔드 선배포 시 실사용자 화면이 깨진다. 완주 신호는 기존 필드로 이미 표현 가능하다 |
| **신규 필드 `backfillCompletedAt` 신설** | `collectionCompletedAt`이 이미 전량 완주 시점에만 찍힌다 — 의미가 같은 필드를 응답에 둘 두는 셈 |
| **전송 계층에서 404 재시도 전면 승격** | `by/username`·게시물 단건의 404는 여전히 결정적 부재고, 재시도를 켜면 계정 삭제 판정이 그만큼 늦어진다. 실측으로 flaky가 확인된 `by/id`에만 건다 |
| **워커를 12 이상으로** | 08-12 램프 실측상 동시 12부터 꼬리 15~22초 상시화 → 운영 `request-timeout` 15초 초과 → 재시도로 콜 과금 2~3배 |

## 비범위

- 댓글 빈 배열의 "0건 vs 수집 실패" 구분 필드 — 사용자 결정으로 이번 범위 제외(FE 회신본 §3-4에 한계로 명시)
- 해시태그 게시물 표면(별도 엔드포인트, 변경 없음)
- 게시물 목록 API 페이지네이션(현행 전량 응답 유지)
- FE 폴링 간격·백오프 정책(프론트 소관)
