# Grafana 대시보드 개편 — Datadog식 운영 탭 + 비즈니스 흐름

> 상태: 🟢 활성

## 목표

기존 대시보드 9장(HypeNow 6 + 브랜드 모니터링 2 + UI 전용 1)을 **Datadog식 관심사 탭 4장
(`$module` 필터로 모듈 전환)** + **비즈니스 흐름별 대시보드**로 재편성한다.
패널은 재활용이 기본이고, 체계만 새로 잡는다.
(v1 "모듈별 대시보드 4장" 설계는 08-25 사용자 피드백으로 탭+필터 방식으로 대체 —
모듈마다 장을 만들면 같은 패널이 4벌 복제되고, 탭이면 1벌로 모듈을 갈아끼운다.)

## 폴더·대시보드 구성

```
📁 HypeNow            ← 진입점만 남김 (json/)
   └ 홈 — 지금 정상인가   (유지, 신호등)
📁 운영                ← 신설 (json-ops/) — 탭 4장, 각 장 상단 $module 드롭다운
                          (custom: crawler,analytics,was,monitoring) + 태그(hypenow-ops)
                          기반 탭 링크 바(includeVars — 탭 이동 시 선택 모듈 유지)
   └ 운영 / 인프라        (호스트 row는 모듈 무관, 컨테이너 row는 name=~".*-${module}-[0-9]+")
   └ 운영 / 메트릭        (요청 reqps·p95·5xx / JVM 힙·GC·Hikari / 외부 콜 — job="$module")
   └ 운영 / 로그          (ERROR·WARN 로거별 추이 / 응답코드·예외클래스 원인 축 / 탐색 — service="$module")
   └ 운영 / 모니터링       (alertlist + 잡·크론 신선도 + 오늘 처리량 — 잡 타일은 SQL이 모듈
                           고유라 필터 무관, 제목에 담당 모듈 명시)
📁 비즈니스 흐름        ← 신설 (json-flow/)
   └ [흐름] 콘텐츠 파이프라인  (탐색→수집→분석→서빙 — 기존 '탐색' 흡수)
   └ [흐름] 브랜드 모니터링    (스윕→적재→광고 판정→알람 — 기존 [브랜드] 2장 통합·재배치)
   └ [흐름] 경쟁사 모니터링    (기존 이관)
   └ [흐름] 비용·외부 의존     (Hiker — 기존 이관)
```

- 프로비저닝: `dashboards.yaml`에 provider 2개 추가(`json-ops/` → "운영", `json-flow/` → "비즈니스 흐름").
  디렉토리명 영문 유지(NFC/NFD 회피 — 기존 json-brand 결정 준수), 폴더명은 yaml에서 한글 지정.
- 알려진 공백(백로그): 프로메테우스 스크레이프는 was·monitoring만 — crawler·analytics는 메트릭 탭
  JVM·요청 패널이 무데이터(noValue 문구로 명시). 스크레이프 추가는 별도 작업.
  외부 콜 지표(external_call_seconds)는 monitoring만 계측. 응답코드 추이는 로그 문구
  "Hiker NNN" 의존 — HikerClient 로그 포맷 변경 시 동반 수정.
- 08-25 브랜드 모니터링 posts 서빙 장애(타 세션 공유)에서 확인된 관측 공백 2건:
  ① was 엔드포인트별 p95 패널 부재 — **메트릭 탭 "응답 p95 (uri별)"(module=was)이 해소**
  (실측: posts 엔드포인트 p95 30s로 표시. 단 30s는 히스토그램 최대 버킷 포화 — 실제 96s+도
  30s로 눌려 보였다 → 이 브랜치에서 was http.server.requests·monitoring external.call의
  maximum-expected-value를 120s로 확장, 배포 후부터 실값 표시).
  ② "200 흘리다 클라이언트 abort" 실패 양상은 5xx 스탯 어디에도 안 잡힘 — 엣지(caddy-access)
  로그의 duration 기반 "느린 응답" 패널이 개선 후보(백로그).
- 퇴역: 기존 `인프라`·`요청 추적`은 운영 탭에 흡수, `탐색`·`경쟁사`·`Hiker`·`[브랜드]` 2장은 흐름
  폴더로 이관·통합. UI 전용 "[브랜드] 수집 현황"은 필요 패널만 흐름 대시보드에 재현. 기존 uid는
  살아있는 알림·링크가 참조할 수 있으므로 **퇴역 대시보드 삭제는 전 장 완성 후 별도 확인을 거쳐
  마지막에**.

## 작업 방식 — 운영 실데이터 + 작업용 사본 (사용자 결정)

목 시드 하니스 대신 **운영 Grafana(ssh 터널 localhost:3001)에서 실데이터로 반복**한다 —
실데이터라야 밀도·임계값 감이 잡힌다는 사용자 판단. 근거: `allowUiUpdates: false`가 덮는 건
프로비저닝 대상뿐, UI에서 새로 만든 대시보드는 Grafana DB에 저장돼 재기동에도 살아남는다.

1. 운영 Grafana에 **`🚧 개편 WIP` 폴더**를 만들고 작업 중 대시보드는 전부 거기에만 둔다.
2. 대시보드 JSON은 **레포 파일로 작성**(최종 PR 산출물)하고, 같은 내용을 브라우저 로그인 세션으로
   Grafana API(import)에 밀어 WIP 폴더에 반영한다. **화면에 보이는 것 = 커밋될 파일** 유지.
3. 사용자가 실데이터로 보면서 피드백 → JSON 수정 → 재반영 반복. 장 단위로 확정.
4. 확정 즉시 커밋 → PR → CD(develop→staging→main)로 운영 반영 → 프로비저닝본 확인 후 WIP 사본 삭제.

가드레일:
- **쿼리 비용**: 운영 postgres는 2코어 서버. 새 패널 쿼리는 시간 범위 조건·LIMIT 필수,
  무거운 집계는 패널로 열기 전 먼저 비용을 확인한다.
- **`grafana_reader` GRANT**: 새 컬럼 참조 패널의 permission denied는 GRANT 누락 신호 —
  발견 즉시 GRANT 런북(deploy/README)에 추가해 PR에 동봉한다.
- 시간 판정은 KST 규약 유지(`(now() AT TIME ZONE 'Asia/Seoul')::date`).

## 이관 원칙

- **모듈 대시보드 = "이 프로세스가 건강한가"**: JVM·잡 크론·에러 로그·큐 적체 등 런타임 관점.
- **흐름 대시보드 = "이 업무가 흘러가고 있나"**: 단계별 처리량·전환·잔여·신선도, 모듈 경계 무시.
- 같은 지표가 양쪽에 나와도 됨(관점이 다르면 중복 아님).
- 데이터소스 uid는 운영과 동일 유지(`hypenow-analysis-pg`·`hypenow-monitoring-pg`·
  `hypenow-prometheus`·`hypenow-loki`) — JSON 무수정 이식.
