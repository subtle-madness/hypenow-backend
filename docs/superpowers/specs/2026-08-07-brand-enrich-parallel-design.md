# 브랜드 보강(enrichment) 제한 병렬화 — 설계

> 상태: ✅ 구현/반영됨 (2026-08-07 — #363 단계식 ready 후속. ready ~30초는 해결됐지만 보강 총
> 시간 ~3분이 그대로인 문제를 동시 6 병렬화로 단축하는 설계. 동시성 상한은 운영 실측으로 결정)
>
> 정정(2026-08-07, 구현 리뷰): §2의 전역 동시 콜 상한을 7 → **8**로 사실 정정. 스윕과 등록
> 백필이 겹치면 core 스레드가 1개가 아니라 2개(스윕 executor + 등록 backfill executor)라
> 워커 6 + 2 = 8이 맞다. 스펙 내용 불변 원칙의 예외 — 서술 변경이 아니라 산식 오류 정정.

## 0. 한 줄 요약

보강(게시자 프로필+댓글) 콜 수십 개가 단일 스레드 순차 HTTP 왕복(콜당 ~1.5초)이라 총
~3분이 걸린다 — enrich **내부**만 공유 워커 풀(고정 6스레드)로 병렬화해 **~30초**로 줄인다.
브랜드 단위 큐잉(backfill/enrich executor 각 단일 스레드)과 게이트·격리·백스톱 의미는 불변.

## 1. 근거 — 운영 실측 (2026-08-07)

`deploy-monitoring-1` 컨테이너에서 HikerAPI 프로필 엔드포인트로 순차 6콜 / 동시 4콜×3웨이브 /
동시 8콜×2웨이브(총 34콜, 전부 상이한 공개 계정) 실측:

| 조건 | 콜별 레이턴시 | 웨이브 벽시계 | 429/오류 |
|---|---|---|---|
| 순차 ×6 | 1.2~2.9s (중앙값 ~1.4s) | 11s | 없음 |
| 동시 4 | 1.1~2.1s | 각 2s | 없음 |
| 동시 8 | 1.1~2.4s | 각 2s | 없음 |

- 동시 8까지 콜별 레이턴시 열화·스로틀·429 전무 → 기존 "동시 2 = 부하 완충"은 Hiker 보호
  효과가 사실상 없었다. 병목의 정체는 **콜당 ~1.5초 × 순차 실행**.
- 미실측 한계: 댓글 엔드포인트(`/v2/media/comments`)는 직접 실측하지 않았다. 같은 게이트웨이라
  다를 가능성은 낮고, 만에 하나 순간 과부하면 기존 재시도+선형 백오프(JdkHikerHttp)가 콜
  단위로 흡수한다.
- 동시성 상한 6은 사용자 결정(2026-08-07): 실측 무저항 한계 8에서 안전 마진을 둔 값.

## 2. 구조

- **`brandEnrichWorkerPool` 빈 추가**(BrandBackfillConfig) — 고정 6스레드(데몬), 설정 키
  `monitoring.brand.enrich-concurrency:6`.
- **공유 빈인 이유(전역 상한)**: 매일 스윕과 등록 보강이 겹쳐도 전역 동시 Hiker 콜이
  워커 6 + 스윕 core 1 + 등록 core 1 = **최대 8**로 묶인다(실측 무저항 한계 8과 동치).
  호출부별 풀 생성이면 겹칠 때 12~14까지 올라가 실측 범위를 벗어난다.
- 기존 executor 2개(brandBackfillExecutor/brandEnrichExecutor, 각 단일 스레드)는 **그대로** —
  브랜드 단위 큐잉·순서 보장 유지. 병렬화는 한 브랜드의 enrich 내부에서만.

## 3. 동작 변경 — BrandCollectService.enrich 내부만

- `ensureAuthors`: stale 판정 쿼리(1회) 그대로, 게시자별 `fetchAuthorProfile`+upsert를 풀에
  제출 후 전체 대기.
- `collectCommentsGated`: 저장값 조회(1회) 그대로, 게이트 통과 게시물별 `fetchComments`+적재+
  워터마크 갱신을 풀에 제출 후 전체 대기.
- 게시자·게시물 단위 try/catch 격리는 태스크 안으로 이동 — 실패 전파 규칙 불변(로그만,
  나머지 태스크 계속). 게이트 로직·워터마크·수집 판정 불변.
- enrich()는 자기 스레드(스케줄러 또는 brand-enrich)에서 제출·대기만 하므로 중첩 제출 없음
  → 고정 풀 데드락 없음.

## 4. 효과·리스크

- 등록: ready ~30초 → 보강 완료 **~1분**(현재 ~3.5분). 매일 스윕 총 시간도 같은 비율 단축.
- 실패 시: 콜 단위 재시도+백오프 → 그래도 실패하면 종전과 동일하게 게시자 stale·댓글
  워터마크 백스톱이 다음 스윕에 자동 재시도. backfill_error 규칙 불변(보강 실패는 미기록).

## 5. 테스트

- 추가 1개: 래치로 "동시 실행이 실제로 일어나되 상한(풀 크기)을 넘지 않는다" 검증.
