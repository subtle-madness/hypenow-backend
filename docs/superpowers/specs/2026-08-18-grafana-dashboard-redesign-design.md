# 그라파나 대시보드 개편 — 홈 신호등 + 기능축 재편 설계

> 상태: 🟢 활성 · 설계 확정(2026-08-18), 구현 계획 별도

## 1. 동기

기존 대시보드 3장(서비스 현황 / 에러 / API 성능)은 **데이터소스 축**(analysis DB / Loki /
Prometheus)으로 갈라져 있고 진입점이 없다. 사용자는 정기 점검·장애 대응·지표 확인 세 목적으로
같은 화면들을 돌려쓰고 있어 "뭘 먼저 봐야 할지 모르겠는" 노이즈가 생겼다.

노이즈의 실체 두 가지(2026-08-18 운영 실측):

- **데이터 밀도 불일치.** 가입 53명·다이제스트 20건·문의 6건 규모의 데이터를 일별 timeseries로
  그려서, 패널 절반이 빈 판에 점 몇 개다. 이 규모에서는 시계열이라는 형식 자체가 맞지 않는다.
- **실재하는 축의 부재.** Hiker 콜 30일 49,756건(= 돈, 4xx도 과금)과 monitoring DB의 수집
  실체(스윕·감지·추적)가 그라파나에서 아예 안 보인다. 08-10 Hiker 402 스윕 고착을 대시보드가
  아니라 수동 확인으로 발견한 이유다.

## 2. 결정 요약

| 결정 | 내용 |
|---|---|
| 분할 축 전환 | 데이터소스 축 → **여는 목적 축**(진입점 홈 + 기능 + 횡단) |
| 대시보드 7장 | 홈(신규) + 기능 3(탐색·모니터링·계정 유입) + 횡단 3(에러·API 성능·인프라(신규)) |
| 기능 대시보드 고정 순서 | 위 = 건강, 아래 = 사용량 — 전 대시보드 동일 |
| 사용량 형식 규칙 | **데이터가 형식을 정한다** — 하루 0~2건 규모는 stat(누적+주간 증분) + 최근 활동 목록, 시계열은 밀도가 충분한 것(Hiker 콜 등)만. 데이터가 자라면 시계열로 승격 |
| monitoring DB 개방 | 그라파나용 읽기 전용 롤 + 데이터소스 신설(스윕·감지·콜 카운트가 대시보드의 핵심 데이터) |
| 인프라 수집 추가 | node-exporter + cAdvisor 컨테이너 2개(compose), Prometheus job 2개 |
| SaaS 전환 안 함 | Datadog 등 검토 결과 부적합(§7) — 별도 안건으로 분리 |
| 기존 3장 처리 | 에러·API 성능은 횡단으로 유지(정리만), 서비스 현황은 기능 3장으로 해체·흡수 |

## 3. 홈 「지금 정상인가」 — 신호등 13타일

원칙: ① 타일 하나 = 예/아니오 질문 하나(답이 애매한 지표는 홈에 안 올림) ② 초록이면 읽을 게
없다(stat 타일만, 그래프·목록 없음, 스크롤 없음) ③ 모든 타일 클릭 → 담당 대시보드(빨간불의
다음 행동이 항상 정의됨).

```
┌─ 지금 아픈가 ──────────────────────────────────┐
│ [API 5xx] [ERROR 급증] [Hiker 402] [IG 401]    │
├─ 돌고 있나 ───────────────────────────────────┤
│ [스윕 신선도] [오늘 Hiker 콜] [미러 신선도]       │
│ [멈춘 등록] [알림 발송 실패]                     │
├─ 여유가 있나 ──────────────────────────────────┤
│ [호스트 CPU] [호스트 메모리] [was JVM] [DB 풀]   │
└───────────────────────────────────────────────┘
```

| # | 타일 | 질문 | 빨간불 기준 | 근거 | 클릭 시 |
|---|---|---|---|---|---|
| 1 | API 5xx | 유저가 에러를 보나 | 최근 1h 5xx율 > 1% | Prometheus | API 성능 |
| 2 | ERROR 급증 | 새로 터졌나 | 최근 1h ERROR 건수 > 임계(§6) | Loki | 에러 |
| 3 | Hiker 402 | 잔액이 말랐나 | 최근 24h **1건이라도** | Loki | 에러 |
| 4 | IG 401 | IP가 막혔나 | 최근 24h 급증 | Loki | 에러 |
| 5 | 스윕 신선도 | 어젯밤 스윕이 돌았나 | 마지막 성공 `sweep_run` 26h 초과 | monitoring DB | 모니터링 |
| 6 | 오늘 Hiker 콜 | 콜이 죽었나·폭주하나 | **0건**(스윕 불발) 또는 7일 평균 2배(과금 폭주) | monitoring DB | 모니터링 |
| 7 | 미러 신선도 | 랭킹이 최신인가 | `landing_stats.updated_at` 26h 초과 | analysis DB | 탐색 |
| 8 | 멈춘 등록 | 유저 등록이 걸렸나 | processing 임계시간 초과 > 0건 | app 스키마 | 모니터링 |
| 9 | 알림 발송 실패 | 메일이 나가나 | `alarm_event.email_status` 실패 > 0건(24h) | monitoring DB | 모니터링 |
| 10 | 호스트 CPU | CPU가 상시 포화인가 | **15분 지속** 85%(02:00 스윕 스파이크는 정상) | node-exporter | 인프라 |
| 11 | 호스트 메모리 | 가용량이 말랐나 | MemAvailable < 1GB(오버커밋 설계라 사용률 아닌 가용량) | node-exporter | 인프라 |
| 12 | was JVM | 힙이 차오르나 | old gen 85% 지속 또는 GC pause 급증 | Prometheus(기존) | 인프라 |
| 13 | DB 커넥션 풀 | 커넥션이 말랐나 | HikariCP pending > 0 지속 | Prometheus(기존) | 인프라 |

설계 판단 기록:

- **3(402)과 6(콜 0건)은 중복이 아니라 보완** — 402는 원인, 콜 0은 결과. 하나만 있으면 반나절
  늦게 안다(08-10 사고의 교훈).
- **6의 "2배" 기준은 Hiker가 실패(4xx)도 과금하기 때문** — 결과물은 안 쌓이는데 청구서만 느는
  시나리오는 3·4가, 콜 수 자체가 튀는 시나리오는 6이 잡는다.
- **7은 대용 지표임을 인정하고 감** — 미러 실행 이력이 analysis DB에 없다(08-18 실측:
  이력성 컬럼은 `landing_stats.updated_at`뿐). 미러가 반복적으로 문제 되면 그때 analytics에
  실행 마커를 넣는다. 이번 개편에 백엔드 코드 변경을 끼워 넣지 않는다.
- **감지(WATCHING→TRACKING)는 홈에 안 올림** — `detected_candidate` 0건은 "감지 고장"이
  아니었다(08-18 실측: 첫 감지는 후보 단계 없이 target에 `matched_keywords`만 남기고 바로
  자동 추적 전환 — 74·76이 08-12 키워드 "리끌로우"로 전환됐는데도 테이블은 빈 상태).
  "0이 정상일 수 있는" 지표라 신호등 부적격. 모니터링 대시보드에 정보성으로만 둔다.
- **컨테이너 다운은 홈에 안 올림** — OCI 커스텀 메트릭 알람이 이미 디스코드로 푸시한다.
  **푸시(OCI→디스코드)는 "죽었다", 그라파나는 "죽어간다"** 분업 — 같은 신호를 두 곳에
  올리면 정본이 흐려진다.

## 4. 기능·횡단 대시보드 구성

### 탐색 (지금 뜨는 인플루언서 + 콘텐츠 — 같은 랭킹 파이프라인이라 한 장)

- 건강: 미러 신선도, 랭킹 산출 건수(accounts·contents 미러 규모)
- 사용량: 저장 인플루언서·저장 콘텐츠 stat + 최근 저장 활동 목록

### 모니터링 (브랜드 + 경쟁사 + 캠페인 — 같은 스윕 엔진·도메인이라 한 장. 캠페인·성과 별도 장은 데이터 규모 미달로 기각: 캠페인 12·다이제스트 20)

- 건강: 스윕 성공 이력(`sweep_run`), 감지 전환 추이(정보성), fetch 실패 타깃, 알림 발송 상태
- 비용: **일별 Hiker 콜 시계열**(`brand_call_count` + `target_call_count` — 밀도 충분, 시계열
  제값) + 브랜드별 상위 콜
- 사용량: 브랜드 모니터링 130·타깃 73·캠페인 12 stat + 최근 등록 목록

### 계정 유입 (제품 메뉴에 없지만 기존 「서비스 현황」의 알맹이)

- 건강: 멈춘 등록·결과 미확정 상세(기존 패널 이전)
- 사용량: 가입·문의·가입 코드 소진 stat + 최근 가입 목록 (일별 timeseries 폐기)

### 인프라 (신규 횡단)

- 위: 호스트 — CPU·메모리·디스크·네트워크(node-exporter)
- 아래: 컨테이너별 CPU·메모리(cAdvisor, **mem_limit 대비 사용률**) + was JVM 상세(힙·GC·
  스레드·HikariCP)

### 에러 / API 성능 (기존 유지)

구조 변경 없음. 홈 타일의 착지점 역할. 개편 범위는 홈 타일과의 링크 연결 정도.

## 5. 인프라 변경 (compose·프로비저닝)

| 항목 | 내용 |
|---|---|
| node-exporter | `mem_limit: 64m`, `oom_score_adj: 500`(관측 스택은 압박 시 먼저 죽는 쪽 — 기존 규율) |
| cAdvisor | `mem_limit: 256m`, `oom_score_adj: 500` |
| prometheus.yml | job 2개 추가(node-exporter·cadvisor) |
| post-container-metrics.py | SERVICES에 2개 추가(사라지면 0 게시 → OCI 알람 — 기존 규율) |
| 데이터소스 | monitoring DB 읽기 전용(`grafana_reader_monitoring` 등 — 기존 postgres.yaml 관례로 파일 프로비저닝) |
| 대시보드 JSON | 홈·탐색·모니터링·계정유입·인프라 신규 + 서비스현황 제거. `allowUiUpdates: false` 유지 — 수정은 레포로만 |

**수동 런북(사용자 실행, Flyway 아님 — README §14 관례)**: monitoring DB에 읽기 롤 생성 +
필요 테이블 GRANT, app 스키마 `grafana_reader`에 신규 참조 컬럼 GRANT. `grafana_reader`는
컬럼 단위 화이트리스트라 **패널 추가 = GRANT 추가**다. 개편이 "패널을 골라서"인 이유이기도 하다.

배포는 정규 CD(develop→staging→main). compose 변경 포함이라 수동 배포 금지 규율 그대로.

## 6. 임계값 보정 유보

ERROR 급증 임계(타일 2), IG 401 급증 기준(타일 4), GC pause 기준(타일 12)은 **배치 후 1주
실측으로 보정**한다. 지금 정하는 숫자는 어차피 틀리므로 초기값은 느슨하게(오탐 없는 쪽으로)
넣고, 보정 자체를 후속 작업으로 남긴다.

## 7. SaaS(Datadog 등) 전환을 하지 않는 이유

① 대시보드 알맹이가 사설 Postgres SQL 패널(홈 13타일 중 5개 + 사용량 절 전부) — SaaS APM의
DB 기능은 DB 성능용이지 비즈니스 SQL 대시보드가 아니고, 옮기려면 커스텀 메트릭 계측 코드가
필요하다. ② 비용 규율(OCI Always Free·월 $1 알림) 대비 Datadog 월 $50~70. New Relic·Grafana
Cloud 무료 티어는 비용은 통과하나 ①이 남는다. ③ 노이즈는 도구가 아니라 설계 문제 — 벤더를
바꾸면 노이즈도 이사 간다. SaaS가 이기는 조건(팀 확장·분산 트레이싱·관측 스택 오프로딩)이
오면 **별도 안건**으로 재검토 — 이번 개편이 그 실험을 막지 않는다.

## 8. 비범위

- crawler·analytics·monitoring에 actuator/micrometer 추가(JVM 시야 확장) — 백엔드 코드 변경이라 별도 작업
- 미러 실행 마커 테이블 — §3 타일 7 판단 참조
- Thymeleaf 어드민(crawler `/ui`·analytics `/ui`) 개편 — 이번 축은 그라파나
- OCI 알람 체계 변경 — 푸시/풀 분업으로 공존
- 분산 트레이싱(Tempo·OTel)
