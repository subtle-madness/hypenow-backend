# 공동구매 판정 - 규칙 우선 + 애매분만 LLM (analytics 판정기)

> 상태: 🟢 활성 · 작성 2026-09-03 · 방향 사용자 승인(09-03 구두)

## 1. 배경

발굴 카드(6.21) `groupPurchaseCount`·`hasGroupPurchase`와 상세(6.4) 뱃지는 캡션의 공동구매 시그널로
판정한다. 현 규칙은 FE `src/lib/discover/group-purchase.ts`의 `/공동구매|#공구/`이며, `#` 없는 `공구`는
도구(연장) 오탐을 피하려고 제외했다. 운영 analysis DB `contents` 전량(295,621건, 12,047계정) 실측
결과 이 제외가 누락의 본체였다.

| 지표 | 현 규칙 | `공구` 전부 인정 |
|---|---|---|
| 게시물 적중 | 1,188 | 4,808 |
| 계정 12개 창 적중 게시물 | 625 | 2,206 |
| 12개 창에 이력 있는 계정 | 259 | 655 |

- 규칙 미적중 맨몸 `공구` 3,620건(765계정)의 무작위 표본 50건은 전부 공동구매 용법("공구는/가/기간/
  일정/오픈/예고/마감/중", "[공구]", "재공구", "브랜드명+공구"). 인플루언서는 본문에 `#` 없이 쓰는 게 기본.
- 도구 의미는 코퍼스 전체에서 20건 안팎("공구 없이 조립/설치", "공구함/통", "전동 공구", "DIY공구").
  "메이크업 공구" 류는 0건.
- 그 외 점검(문제 없음): 전각 `＃공구` 0, NFD 분해 한글 미매칭 0, 제로폭 문자 0, "공동 구매" 3,
  영문 동의어 7, `#공구x`·`#공구아님` 각 1.

**요구**: 오탐은 사실상 0이어야 한다(1건이 데이터 신뢰를 깬다는 사용자 판단). 동시에 누락 2.5배는
줄여야 한다.

## 2. 결정

**규칙이 확실한 곳은 규칙, 규칙이 흔들리는 곳만 LLM.** 브랜드 모니터링 광고 판정(monitoring
`AdDisclosureJudgeService`: Tier1 사전 → NEGATION 보류 가드 → Tier2 LLM)과 같은 계층 원칙을
analytics 층에 소형 판정기로 둔다.

기각한 대안과 이유:
- **정규식만(제외 목록 포함)**: 실측 잔여 오탐 1건. "0"이 요구라 탈락. 단, 이 규칙은 아래 Tier1·
  애매 분류 어휘로 그대로 살아남는다.
- **기존 콘텐츠 분석(`content_analyses`) 프롬프트에 필드 추가**: 토큰 비용은 0에 가깝지만 ① 새벽 배치라
  게시 후 하루 뒤 반영 ② 12개 창 커버 95%(142,075건 중 135,357건)라 나머지 5%에 정규식 폴백이 어차피
  필요 ③ 확실한 99.5%까지 LLM에 맡겨 LLM 고유 오판(광고 표기 트랙 오탐 730건 핫픽스 전례)이 유입
  ④ 기존 13만 행 재판정 또는 백필 필요. 세 축(비용·시간·판정 성능) 모두 열위.
- **애매분만 LLM에 보내되 was에서 호출**: was는 분석 결과 읽기 전용(시스템 경계). 탈락.

## 3. 판정 규칙

캡션 1건에 대해 순서대로 적용한다. 앞 단계에서 확정되면 뒤는 생략.

| 단계 | 조건 | 결과 |
|---|---|---|
| T1 확정 참 | `공동구매` 포함 | true (LLM 없음) |
| T1 확정 참 | `#공구` 포함 | true |
| 애매 분류 | `공구` 포함이면서 캡션 어디든 도구 어휘 동반 | LLM으로 |
| T1 확정 참 | `공구` 포함, 도구 어휘 없음 | true |
| 확정 거짓 | `공구`·`공동구매` 없음 | false (LLM 없음) |

- 도구 어휘(애매 분류 트리거, 캡션 전체 대상 - 근처 N자가 아님): `없이`, `조립`, `설치`, `나사`, `드릴`,
  `망치`, `볼트`, `드라이버`, `렌치`, `톱`, `목재`, `목공`, `철물`, `전동`, `DIY`, `수리`, `공구함`,
  `공구통`, `공구박스`, `공구세트`, `공구 ?(를|가) (들|필요|사용|이용|챙)`. 넉넉하게 잡는다 - 애매로
  분류돼 늘어나는 건 LLM 콜 몇백 건이고 비용은 무시할 수준. `드릴게요`류 오분류는 LLM이 걸러주므로
  무해(애매 분류는 "보류"이지 "거짓"이 아니다).
- **2026-09-04 정정(운영 실측)**: 위 어휘를 캡션 전체 부분 문자열로 잡으니 후보 4,808건 중 애매가 1,717건이었고,
  그 원인은 `드릴`("알려드릴게요"류 995건)과 `없이`("부담없이"류 957건)였다. 도구와 무관한 일상어가 LLM 콜
  1,700건과 staging 오탐 2건("공구없이 돌려서 끼우기만", "팔이공구러가 아닙니다")을 만들었다. "LLM이 걸러주므로
  무해"라는 위 전제는 틀렸다. 구현은 `드릴`을 동사 활용(게·께·까·수·지·테·려) 제외 명사형만, `없이`는
  `공구 ?없이`만 트리거로 좁혔다(`GroupPurchaseRule`). 좁힌 뒤 운영 애매 추정 239건(명사형 드릴 76건 포함).
- 이 표는 FE에도 그대로 전달하되, **FE는 더 이상 캡션에서 직접 계산하지 않는다**(§6).

### LLM(애매분)

- 입력: 캡션 1건. 질문: "이 게시물이 인플루언서 공동구매(공구) 판매 게시물인가. `공구`가 연장·도구
  의미로만 쓰였으면 아니오." 출력 JSON `{groupPurchase: boolean, reason: string}`.
- 전송: analytics 자체 `llm` 패키지의 `GeminiApi`(구현 `VertexHttpApi`, 생성은 `LlmClientFactory`) 온라인
  호출(소량·즉시). analytics는 `common-llm` 의존이 없다(monitoring·was만 사용). 모델·프로젝트는
  콘텐츠 분석과 같은 설정(`LlmConfig`)을 재사용.
- 콜 규모: 백로그 수백 건 1회 + 일 한두 건.

## 4. 데이터 모델 (analysis DB, analytics 소유)

```
group_purchase_judgments (
  short_code        text primary key,
  verdict           boolean,          -- NULL = 미판정(LLM 실패·대기)
  tier              text not null,    -- 'RULE' | 'LLM'
  reason            text,
  judged_caption_hash text not null,  -- md5(caption), Java MessageDigest (광고 판정과 동일 원칙)
  judged_at         timestamptz not null,
  model             text
)
```

- RULE 확정분도 기록한다(창 12개 판정을 was가 단일 테이블 조회로 끝내기 위해). 캡션 해시가 바뀐 행은
  재판정 대상.
- was는 미러 없이 이 테이블을 직접 읽는다(`contents`·`content_analyses`와 같은 DB). 기존 미러·뷰 무변경.
- 마이그레이션: analytics `db/migration/analysis`, UTC 타임스탬프 채번.

## 5. 잡 (analytics)

- `JobName.GROUP_PURCHASE_JUDGE`. 후보 = `contents`에서 `caption ~ '공구|공동구매'`이고 판정 행이 없거나
  해시가 다른 것. 규칙 확정분은 LLM 없이 즉시 기록, 애매분만 LLM.
- 주기: `ScheduleRunner` 패턴대로 `analytics.schedule.group-purchase-cron` 프로퍼티(기본 `-`=off)로
  등록하고, 운영 compose env에 미러 완료 직후 1회 + 낮 시간 30분 간격 크론을 넣는다(배포 PR에 env 동반).
  어드민 `/ui` 수동 트리거는 `AnalyticsJobService`에 `JobName` 추가로 자동 노출.
- 실패 격리: 게시물 단위. LLM 실패는 verdict NULL로 남기고 다음 주기 재시도. 연속 실패 임계 도달 시
  런 중단(광고 판정 `llmFailureAbortThreshold` 패턴).
- 킬 스위치·리셋: `app_setting` `analytics.group-purchase.enabled`(기본 true, 마이그레이션 시드). 사전·
  프롬프트를 고치면 기존 판정은 자동 재판정되지 않는다 - 리셋 SQL(`DELETE ... WHERE tier='LLM'` 또는
  해시 무효화)을 런북에 둔다.

## 6. was·API 계약

- 6.21 `groupPurchaseCount` = 상세 6.4와 같은 모수(contents `posted_at DESC` 12개, 게이트 없음)에서
  `verdict = true`인 게시물 수. `hasGroupPurchase` = count > 0. **미판정(NULL)은 미포함**(신뢰성 우선 -
  잡 주기가 짧아 공백은 분 단위).
- 6.4 `recentContents[]`에 `groupPurchase: boolean` 추가(미판정은 false). FE는 자기 정규식을 버리고
  이 값으로 뱃지를 그린다 - 정답이 서버 한 곳이 된다.
- 6.23 유사 카드는 6.21과 같은 어셈블러라 자동 동승.
- 계약 문서 `docs/contracts/discovery-card-comments-range-group-purchase-reply.md`를 이 판정 소스로 갱신
  (같은 커밋). 현 PR(정규식, FE와 동일 규칙)은 필드 형태를 먼저 내보내고, 이 트랙이 판정 소스만 교체한다.

## 7. 검증

- 유닛: 규칙 표 전 행 + 도구 어휘 각 1건 + 광고 판정 골드 사례 이식(공구 없이 조립 → 애매).
- 통합(Testcontainers): 잡이 규칙 확정분을 LLM 없이 기록, 애매분만 LLM 스텁 호출, 해시 변경 시 재판정,
  NULL은 count 미포함.
- 운영 전: staging에서 백로그 1회 완주 후 §1 표의 `공구` 전부 인정 수치(2,206건·655계정)와 대조 - 잡 결과
  true 합이 그 근처(오탐 20건 안팎 제외)여야 한다. 애매분 LLM 판정은 전수 육안 확인(수백 건).
- 운영 후: 애매분 판정 로그를 주 1회 표본 점검.

## 8. FE 통지 요지

필드 형태는 현 PR 그대로. 판정 소스가 서버 판정 테이블로 바뀌며 6.4에 `groupPurchase` 게시물 플래그가
추가되니, `group-purchase.ts`의 클라이언트 판정을 제거하고 서버 값을 쓰도록 요청. 규칙 표(§3)와 실측
근거(§1)를 함께 전달.
