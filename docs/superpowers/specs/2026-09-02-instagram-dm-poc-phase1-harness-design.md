# 인스타 DM 자동 발송 POC — 1단계 하네스 설계

> 상태: 🟢 활성 · 설계(구현 착수 전) · 2026-09-02
> 범위: **1단계(신규 계정 + 즉시 발송)** 만. "신규 계정으로 콜드 DM을 자동 발송하면 즉시 정지당하는가, 아니면 몇 건까지 버티는가"를 재는 최소 하네스.
> 전제: 갈림길 ①~⑧ 결정([핸드오프](2026-09-01-instagram-dm-poc-handoff.md))을 근거로 함. 결정의 이유·기각 대안·재검토 트리거는 핸드오프 참조, 이 문서는 그 위에 얹는 실행 설계.
> 병렬 트랙: 공식 API "합법 구간"([official-api-dm-poc](2026-09-02-instagram-official-api-dm-poc.md)), 계정 조달 방안(별도 세션)은 이 하네스와 분리.

## 1. 무엇을 알아내나

- **1단계 질문**: 신규 계정이 워밍업 없이 콜드 DM을 자동 발송하면 **즉시 정지당하나**? 안 당하면 **계정당 몇 건 / 며칠까지 버티나**?
- **관문 구조**(단계 나눔):
  - **관문 1 = 이 문서**: 자동화·볼륨·패턴만으로 계정이 타는지(친절한 우리 더미 상대로도). 싸고 안전한 첫 필터. 근거상 여기서 이미 결론 날 가능성 높음.
  - **관문 2(범위 밖)**: 실제 수신자의 신고·차단 축. **동의한 고객 파일럿**으로만. 이 문서 다루지 않음.
- **측정 대상 = 자동화·볼륨·패턴 축**. **측정 안 하는 것 = 응답률(효과)**(수신자가 우리 더미라), **실제 수신자 신고 축**(관문 2).

## 2. 실험 설계

### 계정 두 그룹
- **발송 그룹(senders)**: 신규 계정. 즉시 콜드 DM 발송. → 死까지 발송수·시간 관찰.
- **대조 그룹(controls)**: 같은 신규 계정인데 **콜드 DM만 안 하고** 비DM 활동(피드 열람·좋아요)만. → "우리 인프라 위 신규 계정이 DM 없이 사는가" 기준선.
- **판정 논리**: 대조도 죽으면 死 원인은 인프라·지문(DM 무관), 대조는 살고 발송만 죽으면 死 원인은 콜드 DM.
- 발송 계정은 사용자가 조달(폰·이메일 인증 섞임 가능). N은 config로 유연. 인증 등급은 계정별 조건 라벨로 기록(§4 표).

### 수신 더미
- **우리 통제 계정 20개.** 발송 그룹이 공유(한 더미가 여러 발송계정한테 받아도 됨). 받기전용이라 프록시·기기·워밍업 불필요, **로그인만 되면 됨**(도착 확인용).
- 조달은 사용자 몫(직접 생성 권장). 하네스는 출처 무관, **로그인 목록만** 받음.
- 20개인 이유: 21/시간 앵커 레이트를 1시간에 서로 다른 20명에게 보내 테스트하려면 서로 다른 20명이 필요(콜드=사람당 1건). → §3.

### 조건 축 (1단계에서 고정 vs 관찰)
- **고정**: 워밍업 없음(1단계 정의), 발송률 21/시간 근처, L2 한국 기기 프로필, 한국 sticky 레지던셜 프록시.
- **관찰(산출)**: 死까지 발송수, 생존시간, 死 신호 종류, 도착률, 발송 vs 대조.
- **부수 조건 라벨**(섞이면 나눠 볼 것): 인증 등급(폰/이메일), 문구 변형 모드.

## 3. 아키텍처 (모듈형 + 단순 러너)

관심사별 모듈을 러너 하나가 오케스트레이션. 큐/워커 인프라는 안 씀(1단계 규모).

| 모듈 | 책임 | 근거 갈림길 |
|---|---|---|
| `config` | 실행 정의 로드 — 발송계정·수신더미 로그인 목록, 발송 잡(수신자+사용자 문구), 파라미터. 실험의 단일 정본 | — |
| `session` | 계정당 세션 저장분 있으면 로드, 없으면 **1회 로그인 → dump_settings**. 로그인 챌린지는 死로 기록·정지(복구 안 함) | ②C, ⑦ |
| `device` | 계정당 일관된 **한국 실기기 프로필(L2)** 생성·영구 고정. 세션과 같은 파일. 공유·변경 금지 | ⑤ |
| `proxy` | 발송계정 → **한국 sticky 레지던셜 출구 1:1(미중첩)**. 수신 더미엔 프록시 안 붙임 | ④ |
| `sender` | `(세션, 수신자, 문구)` → instagrapi로 DM 발송. 결과/신호 반환. **자동 재시도 없음** | ③(바닐라 instagrapi), ⑦ |
| `pacer` | 언제 보내나 — 발송 간 지터, 활성시간 게이트, 비DM 액션 삽입, 계정당 레이트 상한 | ⑥ |
| `detector` | 응답·예외를 **3단계 분류**(일시/차단/종료), 계정 즉시 정지 + **함대 서킷브레이커** | ⑦ |
| `delivery` | 수신 더미에 로그인해 수신함·요청함 읽어 **도착/사일런트드롭 확인**. 공식 API 소스는 나중 pluggable | ⑦, delivery-A |
| `ledger` | **SQLite** — 발송 이벤트·계정 메타·死 이벤트 append. 전 모듈이 기록 | ⑧ |
| `runner` | 오케스트레이션. 계정별 (session+device+proxy) 조립, 루프, 정지 존중, 킬 스위치 | — |

**대조 그룹 처리**: 나머지 동일하되 `sender`가 콜드 DM 대신 비DM 액션만. arm 플래그로 분기.

**데이터 흐름**:
```
config → runner가 계정별 (session+device+proxy) 조립
  └─ 계정별 루프:
       pacer가 다음 행동 스케줄 (활성시간 안 + 지터)
         ├─ 발송 그룹: sender.send(수신자, 문구)
         └─ 양쪽 공통: 비DM 액션(피드·좋아요)
       결과 → detector 분류 → ledger 이벤트 기록
       발송이면 → delivery가 수신측 도착 확인 → ledger
       하드 신호면 → 계정 死 기록·정지 ; 서킷브레이커가 함대 감시
  └─ 종료: 전 계정 死 or 실행기간 만료 or 킬 스위치
```

**재사용**: crawler `JdkInstagramWebClient`의 프록시·HTTP 위장 관용구 참고 가능하나, 본 하네스는 **독립 Python + instagrapi**(확정결정 #4, 백엔드와 격리). 로그인·세션·DM·기기에뮬은 instagrapi 담당.

## 4. 기록 (SQLite — 표 3개, 파일 하나)

**계정 메타** (테스트 계정당 1행)
| 필드 | 설명 |
|---|---|
| account_alias | 계정 별명 |
| arm | send / control |
| verification | phone / email |
| proxy_exit | 배정된 sticky 출구 식별자 |
| device_profile | 기기 프로필 요약(모델·앱버전·로케일) |
| instagrapi_version | 핀 고정된 버전 |
| created_at | 계정 생성 시각(기록) |

**발송 이벤트** (발송/비DM 시도당 1행)
| 필드 | 설명 |
|---|---|
| ts | 시각 |
| account_alias | 어느 계정 |
| action | dm_send / non_dm(피드·좋아요) |
| recipient | 어느 더미(발송일 때) |
| result | success / fail |
| signal | 신호 등급·코드(있으면) |
| delivered | 도착 확인 결과(확인됨/미도착/미확인) |
| dt_since_prev | 직전 발송과의 간격(초) |
| message_variant | 문구 변형 식별(변형 모드일 때) |

**死 이벤트** (계정이 죽으면 1행)
| 필드 | 설명 |
|---|---|
| account_alias | |
| died_at | 시각 |
| signal | 死 유발 신호 종류·코드 |
| cumulative_sends | 死까지 누적 발송수 |
| survival_seconds | 첫 발송~死 시간 |
| nth_send | 몇 번째 발송에서 |
| raw_response | 응답 본문(진단용) |

**파생 산출**: 조건별 생존곡선(폰 vs 이메일, 발송 vs 대조), 死 사유 분포, 도착률.

**원칙**: 발송 하나하나를 다 append(死만 기록하면 곡선·간격·몇건째 재구성 불가).

## 5. 실행 파라미터 (전부 config 조절 가능, 시작값)

| 파라미터 | 시작값 | 비고 |
|---|---|---|
| 활성 시간 | KST 10:00 ~ 22:00 | 새벽 발송 없음 |
| 발송 간격(지터) | 1 ~ 5분 랜덤 | 등간격 금지 |
| 비DM 액션 | 발송 사이 피드 열람·좋아요 소수 | DM만 하지 않게 |
| 발송률 | **1시간에 ~20건 몰아서**(≈ 피처링 Max 21/시간, 공개된 콜드 상한) | worst-case 앵커 |
| 수신 더미 수 | 20 | 21/시간을 서로 다른 20명에게 = 20 필요 |
| "1단계 생존" 기준 | **20건 다 보내고 밴 신호 없음** | |
| 死 후 관찰 | 발송 끝나도 2~3일 계정 켜둠 | 지연 밴 포착 |

**정직한 단서**: 근거표에 "40건 콜드DM에 경고" 사례. 死가 ~40건일 수 있어 20건 깊이로는 20건 안에 죽으면 완벽 포착, 20건 다 살면 "즉사 아님"까지만. 그 경우 관문 1 통과 → 수신 더미를 늘려 ~40건 깊이로 재실행(2단계 성격).

## 6. 안전·정지

**신호 3단계 분류·대응**
| 등급 | 신호 예 | 대응 |
|---|---|---|
| 일시 | `429` / `PleaseWaitFewMinutes` | 백오프·재개(死 아님), 스트레스로 기록 |
| 액션 차단 | `FeedbackRequired` | 그 계정 발송 중단, 기록 |
| 종료(死) | `ChallengeRequired` / 계정 비활성 / `LoginRequired` 반복 | 死 확정, 그 계정 완전 정지, 기록 |

**정지 두 레벨**
- **계정 단위**: 위 신호 시 그 계정만 즉시 정지.
- **함대 서킷브레이커**: 짧은 창(예: 15분)에 **2개 이상** 계정이 하드 신호 → 전체 정지(계통 문제 방어). 임계 config 조절.

**재시도·복구 없음**: 하드 신호에 자동 재시도 금지(밴 가속). 챌린지 복구 시도 안 함 → 첫 하드 신호 = 死 확정(생존 측정 정합).

**사람 킬 스위치**: 언제든 전체 즉시 정지.

**발송 전 가드**: 수신자가 통제 더미 목록에 있는지 확인(실제 사람 오발송 방지 — 안전선 강제), 활성시간·레이트 초과 시 발송 차단.

## 7. 안전선 (POC 내내)

- 100% 버릴 테스트 계정으로만. 고객사 계정 절대 미사용.
- 수신 = 우리 소유·통제 더미로만. 실제 인플루언서 스팸 금지(윤리·법무·정보통신망법 + 측정 오염).
- 밴 신호 시 즉시 정지. 실제 사람 대상 발송은 하네스 가드가 원천 차단.

## 8. 범위 밖 (후속)

- **워밍업 단계(2단계)**: 워밍업 후 재측정. 관문 1 결과 보고.
- **rate 코호트 실험**: 워밍업 유효 확인 후.
- **깊이 확장**: 20건 다 살면 수신 더미 늘려 ~40건+.
- **관문 2**: 실제 수신자 신고 축 = 동의 고객 파일럿(법무 검토 동반).
- **하이브리드(비공식→공식 API)**: 공식 API 트랙([official-api-dm-poc](2026-09-02-instagram-official-api-dm-poc.md))의 브리지·username 매핑 실측 결과에 따라.
- **제품화 법무**: 정보통신망법 광고성 정보·옵트인, 뒷광고 표시 — 실서비스 전 변호사 검토(POC엔 무관).

## 9. 테스트 (하네스 자체 검증)

- `detector`의 신호 분류·서킷브레이커: 가짜 응답 주입으로 3단계 분기·함대 정지 유닛 테스트.
- `pacer`: 활성시간 게이트·지터·레이트 상한 로직 유닛 테스트(실발송 없이).
- `ledger`: append·파생 집계 쿼리 검증.
- **드라이런 모드**: 실제 발송 없이 스케줄·기록만 돌려 파이프라인 검증 후 실계정 투입.
