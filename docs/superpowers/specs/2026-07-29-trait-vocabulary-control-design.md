# trait 어휘 통제 설계 (유사도 v2 2단계)

> 상태: 🟢 활성 · 설계 확정(2026-07-29) — 어휘 172개·1:N 분해 매핑 사용자 확정. 구현 계획은 plans/ 참조

## 1. 배경 — 보류 해제

[2026-07-28 유사도 v2 설계](2026-07-28-similar-influencer-similarity-v2-design.md) §5에서 2단계(어휘 통제)는
"카테고리·태그라인 변경이 반영된 분석 데이터 확보 후 사용자 재결정"으로 보류됐다. 트리거는 충족됐다:

- 리포트 개편 카피 백필이 07-29 01:33Z 완결(6,656계정 100%) — 합성이 tagline·traits·카피를 한 콜에
  만들고 백필이 행 전체를 재기록하므로 **traits 전량이 새 프롬프트 산출로 교체됨**.
- 운영 재실측(07-29, 새 프롬프트 산출분만): 인스턴스 25,818 / 고유 4,242 / 싱글톤 62.6%.
  **난수화 문제는 새 프롬프트에서도 그대로다** — "솔직 리뷰/솔직한 후기/솔직한 리뷰/솔직한 사용 후기"가
  전부 별개 값. 어휘 통제 없이는 혼합 점수의 Jaccard 성분(0.6)이 죽은 채 카테고리 믹스(0.4)만 동작한다.
- 커버리지 곡선: 상위 100개=56.8%, 상위 300개=71.2%, 상위 353개(≥10회)=73.4%.

07-29 사용자 결정: **착수 + 데이터 주도 어휘 구성** (44개 수동 초안의 반려 사유였던 표현력 하락을
운영 최다 빈도 표기 채택으로 회피).

## 3. 구성 요소

### 3-1. 어휘 테이블 (analysis DB, analytics Flyway V41)

```sql
CREATE TABLE trait_taxonomy (
    name  text PRIMARY KEY,   -- 캐노니컬 태그 (화면·저장 표기 그대로)
    facet text NOT NULL,      -- 부록 A의 13개 축 (프롬프트 구획·관리용)
    facet_order int NOT NULL,
    sort  int NOT NULL        -- 축 내 표시 순서
);
```

- `beauty_taxonomy`(V30)와 동일 원칙: 어휘 수정은 후속 마이그레이션, CHECK 제약 없음
  (방어는 Java sanitize — 같은 로더 스냅샷을 프롬프트와 공유).
- 감사 테이블(같은 마이그레이션):

```sql
CREATE TABLE trait_canon_log (
    raw_value   text NOT NULL,
    canon_value text,          -- NULL = 매핑 불가(드롭)
    mapped_at   timestamptz NOT NULL,
    PRIMARY KEY (raw_value, canon_value)  -- 1:N — raw당 복수 행
);
```

> PK에 NULL 불가이므로 매핑 불가 기록은 canon_value에 센티널 `''`(빈 문자열)을 쓰거나 PK 대신
> UNIQUE 부분 인덱스로 — 구현에서 택일(계획서에 기록).

### 3-2. 로더·프롬프트 주입 (analytics)

- `TraitTaxonomyLoader`: `BeautyTaxonomyLoader` 패턴 그대로(첫 로드 후 메모이즈, 빈 테이블이면 fail-fast).
- `GeminiAccountSynthesizer.INSTRUCTIONS`의 traits 항목을 "아래 어휘에서만 3~5개 선택(임의 조어 금지)"으로
  바꾸고 어휘 목록(축별 구획)을 주입. **static 상수 → 어휘를 받는 `instructions(vocab)` 로 전환** —
  `AnthropicAccountSynthesizer`가 static final로 캡처하던 공유 방식도 같이 바꾼다(한쪽만 낡는 사고 방지
  주석의 취지 유지: 원천은 여전히 Gemini 어댑터 한 곳).
- `AccountAnalysisWriter`: 어휘 밖 값 드롭 + 중복 제거(sanitize). 드롭 후 0개면 기존 `isValid` 가드에
  걸리지 않도록 — traits 0개는 **빈 배열로 저장 허용으로 완화**(믹스 성분으로 후보 유지, 07-28 스펙 §5 합의).

### 3-3. 배치 매핑 잡 (analytics 어드민 원샷)

- `JobName.TRAIT_CANON` 신설 — 기존 어드민 /ui 잡 등록 패턴(JobLock·RunHistory·수동 트리거) 재사용.
- 절차: `account_analyses`(전 이력 행)에서 고유 trait 값 수집 → LLM 배치 매핑(~100개/콜, 어휘 전문과
  분해 규칙을 프롬프트에 제시, 응답은 raw→[canon…(≤2)] JSON) → `trait_canon_log` 기록 →
  `account_analyses.traits` in-place UPDATE(캐노니컬 치환, 중복 제거, 매핑 불가 값 제거).
- **dry-run 모드 기본**: 매핑 결과와 치환 통계(치환/드롭/빈 배열 계정 수)만 산출, UPDATE 없음.
  실행 모드는 사용자 승인 후.
- 매핑 후 태그 0개가 된 행은 빈 배열 그대로(계정 제외 안 함).

### 3-4. 배포 순서 (엄수 — 1단계와 달리 순서 제약 있음)

1. analytics 배포(V41 시드 + 프롬프트 주입) — 이후 신규 분석은 어휘 내 산출.
2. 매핑 잡 dry-run → 사용자 승인 → 실행 — 기존 데이터 이행.
3. 운영 유사도 분포 재실측 → 필요시 was 컷 상수 조정(별도 PR).

매핑 전 신어휘 분석이 섞이는 기간(1~2 사이)은 짧게 유지한다.

## 4. 검증

- 단위: sanitize(어휘 밖 드롭·중복 제거·빈 배열 허용), 매핑 응답 파싱(1:N·불가 처리), 로더 fail-fast.
- 통합(Testcontainers): V41 적용 + 잡 dry-run/실행이 traits·trait_canon_log를 기대대로 바꾸는지.
- 운영 검증: 매핑 후 고유 trait 수(≈172 수렴)·싱글톤 비율, 유사도 점수 분포 재실측(§2-⑧).
