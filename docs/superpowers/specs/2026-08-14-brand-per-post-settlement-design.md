# 브랜드 초기 수집 — 게시물 단위 정산 + ready 10초 상한 설계

> 상태: 🟢 활성 · 설계 승인(2026-08-14)

## 배경 — 왜 바꾸나

08-13 완결 배치 서빙([2026-08-13-brand-initial-batch-serving-design.md](2026-08-13-brand-initial-batch-serving-design.md))은
정산·방출 단위를 **열거 페이지(21건) 배치**로 잡았다. 실측 기준 첫 배치 완결 ~10초를 기대했지만
운영 체감은 **~30초**다(꼬리 콜이 배치 전체를 붙든다 — 배치 정산의 구조적 약점). 또한 이후
폴링도 21건 단위로만 점프해서, 완결된 게시물이 있어도 같은 페이지의 느린 게시물을 기다린다.

사용자 요청(2026-08-14): ① 첫 ready는 **최대 10초만** 기다린다 — 10초 안에 첫 배치(21건)가 안
끝나면 되는 만큼만 보낸다. ② 이후에도 21건 배치를 기다리지 말고 **폴링마다 완결된 게시물부터**
내려간다. ③ 단, 내려가는 게시물은 **댓글 인플루언서 보강이 끝난 상태**여야 한다(반쯤 빈 카드
금지 — 완결 서빙 계약 유지).

사용자 결정(2026-08-14 문답):

| 결정 | 값 |
|---|---|
| 10초 타이머 기준점 | **등록(백필 시작) 시점** — FE 폴링 시작과 일치 |
| 10초 시점 정산 0건이면 | **최소 1건 정산까지 대기** — 빈 ready를 열지 않는다 |
| 보강 실패 게시물의 정산 | **시도 종료 시 정산(현행 유지)** — 성공 보류는 영구 미노출 위험 |

## 설계

### 1. 정산 단위 — 페이지(21건) → 게시물 1건

`BrandCollectService.enrich`를 게시물당 태스크 합성으로 재구성한다. 현행은
"게시자 전체 join → 댓글 전체 join → 페이지 일괄 `markEnriched`"의 2단계 배리어 구조다.

- **게시자 퓨처는 게시자별 1개로 공유** — 같은 페이지에 같은 작성자가 여러 번 나와도 콜 1번
  (현행 dedup 유지, 총 Hiker 콜 수 불변). stale 판정(`freshIgUserIds`)도 현행 그대로.
- 게시물별로 `allOf(자기 게시자 퓨처, 자기 댓글 퓨처)` 완료 시 **그 게시물 1건만 즉시
  `markEnriched`** — 성공·실패 무관(시도 종료 = 정산, 08-13 스펙 §1 의미 유지). 댓글 게이트에
  안 걸린 게시물(댓글 증가 없음·숨김)은 댓글 퓨처가 즉시 완료라 게시자만 끝나면 정산된다.
- **메서드 전체 join은 유지** — enrich 호출자가 페이지 완주까지 블로킹되는 것이 유일한 브랜드 간
  백프레셔라는 08-13 설계 의도를 보존한다(제거하면 08-12 OOM 형태 재현).
- **배치 DB 조회 실패의 안전판 유지** — `freshIgUserIds`·`commentsCollectedCounts`는 태스크 생성
  전의 무방비 지점이다. 바깥 try/finally를 유지해 finally에서 **페이지 전체를 일괄
  `markEnriched`**한다(180일 초과 게시물 영구 미노출 방지 — 08-13 스펙의 finally 근거 그대로).
  게시물별 마킹과 겹쳐도 안전하도록 §3의 COALESCE로 이중 마킹을 무해화한다.

일일 스윕(`sweep`)도 같은 `enrich`를 쓰므로 자동으로 게시물 단위 정산이 된다. was는 이미
`enriched_at IS NOT NULL` 게이트로 정산분만 내려주므로 **폴링마다 완결된 게시물부터 그때그때
내려간다** — was 변경은 없다.

### 2. ready 조건 — "첫 배치 완결" → "첫 배치 완결 ∨ (10초 경과 ∧ 정산 ≥ 1건)"

`BrandRegistrationService.runBackfillSafely`에서:

- 백필 시작 시점에 **10초 타이머**를 건다(설정화 — `monitoring.brand.serving-open-timeout: 10s`).
- `enrich`에 **게시물 정산 리스너**를 넘긴다(오버로드 — 스윕 경로는 무리스너로 동작 불변).
- ready(markServing) 판정 — 다음 중 먼저 오는 쪽이 연다:
  1. **첫 페이지 배치 완결**(현행 경로 — 10초 전에 다 끝나면 즉시)
  2. **타이머 만료 이후의 정산 1건 이상** — 만료 시점에 이미 1건 이상이면 만료 즉시,
     0건이면 그 뒤 첫 정산이 도착하는 순간
- 경합 안전: `served` AtomicBoolean(1회 실행)은 현행 유지, `markServing`의
  `last_swept_at IS NULL` 가드도 그대로(스윕 경로와의 이중 방어).
- **태그 0건 브랜드의 루프 종료 시 markServing**(collecting 영구 갇힘 방지)은 현행 유지 —
  이 경우 "정산 ≥ 1건" 조건을 적용하지 않는다(정산할 것이 없다).
- `touchSwept`(= 응답 `collectionCompletedAt`, FE 폴링 종료 조건)은 **모든 페이지 보강 뒤** — 불변.

타이머 실행 기반은 구현 계획에서 확정한다(후보: 전용 `ScheduledExecutorService` 빈 /
`CompletableFuture.delayedExecutor`). enrich executor에 태우면 포화 시 10초 약속이 밀리므로
**enrich executor는 쓰지 않는다**.

### 3. `markEnriched` — 최초 정산 시각 보존

```sql
UPDATE brand_tagged_post SET enriched_at = COALESCE(enriched_at, ?) WHERE ...
```

현행은 평범한 `SET`이라 이중 마킹(게시물별 + finally 안전판, 그리고 매일 스윕의 재보강)이
시각을 덮는다. `enriched_at`의 소비자는 was 게이트(`IS NOT NULL`)뿐이라 어느 쪽이든 동작은
같지만, "최초 정산 시각"으로 의미를 고정해 이중 마킹을 무해화한다. 스키마 변경은 없다.

### 4. 바뀌지 않는 것

- status 3값 계약(`collecting|ready|error`), FE 응답 셰이프, 신규 필드 없음
- was 게이트 4곳의 표시/판정 분리(08-13 스펙 §5)
- 실패 게시물 정산 규칙 — 게시자 404 1회 재시도, 타임아웃 즉시 포기, 소진 시 빈 채 정산
- 워커·executor 동시성 설정(워커 10 · enrich executor 2 · backfill 2)
- 마이그레이션 없음

### 5. 트레이드오프

- 정산 UPDATE가 페이지당 1회 → 게시물당 1회(백필 최대 수백 건·단건 UPDATE) — 무시 가능.
- FE 목록 증가가 21건 점프 → 세밀한 증가로 바뀐다. 순서 흔들림(taken_at 비단조 끼어들기)은
  08-13 FE 통지 사항 그대로이며 새 통지는 불필요(증가 패턴만 달라진다).
- 2단계 배리어("게시자 전체 → 댓글 전체")가 사라지지만 게시자 dedup을 공유 퓨처로 보존하므로
  총 콜 수는 동일하다. 페이지 완주 시간은 배리어 제거로 오히려 같거나 빨라진다(댓글이 자기
  게시자만 기다리면 된다).

## 실패 시나리오

- **10초 내 정산 0건 + 이후에도 전멸(페이지 보강 전체 실패)** → markServing 미호출 → 현행과
  동일하게 `collecting` 유지, core 실패 시 `backfill_error`. 다음 스윕이 백스톱.
- **타이머 발화와 첫 배치 완결이 동시** → `served` CAS로 1회만 markServing.
- **정산 1건 후 앱 사망** → ready는 열렸고 `collectionCompletedAt` null → FE 폴링 지속 →
  다음 새벽 스윕이 잔여 백스톱(08-13 시나리오와 동일).

## 테스트

기존 monitoring 관용구(가짜 `HikerHttp`)로:

1. 게시물별 정산 — 페이지 안에서 먼저 끝난 게시물의 `enriched_at`이 늦게 끝난 게시물보다
   먼저(따로) 찍힌다
2. 첫 배치 완결 전 + 10초 경과 + 정산 1건 → markServing
3. 10초 시점 정산 0건 → 열리지 않고, 그 뒤 첫 정산 도착 시 markServing
4. 10초 전 첫 배치 완결 → 즉시 markServing(현행 보존)
5. 배치 DB 조회 실패 → finally 안전판이 페이지 전체를 정산(전건 `enriched_at` NOT NULL)
6. 이중 마킹이 최초 정산 시각을 보존한다(COALESCE)
7. 태그 0건 브랜드 → 루프 종료 시 markServing(정산 0건이어도)
8. 스윕 경로(무리스너) 동작 불변 — 게시물 단위 정산만 적용

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| ready 타이머만 추가(정산은 21건 배치 유지) | 폴링이 여전히 21건 단위로 점프 — "되는대로 보내기" 미충족 |
| 배치 크기 축소(예: 5건) | 근사치일 뿐, 배치 경계에서 느린 콜이 나머지를 붙드는 구조가 그대로 |
| 빈 ready(10초 시 0건이어도 개방) | 사용자 결정으로 기각 — 최소 1건 정산까지 대기 |
| 댓글 성공까지 정산 보류 | 404 2%·타임아웃 1% 게시물이 영구 미노출 — 08-13 스펙과 같은 근거로 기각 |
