# 주간 알림 다이제스트 개편 설계

> 상태: 🟢 활성 · 2026-08-27 브레인스토밍 확정. 구현 계획은 후속(plans/).

## 1. 배경과 문제

현행 알림은 콘텐츠 모니터링 추적 이벤트 4종(수집 시작/종료, 지표 숨김, 콘텐츠 접근 불가)의
**일일 다이제스트**(인앱 `monitoring_digests` + 이메일)뿐이다. 그 이후 커진 핵심 기능 —
브랜드 모니터링(해시태그 스윕의 새 게시물 발견), 광고 표기 판정 — 에는 알림이 전혀 없어
사용자가 직접 화면에 들어가야만 변화를 안다.

구조적 제약도 셋 있다.

1. **이벤트 어휘 4종 하드코딩**: `alarm_event.event_type`, 옵트아웃 테이블 CHECK 제약,
   `MonitoringEventTypes` 매핑, 알림 설정 API의 완전체 매트릭스까지 전부 4종 전제.
   이벤트 추가마다 마이그레이션 + monitoring/was 양쪽 + FE 계약이 같이 움직인다.
2. **읽음 모델 3원화**: 다이제스트(id 배열) / 공지(last-seen) / 등록 내역(acknowledged).
3. **레인이 일일 하나**: 매일 오는 알림은 사용자에게 부담이고(이번 개편의 직접 동인),
   즉시성이 필요 없는 이벤트까지 매일 리듬에 묶여 있다.

## 2. 결정 요약

| 항목 | 결정 |
|---|---|
| 리듬 | **전부 주간 통일. 일일·즉시 레인 폐지.** 매주 월요일 09:00 KST, 지난주(월~일) 요약 1건. 이벤트 0건이면 그 주는 알림 미생성 |
| 신규 이벤트 | ① 등록(시딩) 게시물의 **광고 미표기 판정** ② 해시태그 스윕의 **브랜드 새 게시물 발견** |
| 기존 4종 | 유지하되 주간 리듬으로 이동 |
| 제외 | 캠페인 수명주기 알림(기각 — 다이제스트 문안에 캠페인 이름 문맥만 반영), 저장 인플루언서 워치리스트(후속 후보), 업데이트 소식(무변경), 주간 성과 리포트(별도 트랙) |
| 채널 | 인앱 + 이메일 둘 다. 이메일 옵트아웃은 **"주간 이메일 수신" 토글 1개**로 축소 |
| 미표기 범위 | **사용자가 등록한(시딩) 게시물만.** 스윕이 발견한 제3자 게시물의 미표기는 알림 제외(대응 불가능한 소음) |

### 결정 근거(요약)

- 일일 레인 폐지는 "매일 오는 알림은 부담"이라는 사용자 판단이 직접 동인. 긴급도별
  2단(일일 문제 알림 + 주간 요약) 안을 검토했으나 기각 — 미표기·삭제 인지가 최대 7일
  늦어지는 트레이드오프를 감수하고 단일 리듬의 단순함을 택했다.
- 즉시 레인(직접 등록 시 수집 시작 즉시 알림)은 등록 처리 내역(acknowledged) 표면과
  중복이라 함께 폐지.

## 3. 주간 알림 1건의 내용 구성

섹션 3개, 내용이 있는 섹션만 노출:

1. **확인 필요** — 광고 미표기 판정 N건 · 콘텐츠 접근 불가(삭제/비공개) N건 · 지표 숨김 N건
2. **브랜드 소식** — 해시태그로 새로 발견된 브랜드 게시물 N건
3. **모니터링 진행** — 수집 시작 N건 · 수집 종료 N건 (캠페인 이름 문맥 포함)

`monitoring_digests.items` jsonb(`[{category, type, summary, count}]`)에 카테고리를
추가하는 형태라 FE는 항목 렌더링만 확장하면 된다.

## 4. 파이프라인 — 이벤트 원장 없이 "주간 조회" 방식

주간 리듬에서는 실시간 이벤트 적재가 대부분 불필요하다. **주간 집계 잡이 정본 테이블을
기간 조회**해 다이제스트를 만든다.

| 섹션 | 데이터 소스 | 조회 방식 |
|---|---|---|
| 브랜드 새 게시물 | monitoring DB `brand_tagged_post`(+ `brand_hashtag_post` 매핑) | 지난주 발견분(발견 시각 기간 조회), 등록(direct)분 제외 |
| 광고 미표기 | `brand_tagged_post.ad_verdict`/`ad_judged_at` × 등록 원장(`app.brand_post_registrations`) | 지난주에 미표기 판정된 등록 게시물. **FE 노출 킬 스위치(`AD_DISCLOSURE_EXPOSE`)를 알림도 동일하게 따른다** |
| 수집 시작/종료 · 접근 불가 · 지표 숨김 | 기존 `alarm_event` 원장 | 주간 범위 조회. 지표 숨김 같은 상태 전이는 소급 조회가 불가능하므로 `AlarmRecorder` 적재는 그대로 유지, **소비 리듬만 주간으로** |

- 기존 `DigestJob`(일일 09:00 + 10분 따라잡기)을 주간 잡으로 개조. `(user_id, 주 시작일)`
  멱등 upsert로 재실행 안전성 유지.
- 크로스 DB 조회는 기존 `AlarmRecipientReader`처럼 읽기 전용 롤 패턴을 따른다
  (was가 monitoring DB를 읽는 방향 — 시스템 경계 원칙과의 정합은 구현 계획에서 확정).
- `alarm_event`의 `dispatch_after` 즉시/09:00 레인 구분은 소비 측에서 무의미해진다
  (적재는 무해하므로 정리 여부는 구현 계획 재량).

## 5. API·읽음 모델

- `GET /v1/notifications` / `POST /v1/notifications/read`: **계약 유지.** 알림 단위가
  일→주로 바뀔 뿐 목록·읽음(id 배열 / all) 구조 동일.
- `GET/PATCH /v1/notification-settings`: 이벤트 종류별 4토글 매트릭스 →
  **주간 이메일 수신 토글 1개**로 계약 변경. **FE 통지 필요.**
- 공지(last-seen)·등록 내역(acknowledged) 읽음 모델은 이번 개편 비범위.

## 6. 이메일

- 주간 다이제스트와 같은 내용을 **주간 리포트 메일 1통**으로 발송. 발송 트리거는
  "주간 다이제스트 생성 직후" — 기존 5분 틱 + 디바운스 디스패처는 불필요해져 제거·단순화.
- 실패 처리(유저 단위 격리, 재시도 상한, at-least-once)와 Resend 발송 스택은 유지.
- 문안은 기존 "임시 카피"를 폐기하고 주간 리포트 형식으로 정식 작성(딥링크 포함).
  사용자向 문안 엠대시 금지 규칙 준수.

## 7. 마이그레이션·이관

- `monitoring_digests` 테이블 재사용: 기존 일일 행은 히스토리로 보존, 신규 행부터
  `digest_date` = 주 시작일(월요일). 스키마 변경 최소(필요 시 expand-contract 준수).
- 옵트아웃 이관: 기존 4종 레코드 중 **하나라도 꺼져 있으면 주간 이메일 off**로 보수적
  이관(사용자의 끈 의사 존중). 이관 후 구 테이블·CHECK 제약은 contract 단계에서 정리.
- 이메일 디스패처 크론(`monitoring.alarm.dispatch-cron`) 등 운영 compose 설정 변경 동반.

## 8. 함정·엣지

- **미표기 재판정 중복**: 사전·프롬프트 갱신 후 리셋·재판정 시 같은 게시물이 다음 주에
  다시 미표기로 잡힐 수 있다. **게시물당 미표기 알림 1회** 가드(알림 이력 마킹) 필수.
- **주간 경계 유실**: 다이제스트 자정 경계 유실(트랙 GG)과 같은 계열. 잡은 "지난주 범위"를
  벽시계가 아닌 **명시적 기간 파라미터**로 받아 재실행·따라잡기를 안전하게 한다.
- **킬 스위치 정합**: `AD_DISCLOSURE_EXPOSE`가 꺼진 환경에서 미표기 섹션이 생성되면
  FE 미노출 정보가 알림으로 새는 사고 — 잡 레벨에서 게이트.
- **주간 이메일 발송 시각 집중**: 월요일 09:00 전 유저 일괄 발송이므로 Resend 호출이
  몰린다. 발송 루프의 레이트·배치 처리 여부를 구현 계획에서 확인.

## 9. 비범위(명시)

- 업데이트 소식(notices) 구조·읽음 모델
- 주간 성과 리포트(성과 대시보드 기반 발행물 — 별도 트랙)
- 저장 인플루언서 워치리스트 알림
- 읽음 모델 3원화 통합(공지·등록 내역은 현행 유지)
- 푸시/웹소켓 등 신규 채널
