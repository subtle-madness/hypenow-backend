## 1. 요청 1(목록 recentComments 제외) — 이미 반영됨, 재측정 요청

요청서의 `recentComments` 7.9MB는 **이전 캡처로 추정**됩니다. 08-12 회신대로 목록·비교는
댓글을 **조회 단계에서 생략**하는 슬림 조립으로 전환해 이미 운영 배포됐고, 이번 2단 조립도
그 계약을 그대로 승계합니다:

- 목록의 `item.post.recentComments`는 **항상 빈 배열**, `commentsCollectedCount`는 0.
- 댓글이 필요한 소비자는 단건 `GET /v1/performance-dashboard/contents/{contentId}`로 오면
  됩니다(전체 이력 + 댓글 포함, 무변경).

**요청**: 현재 운영에서 응답 크기를 한 번 재캡처해 공유해 주세요. 20.8MB 중 댓글 지분이
이미 0이라면, 남은 크기의 주범은 스냅샷 이력이고 그건 이번 `snapshotMode=latest`가 해법입니다.

요청서에 인용된 브랜드 목록의 1.9초 고정비는 **PR #602(08-27 브랜드 게시물 2단 조립) 배포

브랜드 표면에 반영했으니, **배포 후 재측정**을 부탁드립니다. 이번 대시보드 PR ①은 그
2단 조립을 대시보드에 복제한 것입니다.

## 3. PR ①에서 배포되는 것 (요청 2·3)

`GET /v1/performance-dashboard/contents` 파라미터 추가분입니다. **전부 additive**이고,
새 파라미터를 하나도 안 보내면 응답은 종전과 완전히 같습니다(하위 호환).

| 파라미터 | 값 공간 | 기본 | 비고 |
|---|---|---|---|
| `sort` | `uploaded`\|`views`\|`likes`\|`comments`\|`engagement` | `uploaded` | 값 공간 밖 400 |
| `order` | `desc`\|`asc` | `desc` | 값 공간 밖 400 |
| `offset` | 정수 ≥ 0 | (생략 시 전량) | 범위 밖 400 |
| `limit` | 1..100 | 100(`offset`만 준 경우) | 범위 밖 400 |
| `accountIds` | 쉼표 구분 brandAccountId | — | 단수 `brandAccountId`와 둘 다 오면 **`accountIds`가 이김** |
| `authorUsername` | handle(대소문자 무시 일치) | — | 인플루언서 상세 뷰용 |
| `snapshotMode` | `full`\|`latest` | `full` | 옵트인 |

세부 계약:

- **정렬**: 정렬 키가 null인 콘텐츠(조회수 미제공 피드, 좋아요 숨김 등)는 `order`와 무관하게
  **항상 마지막**입니다 — null은 "작은 값"이 아니라 "순위 밖"이라서입니다. 타이브레이크는
  업로드 최신순 → `item.id`라 전순서이고, 그래서 페이지 간 중복·누락이 없습니다.
  `engagement` = (최신 likes + comments) ÷ 작성자 팔로워이며, 분자·분모 어느 쪽이든 미상이거나
  팔로워가 0이면 순위에서 제외(null)합니다.
- **페이지네이션**: `offset`·`limit` **둘 다 생략하면 종전 전량 응답** 그대로입니다. 하나라도
  오면 페이지 모드로 전환됩니다.
- **`accountIds`**: `brandAccountId`와 마찬가지로 **명시하면 `accountType=all`이 함의**됩니다
  (08-12 규칙 승계 — 브랜드를 콕 집어 물었으니 "경쟁사 제외" 기본값을 겹쳐 걸지 않습니다).
  `accountType`을 직접 명시하면 그쪽이 이깁니다.
- **`authorUsername`**: 분류 필터라 `meta.statusCounts` 모수에도 적용됩니다 — 인플루언서 상세
  뷰의 상태 뱃지가 그 작성자 기준이 되도록 하기 위함입니다.
- **`snapshotMode=latest`**: 각 콘텐츠의 `snapshots`를 최신 1개만 싣습니다. 단건 조회는
  무변경(항상 전체 이력)이라, FE가 상세 화면을 단건 GET으로 전환하기 전에도 **배포 순서
  제약 없이** 켜실 수 있습니다.
- **`previousDayValues`**: `post`에 additive로 **항상** 실립니다(`full` 모드에서도). 셰이프는
  `{views, likes, comments}`이고, 직전 스냅샷이 없으면 값은 null이되 **필드 키는 유지**됩니다.
- `meta.page = {offset, limit}`가 additive로 추가됩니다. 전량 응답이면 `{offset: 0, limit: null}`
  (`limit: null` = 자르지 않았다는 표식).

## 4. 명시 확인 3건

**① `previousDayValues`는 "직전 날"이 아니라 "직전 스냅샷"의 값입니다.**
필드 이름이 Day지만 의미는 **직전 스냅샷 행**입니다. 수집이 하루 걸러 뛰면 그 값은 N일 전
관측일 수 있습니다. "▲오늘" 표기의 재료로 쓰시되, 정확히 24시간 델타를 보장하지는 않습니다
(수집 주기는 계정·게시물마다 다릅니다). 스냅샷 자체의 타임스탬프가 필요하면 `snapshots`의
최신 2건을 직접 보시면 됩니다(`snapshotMode=full`).

**② `meta.limit`과 `meta.page.limit`은 다른 값입니다 — 페이지 정보는 `meta.page`만 보세요.**
`meta.limit`은 08-10 목록 상한 철폐 이후 **응답 형태 호환용**으로 남긴 필드라 "필터 적용 후
전체 건수"(= `meta.total`)와 같은 값을 유지합니다(FE가 `total > limit`로 잘림을 판정해도
오탐이 없도록). 페이지 모드에서 실제 페이지 크기는 `meta.page.limit`입니다. 혼동을 피하려면
페이지 관련 판단은 `meta.total` + `meta.page`만 쓰시길 권합니다.

**③ 스냅샷 내 `followers`는 싣지 않습니다.**
요청서 예시에 스냅샷 행의 `followers`가 있었으나, 현 스키마의 스냅샷 행에는 **팔로워 관측이
없습니다**(수집이 게시물 지표만 찍습니다). 작성자 팔로워는 이미 `item.followers`로 내려가고
있으니 그쪽을 쓰시면 됩니다. 시점별 팔로워 추이가 필요하면 별도 수집 설계가 선행돼야 해서
이번 범위 밖입니다.

## 5. 전량 경로는 하위 호환용입니다 — `offset/limit` 전환 권장

`offset`·`limit`을 생략한 전량 경로는 **기존 FE가 깨지지 않게** 남긴 것이고, 서버 비용
절감은 **페이지 모드로 전환한 뒤부터** 발생합니다. 구조상 2단 조립은 요청당 고정비(인덱스)를
새로 내고 그 대신 변동비(카드 조립)를 페이지 크기로 줄이는 거래라, 전량으로 계속 호출하면
고정비만 추가로 냅니다(6절 수치). **탭 3개 모두 페이지 모드로 전환**해 주시길 권합니다.

## 6. 실측 (운영 덤프 복원 + 실코드 하니스, 08-12과 같은 계정)

5,152건 콘텐츠(브랜드 7계정) 기준, 같은 실행에서 구경로·신경로를 나란히 측정했습니다
(로컬 M칩, 2회 반복 — 운영 2코어 박스에서는 절대값이 수 배로 늘지만 비율은 유지됩니다):

| 경로 | 소요 |
|---|---|
| 구경로 전량 조립(2단 전환 전 목록) | 634~659ms |
| 신경로 1단 인덱스(요청당 고정비) | 345~374ms |
| 신경로 2단 하이드레이트 — **전량** | 636~654ms |
| 신경로 2단 하이드레이트 — **20건 페이지** | 7~8ms |

읽는 법:

- **페이지 모드(권장)**: 345 + 8 ≈ **353ms** — 구경로 대비 약 45% 절감. 페이지 크기를 키워도
  2단 비용은 건수에 비례하므로 100건이라도 40ms 안쪽입니다.
- **전량 경로(하위 호환)**: 371 + 646 ≈ **1,017ms** — 구경로(≈640ms) 대비 인덱스 고정비만큼
  늘어납니다. 5절에서 전환을 권하는 이유입니다.

## 8. FE 확인 요청 항목

설계 §4·§5에서 넘어온 것들입니다. **다르게 생각하시면 회신 주세요 — 구현 전에 회수합니다.**

1. **`postCount` 정의(§4)**: "필터 통과 게시물 **전체** 수"로 정의했습니다 — **스냅샷 없는
   게시물도 포함**합니다. 요청서의 "스냅샷 없는 게시물 제외"는 *지표 합산* 규칙으로
   해석했습니다(views·likes·comments 합산에서만 제외). 카드에 "게시물 12개"로 뜨는데 목록을
   열면 15개가 나오는 불일치를 피하려는 판단입니다.
2. **인플루언서 `sort` 값 공간 제안(§4)**: `views|likes|comments|engagement|posts|latest`
   (기본 `views desc`). `engagement` = `ratedEngaged ÷ ratedFollowers`이고 분모 미상·0은 순위
   제외, 타이브레이크는 handle(전순서)입니다. 필요한 축이 더 있으면 알려주세요.
3. **growth 필터 축 통일(§5)**: 요청서 표에는 `from`/`to`/`granularity`/`accountIds`만
   있었지만, **목록과 같은 분류 필터**(`sponsorship`·`accountIds`·`campaignId`·`accountType`)를
   전부 받도록 통일했습니다 — 캠페인·경쟁사 필터가 걸린 개요 탭에서 growth만 못 거르면 결국
   전량 폴백하게 되기 때문입니다(`authorUsername` 부재가 페이지네이션을 무의미하게 만들 뻔한
   전례의 재발 방지). 축이 늘어 곤란한 사정이 있으면 알려주세요.
4. **growth의 `accounts[]`(§5)**: 항상 내려줍니다. 단, **individual(브랜드 미귀속) 콘텐츠는
   최상위 `points`에는 포함되지만 `accounts[]`에는 시리즈가 없습니다**(귀속 브랜드가 없어서).
   계정 비교 차트의 합이 전체와 다를 수 있다는 뜻이니 UI에서 감안해 주세요.
