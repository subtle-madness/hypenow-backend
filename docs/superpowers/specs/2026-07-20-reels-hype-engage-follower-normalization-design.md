# 릴스 hype_score 참여 축 팔로워 정규화 (v2.1)

## 배경 / 문제

hype_score v2(스펙 `2026-07-20-hype-score-v2-redesign`, PR #76 머지·배포)에서
**조회수가 아주 적은 릴스가 과도하게 높은 점수**를 내는 현상이 관측됨.

원인은 릴스 **참여 축의 분모가 조회수**라는 점이다.

```
engage(릴스) = ln(1 + ((likes + comments×3) / views) / e0)
```

조회수가 작으면 `(likes + comments×3) / views` 비율이 폭발한다. 도달 축
(`ln(1 + views/(followers+1000))`)은 낮게 나오지만, **도달:참여 1:1 가중**이라
폭발한 참여가 낮은 도달을 이겨 최종 점수를 끌어올린다. 즉 조회수가 릴스에서
**도달 축과 참여 축 양쪽에 이중으로** 쓰이는 것이 근본 원인이다.

피드는 이미 참여 분모가 `followers+1000`이라 이 문제가 없다.

## 결정

인스타 피처링(탐색 노출) 선정에서 쓰는 `(좋아요+댓글)/팔로워 × 100` 방식을 참고하여,
**릴스 참여 축의 분모를 조회수 → 팔로워로 교체**해 피드와 의미를 통일한다.

교체 후 조회수는 릴스에서 **도달 축에만** 남는다. views = "얼마나 퍼졌나",
engage = "내 오디언스 대비 얼마나 반응했나"로 역할이 분리된다. 조회수 적은 릴스는
좋아요·댓글도 비례해 적으므로 ÷팔로워도 작아지고 도달도 낮아 → 낮은 점수(정상).

100%+ 참여율이 사라지는 방향이 아님을 확인: ÷조회수는 뷰당 참여율이라 대개 한 자릿수
%에 갇히고 100% 초과는 저조회수 아티팩트뿐이었다. ÷팔로워는 팔로워 대비 수백~수천 %가
자연스럽게 나오며, 이 100%+가 "오디언스 대비 바이럴"이라는 **의미 있는 신호**가 된다.

## 변경 범위

| 항목 | 변경 |
|------|------|
| **릴스 참여 축 분모** | `NULLIF(views,0)` → `(COALESCE(followers,0)+1000)` — **핵심(한 줄)** |
| 릴스 도달 축 | `ln(1 + views/(followers+1000))` — **불변** |
| 댓글 가중 | `likes + comments×3` — **불변** (분자는 안 건드림) |
| 피드 참여 축 | 이미 ÷팔로워 — **불변** |
| 도달:참여 1:1 가중(wr=we=1) | **불변** |
| NULL 규칙 | **불변** — 릴스는 도달 축이 여전히 views를 쓰므로 `릴스 ∧ views NULL → NULL` 유지 |
| 화면 참여율 지표 (`03_analysis_baseline.sql`의 `engagement_rate = (likes+comments)/views`) | **손대지 않음** — 랭킹(hype_score)과 표시 지표를 분리 |

대상 파일: `analytics/views/02_serving.sql` `analytics.hype_score(...)` 함수 (현재 47번 줄).

### 변경 후 릴스 축

```
reach  = ln(1 + views/(followers+1000))                                  -- 불변
engage = ln(1 + ((likes + comments×3) / (followers+1000)) / e0)          -- 분모만 교체
Q      = wr·reach + we·engage                                            -- 불변 (1:1)
qf     = Q · 0.5^(elapsed_days/halflife)                                 -- 불변
점수    = qf를 릴스 앵커(p05/p50/p90/p99)로 구간 선형 매핑 [0,100]          -- 앵커 재적합
```

## 튜닝 파라미터 재적합

분모가 바뀌면 릴스 참여 값의 스케일·분포가 달라지므로, 재배포 없이 `app_setting`으로
조정 가능한 기존 키 두 종을 운영 데이터로 재적합한다. **키 이름·함수 시그니처는 불변.**

- **`analytics.hype-reels-e0`** — 새 분모(÷팔로워) 기준 릴스 참여의 중앙값이 기존과
  비슷한 위치에 앉도록 재튜닝. 키 이름은 유지하되 의미가 "뷰당 참여 기준" → "팔로워당
  참여 기준"으로 바뀌므로 함수 주석에 명기.
- **`analytics.hype-anchor-reels-{p05,p50,p90,p99}`** — 변경된 qf 분포에서 백분위
  재산출. 함수 내 COALESCE 기본값도 새 값으로 갱신(단일 소스 원칙).
- **피드 앵커·f0 는 불변.**

실제 수치는 구현 단계에서 운영 릴스 서빙 모수 분포를 쿼리해 산출한다(본 스펙엔 방법만).

## 검증

- **SQL 하니스** (`analytics/test/02_*.test.sql` 컨벤션, BEGIN/ROLLBACK 격리):
  - 저조회수 뭉침 케이스(예: followers=10k, views=200, likes+댓글=340)가
    변경 후 **낮은 점수로 내려가는지**.
  - 진짜 바이럴(팔로워 대비 고참여, 예: followers=1k, views=500k, likes+댓글=43k)이
    **상위를 유지하는지**.
  - 릴스인데 views NULL → 여전히 NULL 반환(도달 축 때문) 확인.
- **운영 분포 스팟체크**: 재적합 전후로 릴스 점수 분포(중앙값 ~45 유지, 상위 뭉침 개수),
  그리고 이전에 튀던 저조회수 릴스들의 점수 하락을 확인 후 운영 뷰 적용·미러.

## 리스크 / 주의

- 운영 뷰 적용은 세션 간 되덮기 방지 위해 반드시 **origin/develop 기준** 워크트리에서
  (메모리 런북 `analytics-prod-view-apply-mirror` 준수). 미러 트리거 시 락 컨보이 주의
  (lock_timeout 재시도).
- 앵커·e0는 함수 기본값(코드)과 `app_setting`(운영)을 **같은 값으로** 맞춰 단일 소스 유지.
- 이번 변경은 원인(분모)만 겨냥한 최소 변경 — 댓글 가중 재검토·피드 재검토는 범위 밖(별도 이슈).
