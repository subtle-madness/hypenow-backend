# [브랜드] 운영 건강 — 게시물 갱신 티어별 상세 테이블

> 상태: 🟢 활성 · ✅ 구현됨

## 배경

'오늘 게시물 갱신' 스탯(대상/미처리 2개 숫자)만으로는 미처리가 떴을 때 **어느 티어에서 왜**
밀렸는지 보이지 않는다. 08-23 실측: 미처리 263건 전부가 3일 티어(14–30일) 게시물의 72시간 경계
레이스(스윕 시각이 직전 touch + 3일보다 몇 초 빨라 due 판정을 비껴감 — 하루 밀림, 다음 날 자동
수습)였는데, 이걸 확인하는 데 서버 DB 즉석 쿼리가 필요했다.

## 설계

기존 스탯(id 120)은 그대로 두고, 같은 "야간 일일 수집" row의 스탯 줄 바로 아래(브랜드별 처리
현황 위)에 **테이블 패널 "오늘 게시물 갱신 — 티어별"(id 122, w24 h7)** 을 추가한다.

- **행 = 티어 6개** — 판정은 `taken_at` 나이, `BrandCrawlPolicy`와 동일 경계:
  매일(0–14일) / 3일(14–30일) / 7일(30–90일) / 30일(90–180일) / 추적 종료(180일+, 보유만) /
  합계(0–180일).
- **열 = 5개** — `보유 = 오늘 처리 + 미처리 + 대기`가 되는 분할:
  - **보유**: 활성 브랜드(closed_at IS NULL)의 해당 구간 게시물 수
  - **오늘 대상**: 오늘 처리 + 미처리
  - **오늘 처리**: `last_crawled_at`이 KST 오늘
  - **미처리**: 지금 기준 due인데 오늘 안 긁힘(`last_crawled_at` NULL 포함 — 정책상 무조건 due)
  - **대기**: 아직 주기 안 지나 due 아님(매일 티어는 정의상 항상 0)
- 쿼리는 기존 스탯과 같은 `hypenow-monitoring-pg` 데이터소스 단일 SQL(티어 버킷 CASE +
  `count(*) FILTER`, 티어 스캐폴드 VALUES에 LEFT JOIN이라 빈 티어도 0으로 행 유지).
  `taken_at` NULL은 기존 패널과 동일하게 제외. 미처리 열은 스탯과 같은 빨강 강조(>0).
- 72시간 경계 레이스로 미처리에 "진짜 지연이 아닌 하루 밀림"이 섞이는 것은 패널 설명에
  명시한다 — 레이스 자체 수정(슬랙)은 이 작업 범위 밖.
