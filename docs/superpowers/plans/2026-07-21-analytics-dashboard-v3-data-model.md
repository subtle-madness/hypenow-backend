# 분석 대시보드 v3 — 파이프라인 데이터 모델 재설계 (핸드오프)

> 상태: 🟢 활성 · 다음 세션 실행 대기
> 작성: 2026-07-21 (대시보드 v2 배포·운영 실측 직후)
> 선행: PR #102(대시보드 v2)·#104(릴리스) — 배포 완료. v2는 표시 개선이었고, 본 문서는 **모델 재설계**.

## 0. 왜 다시 하나 — v2의 근본 결함

v2 퍼널 `수집 31,038 → 후보 4,212 → 분석 16,827 → 미러 30,358`은 **깔때기가 아니다**.
각 단계의 모수·시점이 달라 숫자가 역전된다(후보 < 분석 < 미러). 운영 실측으로 규명한 원인:

1. **스냅샷 vs 누적 혼재** — 후보(raw 뷰)는 "현재 시점 자격"이고, 분석 완료(analysis)는 "역대 누적".
   최근12 윈도우는 새 게시물이 옛것을 밀어내므로, 백필 분석분 14,637은 대부분 이미 후보 자격에서
   이탈했다. 누적(16,827) > 현재 후보(7,402)는 그래서 정상이지만, 한 줄에 그리면 오독된다.
2. **미러는 분석의 다음 단계가 아니다** — 미러(30,358)는 수집→서빙의 **독립 경로**(분석 무관 전체).
   퍼널 마지막 칸에 둔 것 자체가 오류.
3. **모수가 살아 움직인다** — 07-21 뷰티 판정 v2 재판정이 돌면서 뷰티 모수가 1,496 → 723계정
   (진행 중, 계속 변동)으로 축소. raw는 새 세계, 미러(1,515계정·30,358건)는 옛 세계.
   커버리지·계정 카피 % 가 판정 리비전을 넘나들며 왜곡된다(카피 1,517/모수 723 같은 >100%).
4. **"진짜 잔여"를 아무도 계산 안 한다** — 후보 ∩ 미분석은 크로스 DB 대조가 필요한데
   UI·통계 어디에도 없다. 실측: **후보 7,402 중 기분석 7,116, 미분석 286** — 사용자가 알고
   싶었던 숫자는 바로 이 286.

## 1. 실제 파이프라인 (2026-07-21 15:00 KST 운영 실측)

### 계정 축 (raw, 현재 스냅샷)
```
크롤 수집 계정            14,123
└ 프로필 검증 QUALIFIED    1,714
  ├ 뷰티 개인(서빙 모수)     723  ← v_accounts. 판정 v2 진행 중이라 변동
  ├ 뷰티 회사(제외)          169
  └ 비뷰티                   822
판정 v2 재판정: 07-21 1,861명 완료 + 1,977명 배치 실행 중 (BeautyJob 로그)
계정 카피 누적: 1,517핸들 — 현 모수(723) 대비 794+ 는 탈락 계정의 카피 (재정의 필요)
```

### 콘텐츠 축 (raw, 현재 스냅샷)
```
수집 전체                 31,038
└ ENUMERATION            31,010
  └ 뷰티 모수 콘텐츠       12,777  ← v_serving_content (모수 축소 반영, 변동 중)
    └ 핀 지표 계산 가능    12,563  ← v_contents
      └ 캡션 있음          12,506
        └ 분석 자격        7,402  ← v_analysis_candidates = 성숙(제때창 완전 경과)
          |                          ∩ (timely OR 최근12 윈도우)
          ├ timely          1,435  → 분석되면 metric_timeliness='timely' → 랭킹 노출
          ├ 윈도우 전용     5,967  → 분석되면 'late_backfill' → 인플루언서 상세만
          └ (기분석 7,116 / 미분석 286)   ← 크로스 DB comm 실측
        └ 자격 밖          ~5,104  = 미성숙(창 미닫힘) + 늦크롤&윈도우 밖(영구 미분석)
```

### 분석 결과 (analysis DB, 역대 누적 — 모수 리비전 혼재)
```
content_analyses 16,827 = timely 1,745 + late_backfill 14,637 + 레거시NULL 440 + immature 5
· 랭킹 노출 = timely OR NULL(레거시) — late_backfill 제외 (07-21 정책, memory 참조)
· 누적에는 판정 v1 시절(1,496계정) 분석분이 섞여 있어 현 모수 기준 커버리지의 분자가 아님
account_analyses 1,517핸들 (미러 accounts 1,515에도 없는 것 3)
```

### 미러 (analysis DB ← raw 서빙 뷰, TRUNCATE+INSERT)
```
미러 accounts 1,515 · contents 30,358 = 판정 v1 세계의 스냅샷 (다음 미러 때 723/12,777대로 축소 예정)
미러 스냅샷 최신 = raw 스냅샷 최신 = 07-20 14:42 → 미러 문제가 아니라 크롤 지표 수집이 그 후 없음
```

### 백필 배치 (완결된 1회성)
07-20 재도입 배치가 당시 후보 전량을 수거해 14,637 적재 완료(memory: vertex-migration-backfill).
상시 흐름은 일상 잡이 흡수 — "백필이 몇 건 일어나야 하나"의 답은 이제 **후보 중 미분석(286)**
하나로 수렴한다(그 안의 timely/윈도우 구분이 마킹을 정할 뿐).

## 2. 대시보드 v3 목표 모델 — 퍼널 폐기, 2축+상태 전이

사용자 질문에 1:1 대응하는 구성:

### A. 계정 보드
| 질문 | 표시 | 소스 |
|---|---|---|
| 계정 총 몇 명? | 수집 14,123 → QUALIFIED 1,714 | raw influencer |
| 뷰티 인플루언서 몇 명? | 723 (회사 169·비뷰티 822 제외) | v_accounts + 상태 분해 |
| 판정이 돌고 있나? | "재판정 진행 중 N명" 배지 | beauty_judged_at 오늘 count + (갭 G3) |
| 신규 뷰티 유입? | 오늘 첫 판정 뷰티 N | beauty_judged_at + (갭 G3: 이전값 히스토리 없음) |
| 계정 카피는? | 현 모수 723 중 카피 보유 X · stale 대상 Y | 크로스 DB 조인 (갭 G1) |

### B. 콘텐츠 보드 (모수 = 현재 raw 스냅샷으로 통일)
```
수집 31,038 → 뷰티 서빙 12,777 → 분석 자격 7,402
                                  ├ 랭킹 트랙(timely)   1,435 [기분석 a / 미분석 b]
                                  ├ 상세 트랙(윈도우)   5,967 [기분석 c / 미분석 d]
                                  └ 진짜 잔여 = b+d = 286 · 오늘 배치 상한 대비 소요일
자격 밖 5,104 (미성숙 △ / 영구 제외 ▽ 구분 표시)
```
- **누적(16,827)은 참고 각주로 강등** — "역대 분석 저장 총량(모수 리비전 혼재)".
- 커버리지 재정의: **현 서빙 콘텐츠 12,777 중 분석 보유율** (미러 후 analysis 조인로 계산).

### C. 건강 보드 (v2 유지 + 라벨 수정)
- "마지막 미러" → **"크롤 지표 신선도"로 개명** (실체는 max(captured_at) — 이번에 크롤 멈춤을
  정확히 잡아낸 유용한 신호였으나 이름이 오해 유발).
- 미러 잡 자체 실행 시각은 별도 표기 (갭 G4).

## 3. 데이터 갭 — 다음 세션 작업 목록 (우선순위순)

- **G1. 크로스 DB 잔여 대조** ⭐ 핵심 — 후보 ∩ 미분석(286)을 계산할 수단이 없다.
  ContentAnalysisJob이 이미 하는 대조(analyzed set 로드 → 후보 필터)를 PipelineStatsService
  무거운 집계에 편입: analysis에서 short_code 셋 로드 → raw 후보 뷰와 Java에서 대조.
  트랙별(timely/윈도우) 기분석/미분석 4분할까지. 계정 카피도 동일(raw 723 핸들 ∩ analysis 최신 카피).
- **G2. 커버리지 재정의** — 분자·분모를 "현 서빙 모수" 기준으로. 미러 직후가 정합 시점이므로
  미러 잡 끝에 계산·기록하는 방안 검토.
- **G3. 뷰티 판정 히스토리 부재** — 신규/이탈 뷰티 계정을 추적할 이전 판정값이 없다
  (beauty_judged_at만 존재). influencer 판정 변경 로그 테이블 필요 — **crawler 영역이라
  시스템 경계 준수**(분석 세션에서 raw 스키마 변경 금지, crawler 트랙으로 의뢰).
- **G4. 미러 잡 실행 시각 미영속** — RunHistory는 인메모리(재시작 소실). 최소안: analytics가
  자기 DB(analysis)에 잡 실행 기록 1행 테이블. 대안: app_setting은 raw라 경계 위반 아님(값 UPDATE는
  runtime toggle 관례) — 단 "기준값은 Flyway 시드" 컨벤션과 충돌하지 않게 검토.
- **G5. ~~크롤 지표 수집 멈춤~~ → 이슈 아님 (07-21 정정)** — 지표 수집은 **팀원이 수동 실행**하는
  운영 방식이라, 스냅샷 신선도가 어제에 머무는 것은 수동 사이클 사이의 정상 공백이다.
  대시보드 함의: "크롤 지표 신선도" 표시의 등급(ok/warn/bad) 임계값을 자동 크론 전제(26h/50h)가
  아니라 수동 운영 리듬에 맞게 완화하거나, 등급 없이 시각만 표시할 것.
- **G6. 판정 리비전 마킹** — content_analyses·account_analyses에 "당시 모수 리비전" 개념이 없어
  누적 통계가 리비전을 넘나든다. 최소한 대시보드에서 "현 모수 교집합"만 세는 것으로 우회(G1·G2로
  해결 가능, 스키마 변경은 보류).
