캠페인 관리 API — 목 데이터 규모 스윕

캠페인 관리 화면의 두 조회 API(GET /v1/monitoring/items, GET /v1/monitoring/campaigns)를 로컬 벤치 DB에 파라미터별 목 데이터를 재시드해 가며 측정했다. 축 하나씩만 바꾸는 스윕으로 "데이터가 커지면 어디부터 느려지는가"를 귀속시키는 것이 목적.

결론: 데이터 규모는 병목이 아니다. 전체 테이블을 운영의 450배(스냅샷 40만 행)로 키워도 응답은 18ms로 평평하고, 유일하게 기울기가 있는 축은 요청 유저 자신의 추적 행 수(K)뿐인데 그마저 행당 ~0.65ms의 깨끗한 선형이라 극단(300행)에도 213ms다. 운영에서 관측된 1.8~62초 꼬리는 이 데이터로는 재현되지 않는다 — 쿼리·스키마가 아니라 운영 환경 요인(2코어 서버의 자원 경합·대기)이라는 앞선 추정이 배제법으로 굳어졌다.

축별 지연 곡선 — GET /v1/monitoring/items

/v1/monitoring/campaigns는 전 구간 3~4ms로 변동이 없어 차트에서 제외했다(아래 표 참조).

전체 측정표

각 포인트는 재시드 + ANALYZE 후 워밍업 5회, 본측정 50회. 기준점은 N=10 · M=3 · K=12 · D=8 · C=12(운영 실측 분포 재현).

후속 실험 — 운영 꼬리의 범인: 커넥션 풀 대기 재현

메커니즘 확정: monitoring-ro 풀(3개) 고갈 대기. 31행 테이블의 max()가 2.4초까지 부푸는 동안 같은 DB의 app 풀 쿼리는 평시 그대로다 — 쿼리 비용이 아니라 커넥션 획득 대기이고, 이는 운영 단계 로그의 시그니처("하찮은 쿼리에 1.8초")와 정확히 일치한다. 운영에선 백업 등으로 쿼리가 일시 느려지는 순간 3짜리 풀이 즉시 마르며 증폭됐을 것. 수리 후보: 풀 확대(단 2코어 서버 제약 고려), monitoring 쿼리 왕복 병합(7회→1~2회 — 풀 점유 시간 자체를 축소), lastSuccessfulSweepAt 캐싱.

수리와 검증 — monitoring 왕복 병합 7회 → 3회

진단에 따라 GET /v1/monitoring/items의 monitoring DB 왕복을 병합했다: target·last_sweep·post_meta·profile_meta·최신 팔로워 5개 왕복을 단일 SQL(LEFT JOIN + LATERAL, findTargetDetails)로 접고, 행 수가 많은 스냅샷·댓글만 별도 왕복으로 남겼다. 풀(3개) 획득 횟수가 요청당 7회→3회가 되므로 경합 시 대기줄에 서는 횟수 자체가 줄어든다. 기존 통합 테스트 105개 전부 통과(동작 보존).

읽는 법: 개선의 본체는 꼬리(최악치)다. 극한 시드의 평균은 스냅샷·댓글 실작업이 지배해 소폭이지만, 풀 대기가 증폭시키던 최악치는 절반 가까이 줄었고(12.3초→7.0초), "0ms짜리 쿼리가 대기로 2.4초"가 되던 왕복 5개는 아예 사라졌다. 운영의 문제 상황 — 경합 순간의 증폭 — 에 정확히 작용하는 개선이다. 부수 효과로 팔로워 스냅샷 followers NULL이 500을 내던 NPE 함정도 목록 경로에서 제거됐다.

운영 관측과의 대조

로컬 기준점(운영 규모 재현) p50 18ms는 운영 엣지 p50 29ms와 같은 자릿수로, 벤치 환경이 운영의 평시 성능을 정상적으로 재현함을 확인했다. 그러나 운영의 꼬리는 다르다:

  • 운영 7일간 GET /v1/monitoring/items p99 2.8초, 최대 62.6초 — 이 스윕의 어떤 포인트도 240ms를 넘지 못했다.
  • 운영 단계 분해 로그에서 1.8초가 걸린 findTargets는 134행 테이블의 PK IN 조회, 1.8초가 걸린 lastSuccessfulSweepAt은 31행 테이블의 단일 max()다 — 플랜 문제로는 성립 불가.
  • 8~62초 클러스터(08-25 15:51~52 KST)는 백업 직스트리밍 전환으로 서버 CPU가 포화됐던 시각과 겹친다.
다음 단계. 데이터·쿼리 트랙은 종결, 풀 대기 메커니즘은 위 실험으로 확정. 남은 것은 ① 운영 측 귀속 교차 확인(지연 시각 ↔ 백업 크론·CPU 메트릭·Hikari 대기 카운트, 전부 읽기 전용) — 선택 사항, ② 수리: monitoring 쿼리 왕복 병합(요청당 7회→1~2회)이 풀 점유 시간과 K 선형 기울기를 동시에 줄이는 최선 후보이고, 개선 전/후는 이 하네스(bench/concurrent.sh 동시 20 기준)로 검증한다.

재현 방법

# 벤치 DB(전용 컨테이너, 포트 5544) + was 8091 기동 상태에서
bench/seed.sh prod            # 운영 재현 규모 시드 (x10 | x100 | --옵션 지정)
bench/run.sh 라벨              # 로그인→워밍업→50회 측정, p50/p95/p99 출력
bench/sweep.sh all            # K·D·C·N 축 전체 스윕 → bench/results/*.csv

시드는 두 DB에 걸친다 — app 스키마(유저·캠페인·추적 행)와 monitoring DB(target·post_meta·post_snapshot· post_comment·profile_meta·profile_snapshot·sweep_run). 운영 실측 분포(POST 69:31, 상태 TRACKING 59% 등)와 조립 경로 계약(sweep_run ok=true 필수, FEED views NULL, followers NOT NULL)을 반영했다. 전부 로컬 — 운영에는 아무것도 쓰지 않았다.
